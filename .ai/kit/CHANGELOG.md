## [1.2.0] - 2026-11-21

### Added
- A feature map for a project whose user interface has navigable screens, windows, or scenes: «Project Wiki» in `project-overlay.md` keeps `wiki/features.md`, with one entry per screen, window, or scene and one per feature reached inside it, each with its canonical term, the file that defines it, and the steps or command (a `commands.*` key or a project script) that reach it in the running app, or a link to the spec whose user flow gives them. Steps nobody has run are marked unverified until a run follows them, a screen behind sign-in names where its test account comes from but never its values, a repository with several apps keeps one page per app linked from `features.md`, and a command-line tool keeps none. Once the page exists, a change that adds, renames, or removes a screen or feature, or changes how one is reached, updates it in the same unit. `codebase-onboard` drafts it in step 10, with every reach step unverified, and also runs when such a project has no `features.md`, drafting only the map when the profile and `overview.md` are in place; step 11 presents the drafted pages. `domain-terms.md` resolves a UI part the user names by its position or look by finding the screen in the map and the part in the file the entry cites or in the running app, and the first evidence item of «Evidence Format» in `verification.md` writes out the steps taken to each UI state from its screen's entry. Before, the project wiki had no place for the names and routes of screens, so agents guessed what a loosely described UI part meant and searched again for how to reach each changed state. (minor)

### Changed
- «Edit Boundaries» in `change-scope.md`: matching the surrounding code leaves out a workaround whose comment names the defect it masks; new code that needs the same workaround settles it under the workaround rule in «Before Editing» instead of copying it, and the maintainability check of `code-review-perform` follows the exception. Before, "match the surrounding code" also told agents to copy such a workaround into new code, spreading it as the project's pattern. (minor)

### Migration
1. If the project's user interface has navigable screens, windows, or scenes and `.ai/project/wiki/features.md` does not exist, ask the user whether to draft the feature map with `codebase-onboard`, which then drafts only the map when `.ai/project/profile.toml` and `.ai/project/wiki/overview.md` are already in place.

## [1.1.0] - 2026-11-21

### Changed
- «Where Knowledge Goes» in `memory-policy.md` orders the stores for a rule learned from a correction: first a code change that makes the mistake impossible, such as a type that cannot be built in an invalid state, then an automated check, and a written store only for a rule whose application needs judgment a tool cannot make; step 3 of «Promotion» also moves a lesson into a code change. `kit-lesson-capture` follows that order, with the code change and the automated check as its first two destinations: it makes the change or adds the check in the current unit only when that unit's request covers it, and otherwise registers it and keeps the lesson until it lands, appending one only when no lesson or page states the rule yet. It bounds each lesson by the condition its evidence supports, continues past an existing written owner when the mistake happened anyway and a code change or check can hold the rule, and still names or proposes a lesson that would help every project, whatever store holds it. When it adds a check to code that already breaks the rule, it exempts the existing places by a baseline or exclusion list that only shrinks, so the check fails only on new ones, and registers their cleanup as its own unit; every check it adds has a failure message that names the fix. Before, every store in the table was equally eligible, so a mistake a tool could catch could be kept only as a lesson that works when the next agent reads it, one correction could turn into a rule for every case, a check was added whenever the unit owned its configuration even when its request did not cover it, and a check that was only registered left no lesson behind until it landed. (minor)
- «Before Editing» in `change-scope.md`: when a change works only by masking a defect outside the request (a delay or timer, a retry, a guard against a state the code should never reach), choosing between fixing the defect and the workaround is a decision the user owns, put to the user per «Stop, Pause, or Proceed» before the workaround is written; a workaround the user accepts gets a comment that names the defect and links its issue when it has one, in place of a comment arguing that it is right. Step 7 of `bug-diagnose` links the rule for a root cause outside the unit, and the report then states that the root cause is unfixed and names its issue when it has one. Before, no rule covered a workaround for a defect outside the request, so a justified workaround could become the pattern the next agent copies. (minor)
- The UI row of «Verification By Change Type» in `verification.md` reaches each changed state in the running app (`commands.run` or `commands.e2e`) with a screenshot, recording, or captured output of it, and gives the states checked and how only when the app cannot run; «Evidence Format» records each such state in three ways: what was done to reach it and what it showed, written into the report and the pull request body (the merge commit body with `hosting.platform = "none"`) so the record outlives the files; the artifact as a file in a work folder named by its absolute path, for reviewers on that machine, with no path in the report of work that has no task branch since its folder is gone by then; and, with a hosting platform, what lets its reviewers see each file: the link to the CI run when the project's CI runs the same check and publishes its artifacts, or else the file listed by its absolute path for the user to attach before the merge, never committed. The evidence check of `code-review-perform` asks for that evidence, or the fallback, on a UI change. Before, a UI change needed only a manual description of the states checked, even in a project that could run the app. (minor)
- Step 1 of `test-add`: a behavior that must hold a property for every input in a space too large to list (a parser and printer or an encoder and decoder that round-trip, an invariant a state machine keeps, a result that ignores input order) gets a property-based test that generates the inputs from a fixed seed, with each failing input it finds added as a fixed case. Before, the cases covered only hand-picked inputs. (minor)

## [1.0.0] - 2026-11-20

### Added
- «Layers and Precedence» in `ssot.md`: the project overlay may replace policy rules of one section of a core wiki page for its own project. A replacement is a `project.guardrails` entry that starts with the fixed prefix `Replaces «<Section>» in <page>.md:` and states only the project's rule, for example "Replaces «When To Plan» in planning.md: a plan file starts at five steps instead of three."; it may link a page in `.ai/project/wiki/` for detail, and an entry without the prefix replaces nothing. It replaces only the rules of that section that the entry contradicts: the section's other rules and every invariant that binds the new behavior still apply, and a skill that links the section follows the entry. An agent card's `Owns` and `Does Not Own` and a skill's steps are never targets; they change only through local cards and local skills. The invariants are exactly the rules on pages under the kit's `core/wiki/principles/`. `AGENTS.md` «Project Rules» now opens with a line saying that an entry with that prefix replaces those rules in the project, including their summary lines in «Stop First». The policy row of «Rule Types» names the replacement, «Where Knowledge Goes» in `memory-policy.md` sends a project rule that departs from a core policy there, and `project-overlay.md`, `page-spec.md`, «Layers» in `architecture.md`, «Consumer Updates» in `versioning.md`, «Adopt Existing Instructions» in `installation.md`, `kit-install`, `kit-lesson-capture`, `kit-librarian`, and the `guardrails` comment in the profile template point to it where they used to forbid any departure from a core rule or send it upstream. Before, the overlay could only set the parameters the core exposes, add facts, and narrow roles, so every core policy without a profile key bound every project, and the only way out was an upstream proposal that changed the rule for everyone. (minor)
- Profile key `policy.review_gate`, owned by «Choosing Gates» in `review.md`: `all` sends every review-ready change through the agent review gates; `non-trivial`, the default, skips them only for a typo or formatting fix that changes no meaning, a comment-only edit that touches no comment a tool reads (lint or type suppressions, build tags, pragmas, doctests), or regenerated output reproduced from unchanged sources by an unchanged generator, never a lockfile or other output of dependency resolution; `none` runs no agent gate, the security and accessibility gates included, and leaves review to the project's own pull request review, if it has one. In the kit repository the `role-governor` gate applies under every value. The report names each skipped gate and why. Step 10 of `request-lifecycle.md`, «Fan-In» in `concurrency.md`, and «Flow» in `change-intake.md` link that section instead of assuming that a review always runs, and `AGENTS.md` lists the key. Before, a trivial change could skip review only "when the project allows it", with no place for the project to say so and no definition of trivial beyond two examples, and a project with its own human review had no way to turn the agent gates off. A profile that does not set the key now lets trivial changes skip the agent gates. (major)
- Profile key `evolution.propose_upstream`, default `false`, owned by step 4 of «Promotion» in `memory-policy.md`: with `false`, agents never start an upstream proposal on their own. `kit-upstream-propose` runs only when the user asks, and a lesson, rule, or kit defect that would help every project is named in the report as a candidate and kept in `.ai/project/lessons.md`. With `true`, agents propose as before. `kit-upstream-propose` (its description, «Use When», and «Do Not Use When»), `kit-lesson-capture`, «Layers and Precedence» in `ssot.md`, «Sources Of Change» in `change-intake.md`, `project-overlay.md`, and «Consumer Updates» in `versioning.md` follow the key, and `AGENTS.md` now lists the `[evolution]` keys with the other parameters. Before, the agents of every installed project prepared kit proposals whenever a lesson looked generic, spending that project's time on the kit without the project choosing to. (major)
- Skill field `scope: kit-repo` («Frontmatter» in `skill-spec.md`), set on `kit-stack-add` and `kit-trend-scan`: such a skill is active only in the kit repository, so installed projects neither render nor catalog it, and `check` does not warn that `kit-librarian` or `trend-scout` lists it. `check` rejects any other `scope` value. Before, every installed project got both skills although the «Do Not Use When» of each rules out installed projects. The next `sync` in an installed project removes their generated folders, such as `.claude/skills/kit-stack-add/`; nothing else needs to change. `codebase-onboard` and `kit-agent-add` send a missing stack pack to `kit-stack-add` only in the kit repository, and otherwise to step 4 of «Promotion» in `memory-policy.md`; `kit-freshness-review` and `kit-external-adapt` send checks of watched tools to `kit-trend-scan` only in the kit repository, and otherwise to `kit-update`. Rendered agent cards leave a skill the project does not render out of «Skills», so `kit-librarian` and `trend-scout` no longer point to one, and `check` warns when `skills.enabled` names such a skill, or a project skill is ruled out, instead of leaving it out silently. (minor)

### Changed
- «Changelog» in `documentation.md`: the project keeps a changelog only when `docs.changelog`, or a package's `changelog` in `release.packages`, names a file that exists, every changelog rule applies only then, and agents never create a changelog file the project does not have. `project-docs-sync`, the doc-sync check of `code-review-perform`, `code-migration`, `dependency-upgrade`, «Compatibility» in `code-changes.md`, «Release Scope», «Promotion», and «Changelog Finalization» in `release.md`, and steps 3 and 6 of `release-cut` link that condition; «Tags And Notes» in `release.md` has release notes summarize the pull requests merged since the previous tag when there is no changelog (the commits with `hosting.platform = "none"`, since the first commit for a first release). Before, any non-empty `docs.changelog`, such as the default `CHANGELOG.md` left unchanged, turned these rules on in a project that keeps no changelog: agents could create the file at the first user-visible change, every breaking change required an entry, reviews asked for missing entries, and a release flagged every commit as having none. (minor)
- «Specifications» and «Decision Records» in `documentation.md`: with `docs.specs_dir` empty the project keeps no spec files, and with `docs.adr_dir` empty no decision records; the requirements, or the decision with its context, options and their trade-offs, and consequences, go in the unit's issue or pull request body; without an issue the plan holds the requirements until the pull request opens, and with `hosting.platform = "none"` the commit message body takes the place of the pull request body. `requirements-spec-write` writes the spec there in that case, `adr-write` sends such a decision there, `github-issue-create`, `requirements-analyst`, and `software-architect` follow the same places, and `schema-migration` and `code-migration` run `adr-write` only when `docs.adr_dir` is set. Before, an empty key left no place for a spec or a decision record, while those skills still searched and saved into the empty path. (minor)
- Profile template defaults no longer prescribe one team's workflow. `policy.integration_branch` is `"main"` (was `"develop"`) and `policy.protected_branches` is `["main"]` (was `["develop", "main"]`), so integration and release share one branch; `policy.issue_first` and `policy.worktrees` are `false` (were `true`); `policy.commit_convention` is `"none"` (was `"conventional"`); `hosting.platform` is `"none"` (was `"github"`) and `hosting.ci` is `false` (was `true`); `docs.changelog`, `docs.specs_dir`, `docs.adr_dir`, and `docs.glossary` are empty (were `"CHANGELOG.md"`, `"docs/specs"`, `"docs/adr"`, and `".ai/project/wiki/glossary.md"`). `install` no longer creates `.ai/project/wiki/glossary.md`; a project that sets `docs.glossary` starts that file from the glossary template, as the profile template's comment says; with `docs.glossary` empty, `domain-terms.md`, «Terminology» in `translation.md`, `translate`, and `localization-specialist` keep terms and renderings consistent within the change instead of adding glossary entries. Before, every install inherited the kit maintainer's branch flow, issue tracker, worktrees, CI, commit convention, and document paths without deciding them, and a project that relied on the defaults kept following them. A project that sets none of these keys now works trunk-based on `main`, with no issue or worktree requirement, no hosting platform, and no changelog, spec, decision-record, or glossary path. (major)
- `codebase-onboard` also proposes `policy.*`, `hosting.*`, and `docs.*` values, each with its evidence: the integration, release, and protected branches from the remote's default branch and its long-lived branches, `policy.commit_convention` from recent commit subjects, `hosting.platform` from the remote URL, `hosting.ci` from CI configuration, and document paths from files that exist; it asks the user to decide `policy.issue_first` and `policy.worktrees`. `kit-install` writes the confirmed values into `.ai/project/profile.toml` explicitly, even those that equal a default; only when `policy.integration_branch` differs from `policy.release_branch` does it propose creating the integration branch if it is missing and making it the default branch unless it already is; and with `hosting.platform = "none"` it opens no pull request and proposes no repository settings, following «Scaling The Order» in `request-lifecycle.md`. `check` no longer warns about `[policy]`, `[hosting]`, or `[docs]` keys that repeat a default, and «Profile» in `project-overlay.md` and the starter profile say to keep those values explicit. Before, the kit told projects to keep only keys that differ from a default, so a kit update that changed a default also changed a project's branches, hosting, or document paths, and `kit-install` proposed an integration branch even for a single-branch flow, and a pull request and repository settings even for a project without a hosting platform. (minor)
- `update` no longer writes `.gitattributes`: it prints the agentkit lines the file lacks and warns that, without them, a checkout that converts line endings lists every file the update rewrote as modified; `install` still appends them. `update` also prints, for each key the profile leaves unset whose default changes, the old and new default and the line that keeps the previous behavior, and for each key the profile sets that the kit no longer reads, a pointer to the Migration notes; for a `[policy]`, `[hosting]`, or `[docs]` key that still holds an old default, it names the line that sets the new default instead of telling the project to remove the key; `kit-update` asks the user about each line. Before, `update` changed a project-owned file without asking, a project that relied on a changed default learned of it only from the changelog, a removed key was reported with the new default `None`, and a policy, hosting, or docs value was to be removed to adopt a new default, against keeping those values explicit. Both changes live in the installed updater, so they first take effect when a project that runs this version updates to a later one. (minor)
- «Labels» in `issues-and-prs.md`: the project owns its label set. Agents apply only labels the repository already has. When it has no kind labels, they propose `bug`, `enhancement`, and `documentation` to the user before creating any. Area labels apply only when `hosting.area_labels` lists areas, one label per area matching the commit scope. `blocked` is an optional marker, and a blocked issue states its blocker in its body either way; an item without a "done when" gets the project's label for such items only when one exists. The kit repository's `intake` label moved to `kit-upstream-propose`, which applies it when filing there. `github-issue-create`, `github-issue-triage`, `github-pr-create`, and the label review in the last step of `kit-install` follow the section. Before, the kit prescribed five kind labels, an area axis, and the `intake` marker for every repository, agents created a missing label on their own, and no kit file read `hosting.area_labels`. (major)
- The `continue` verdict from `role-governor` is required only for new agents, sections, and invariant changes in the kit's core. `role-governor` gives its verdicts and approves new agents and sections for the kit's core; in an installed project it audits on request and handles ownership gaps. `kit-librarian`, «Use When» of `kit-role-audit`, step 4 of `kit-agent-add`, and the `role-governor` row of «Choosing Gates» in `review.md` say so; that row now also names invariant changes and applies under every `policy.review_gate` value, and «Triage» in `change-intake.md` links it instead of repeating it. For a local card in an installed project's overlay, the adding agent compares the card's `Owns` with every active owner itself and re-runs «Selection Procedure» in `routing.md` on each sample task, which must resolve to exactly one owner. Before, adding a project-local agent required the structural audit meant for the kit's shared catalog. (minor)
- `release-manager` integrates only commits that carry an `approve` disposition from each gate «Choosing Gates» in `review.md` selects for them, or, when that section selects none, the project's own pull request approval, or the user's go-ahead when the project reviews no pull requests. Before, it integrated only branches with an `approve` disposition, which a change exempt from the gates under `policy.review_gate` never gets. (minor)
- «Never Fake Success», «Confirm Before Irreversible Or Outward Actions», and «Secrets And Sensitive Data» in `integrity.md` now own three rules from pages a project can replace, and those pages link them: never approve your own work (from «Role Protocol» in `delegation.md`); act as the account, and on the repository or service, that the task names, and stop instead of falling back to another (from «Platform Preflight» in `issues-and-prs.md`); and never reach data that sign-in or permissions block with other credentials (from «Reading Metrics» in `product-evidence.md`). Before, the fallback rule covered only the `gh` preflight and the credentials rule only metric sources, and all three sat outside the invariants. (major)
- `tech-radar.md`, `change-intake.md`, and `model-calibration.md` state in «When» that they apply when maintaining the kit repository and are read-only in an installed project; `model-calibration.md` keeps «Tier Mapping» and the project's own `[scaffold]` rules in scope there, and the evolution section index says how to read these lines; `trend-scout` says it works only in the kit repository. «Scaffold Rules» notes that the kit core is `.ai/kit/core` in an installed project. Before, an agent in an installed project could take the radar scan, intake triage, or calibration procedure as work for that project, and the search command named a `core` folder that does not exist there. (patch)

- `volatility` and `reviewed` are required only on kit files. On overlay pages, local agents, and local skills under `.ai/project/` they are optional, and `freshness` and `check` track an overlay file only when it has both («Metadata» in `freshness-policy.md`); `check` warns when an overlay file has only one of them. The frontmatter tables in `page-spec.md`, `agent-spec.md`, and `skill-spec.md` say so, and the overlay `wiki/README.md` and `wiki/glossary.md` that `install` copies no longer carry the two fields. `agentkit.py new agent|skill|page` leaves them out of overlay files too, so a new overlay file stays untracked until its author adds both, and keeps them with `--core`; step 5 of `kit-page-add` sets `volatility` on a project page only together with `reviewed`. (minor)

Before, a long project page or lessons file, or a profile with many `project.guardrails`, failed `check`, although the project, not the kit, decides how much of its own text to keep. (minor)
- `hosting.platform = "none"` makes the `github` skill category inactive: `sync` renders and catalogs no `github-*` skill, rendered agent cards such as `release-manager` no longer list one, `check` does not warn that an active agent lists one, and it warns when `skills.enabled` names one. `check` reports an error unless `hosting.platform` is `"github"` or `"none"`. A project with `hosting.platform = "none"` loses the generated `github-*` skill folders at its next `sync`. (minor)
- «Scaling The Order» in `request-lifecycle.md`: with `hosting.platform = "none"`, a unit ends with a merge the user approves, `git merge --no-ff <branch>` into the integration branch, pushed when the branch has a remote, and the merge commit body is the unit's record: its goal, its done-when, and what «Pull Request Body» in `issues-and-prs.md` asks of a pull request body, including `Work-Folder: <absolute path>` lines per «Work Folders» in `git-workflow.md`. A promotion without a platform is the same kind of approved merge into the release branch («Promotion» in `release.md`). The protected-branch rule and «Stop Conditions» in `git-workflow.md`, the main checkout's coordination uses in «Worktrees», `git-conflict-resolve`, «Fan-In» in `concurrency.md`, and the profile template comments name these paths, «Stop First» in `AGENTS.md` renders it, specs and decisions without their folders move into the merge commit body (`documentation.md`), release notes without a changelog summarize the units' merge commits (`release.md`), `release-cut` and `kit-install` merge this way, and `git-worktree-cleanup` finds the merge commit with `git rev-list --ancestry-path --merges --first-parent`, uses it only when its second parent is the task branch's tip, reads the work folders from its body, and otherwise stops and asks the user. Before, the unit was recorded only in its plan, which «Closeout» deletes and a small unit does not have, and the protected branches named no way in without a pull request. (minor)
