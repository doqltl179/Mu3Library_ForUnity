# Clean Up Merged Unit

## Use When
- A unit's pull request merged into the integration branch, or, with `hosting.platform = "none"`, its task branch did.
- The user asks to clean up worktrees or branches of merged work.

## Do Not Use When
- The pull request is open, closed without merging, or awaiting review, or the task branch has not merged → leave the worktree in place.
- The worktree or branch was not created for a task you can identify → stop and ask the user.

## Inputs
- The task branch, the pull request number (with a hosting platform), and the worktree path when the unit has one.
- `policy.integration_branch`, `policy.work_root`, `project.name`, `hosting.platform`, and `commands.worktree_teardown` from the profile.

## Steps
1. From the main checkout, run `git fetch origin --prune` and confirm the merge. With `hosting.platform = "github"`, `gh pr view <number> --json state,mergedAt` shows `MERGED`. With `"none"`, the unit merged through its merge commit («Scaling The Order» in [request-lifecycle.md](../../wiki/operating-model/request-lifecycle.md)): `git rev-list --ancestry-path --merges --first-parent <branch>..origin/<integration_branch> | tail -n 1` prints the first merge on the integration branch that contains the task branch, and it is the unit's merge commit only when its second parent is the task branch's tip (`git rev-parse <merge commit>^2` equals `git rev-parse <branch>`). When it prints nothing, the parents differ, or the repository has no `origin`, stop and ask the user whether and where the unit merged: a fast-forward, a squash merge, or a merge made only in a local branch leaves no such commit although the work may be in. Read the work folders from that commit's body per «Work Folders» in [git-workflow.md](../../wiki/workflows/git-workflow.md): the lines starting with `Work-Folder: ` in `git log -1 --format=%B <merge commit>`.
2. Find the unit's worktree by its state, not by `policy.worktrees`: the unit has one when `git worktree list --porcelain` shows the line `branch refs/heads/<branch>` in a linked worktree's entry (any entry after the first, which is the main checkout), and that entry's `worktree` line is its path. Why: parallel units and agent hosts create worktrees even while `policy.worktrees` is off. Then check every condition in «Cleanup» in [git-workflow.md](../../wiki/workflows/git-workflow.md):
   - `git log --oneline origin/<integration_branch>..<branch>` prints nothing. After a squash or rebase merge it may print commits; then compare the pull request's final diff, or without a platform the task branch's changes, with the integration branch, and stop and ask if they differ.
   - `git -c core.longpaths=true -C <worktree> status --short` prints nothing; for a unit without a worktree, `git status --short` in the main checkout. Why the flag: when `core.longpaths` is not on for the worktree, Git for Windows cannot open a path longer than 260 characters in it and lists a tracked file under that path as deleted (` D`), so the check fails on files that are still in place.
   - For a unit with a worktree, `git worktree list --porcelain` has no `worktree` line whose path starts with `<worktree>/`, the path above followed by a slash so that a sibling such as `<worktree>-2` does not match. Why: `git worktree remove` does not count ignored files as changes, so it deletes a worktree inside an ignored folder such as `.worktrees/`, with its unsaved files, while the status check above prints nothing.
   - `git -C <main checkout> branch --show-current` prints `<integration_branch>`, or `<branch>` for a unit without a worktree. Why: step 7 switches the main checkout to the integration branch, which would take it away from whatever else is checked out there, such as another unit working in place, and carry that unit's uncommitted changes along.
   - With `hosting.platform = "github"`, `gh pr list --base <branch> --state open` prints nothing.
3. If any condition fails, stop and report which one; never force-remove. When worktrees lie inside the worktree, report their paths; clean each one up first with this skill once its pull request merged (an entry marked `prunable` whose folder no longer exists needs only `git worktree prune`; `prunable` alone does not prove that, since an entry that lost only its `.git` file keeps its folder and files, so ask the user about that one), otherwise ask the user. For a unit without a worktree, skip steps 4 to 6 and continue at step 7.
4. Make sure nothing is using the worktree: run every command from the main checkout (move your own shell there first; only step 5 enters the worktree, for its one command), and ask the user to close terminals or editor windows opened in it. A process whose current directory is inside the worktree blocks deleting it, notably on Windows.
5. When `commands.worktree_teardown` is set, run it with the worktree as its working directory and return to the main checkout right after: in a POSIX shell `(cd <worktree> && <command>)`, in PowerShell `$ok = $false; Push-Location <worktree> -ErrorAction Stop; try { $global:LASTEXITCODE = 0; <command>; $ok = $? -and $global:LASTEXITCODE -eq 0 } finally { Pop-Location }; if (-not $ok) { throw 'worktree_teardown failed' }`. It resets `$global:LASTEXITCODE` and checks it together with `$?`, for the reasons in «Pitfalls» in the [shell pack](../../stacks/languages/shell.md); the `throw` stops the same call, since the next call may run in a new shell. If it fails, stop and report its output; never continue to `git worktree remove`. On Windows, links or junctions that `commands.worktree_setup` made can stop the removal halfway and leave the folder behind.
6. Remove the worktree: `git -c core.longpaths=true worktree remove <worktree>`, then `git worktree prune`. Why: Git for Windows reaches a path longer than 260 characters only when `core.longpaths` is on for the command that touches it, and a `core.longpaths` set only in the removed worktree's own configuration is not read by a command run from the main checkout. Without the flag, the removal either refuses with `contains modified or untracked files, use --force to delete it` (never answer that with `--force`; step 3 forbids it) or fails with `Filename too long`, unregisters the worktree anyway, and leaves the folder behind where a later cleanup cannot find it through `git worktree list`. Git on other platforms has no such setting and ignores the key. If it reports `Permission denied` after `git worktree list` no longer shows the worktree, Git already removed its files and only the empty directory is held by a process: once that process has left, delete the empty directory (`rmdir <worktree>`).
7. Update the main checkout before deleting the branch: `git switch <integration_branch>` and `git pull --ff-only`. `git branch -d` checks the branch against the checked-out branch, so it refuses a just-merged branch while the local integration branch is behind; for a unit without a worktree, this step also switches the main checkout off the task branch, which cannot be deleted while checked out.
8. Delete the branch: `git branch -d <branch>` (use `-D` only after step 2 proved a squash merge), and `git push origin --delete <branch>` only when the remote branch still exists (with head-branch deletion on, the platform already removed it).
9. Delete the unit's work folders, with `<unit>` as «Work Folders» in git-workflow.md defines it: each work folder whose last path segment is `<unit>` among those the pull request body names (`gh pr view <number> --json body`), or, with `hosting.platform = "none"`, among those step 1 read from the unit's merge commit. Skip a path that does not exist, and delete each other one by the rules in «Work Folders», which also say when to stop and ask. When the root from `policy.work_root`, read as «Work Folders» describes (an `env:NAME` value from that variable on this machine, then a leading `~` expanded to the home folder), is an absolute path, `project.name` is set, and `<work_root>/<project.name>/<unit>` exists but is not among those folders, report it instead of deleting it: another unit with the same `<unit>` may own it. An empty or relative root skips this check. Delete nothing else outside the worktree; report instead any other folder the pull request body or merge commit names, or the unit made outside its checkout.
10. Confirm with `git worktree list` and `git branch -a --list "*<branch>*"`.

## Output
- The removed worktree path, deleted work folders, the folders reported instead of deleted (step 9), and deleted branches, or the condition that stopped the cleanup.
