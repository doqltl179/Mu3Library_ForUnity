# Unity Verification

The kit's [verification.md](../../kit/core/wiki/workflows/verification.md) owns what verification is and how evidence is reported; this page records this repository's commands and the Unity-specific checks.

## When

- verifying a change to a package, a development project, or the compile tooling.

## Route Away When

- package rules being verified: [package-architecture.md](rules/package-architecture.md),
- changing the compile tooling itself: [tools/README.md](../../../tools/README.md).

## Compile

- `commands.build` compiles with the Unity Editor CLI the development projects that consume a changed package, from staged, unstaged, and untracked files: a Base change selects `built-in`, `urp`, and `watermelon`, a URP change `urp` and `watermelon`, a Watermelon Game change `watermelon`. Package Markdown, licenses, `Documentation~`, and repository tooling select no target.
- Explicit targets: `bash ./compile-unity.sh built-in|urp|watermelon|all`; targets map to projects in `unity-cli-packages.tsv`. `bash ./compile-unity.sh changed --base origin/develop` adds the changes committed since that ref to the selection; `--base` works only with `changed`, and the script refuses it with an explicit target. `--dry-run` prints the selection and where each target would run, without Unity.
- `mu3-cli unity compile` wraps the same script; `mu3-cli unity doctor` diagnoses bash, Editor installs, sample links, project locks, and log readiness.
- The script compiles in place when the project is closed and in a temporary source-only mirror when an Editor holds the lock, so an open Editor, the packages, and the repository `Library/` stay untouched. A `Temp/UnityLockfile` that no process holds, left by a crashed Editor, is reported as stale and does not count as open.
- The script prints Unity's log and keeps it in `log/unity-compile/<target>.log`. When that log has not grown for `--stall-timeout` seconds, 300 by default, it stops Unity and fails the target, so a compile waiting on something batch mode never answers cannot hold `commands.build`; the stalled target ends the run like any failed compile, and `--stall-timeout 0` waits as long as Unity runs. The default is about 12 times the longest silence of a measured first import (25 s, while Unity compiled the scripts); [tools/README.md](../../../tools/README.md#unity-compile-entrypoint) records the runs.
- A development project compiles its package's samples only through a Git-ignored link from `Assets/` to `Samples~`. The script stops before Unity when a selected project lacks it; `commands.worktree_setup` creates the links in a fresh clone or worktree. `--without-samples` runs without them and says so; a report must then state that the samples were not compiled.
- Never substitute `dotnet build` on the generated `.csproj` files: Unity compiles from the `.asmdef` files and the package sources, and the generated projects drift from both.
- On Windows the script runs through Git Bash.
- Open one development project in an Editor at a time. The three projects share the packages through `file:` references, so a newer Editor that rewrites a shared `.meta` while it imports breaks another project's import of the same file with `Import Error Code:(4)`.

## Lowest Supported Editor

- The packages declare their floor in the `unity` field of `package.json` (`6000.3`), and no development project runs that Editor. `--editor-version <version>` on either script runs the targets with that installed Editor in an isolated mirror retargeted to it, with the Unity package versions it bundles; [tools/README.md](../../../tools/README.md#lowest-supported-editor) describes the retargeting.
- Never open a development project in an older Editor in place: the downgrade rewrites its tracked settings. The scripts refuse `--in-place` with `--editor-version`.
- The [DI stripping harness](#di-stripping-harness) takes the same `--editor-version` and builds its player with that Editor in a mirror retargeted by the same rule.

## By Change Type

| Change | Also show |
|---|---|
| Runtime code | The affected assemblies compile; null safety and define guards on the changed paths |
| Editor code | The editor assembly compiles; no runtime assembly depends on editor code |
| DI or core lifecycle | Initialization and injection order unchanged for the samples that depend on it; `commands.test_playmode` passes, `urp` included, since only that target runs the coroutine path |
| DI reflection path (how `ContainerScope` or `InjectableMembers` finds constructors and `[Inject]` members) or Base's link.xml processor (`DILinkerProcessor`) | The [DI stripping harness](#di-stripping-harness) passes at Medium and High |
| Optional integration | The code sits entirely inside its define symbol, and every development project that includes the file compiles, since their define sets differ |
| Editor-version branch, version-sensitive API, package dependency, or the `unity` floor | The affected targets also compile with `--editor-version` set to an installed release of the floor |
| Compile-only request | Compile only; do not add or run tests |

- Base's samples compile only in `UnityProject_BuiltIn`, which resolves every optional package, so an unguarded optional-package reference in a Base sample compiles there. Prove a sample's guards by compiling a temporary mirror of that project with the optional packages removed from its manifest, and read the assembly's defines from its `Library/Bee` response file. A reading-only audit of the Template sample missed six unguarded files.

## DI Stripping Harness

- Do not offer passing tests as evidence that injection survives managed code stripping; only the harness's player is that evidence.
- Run it when a change touches how the container reaches constructors or `[Inject]` members by reflection, or `DILinkerProcessor`: `PYTHONPATH=tools/cli/src python -m mu3_cli unity di-strip-harness --stripping Medium`, then `--stripping High`. Add `--with-unitask` when the change touches core preparation, and `--backend il2cpp` when it touches generics or reflection that IL2CPP compiles ahead of time.
- When the change can behave differently on the lowest supported Editor, such as code behind a `UNITY_6000_x_OR_NEWER` branch, also run Medium and High with `--editor-version` set to an installed release of the [floor](#lowest-supported-editor).
- [tools/README.md](../../../tools/README.md#di-stripping-harness) owns why only a player shows stripping, what the harness builds and where, its checks and how many there are, its options, the Editor modules and toolchain each backend needs, how `--editor-version` retargets the mirror, which work folders it accepts, why `--work-dir` must stay short, and what each exit code means.
- Exit 3 is no result, neither a pass nor a DI regression: fix the cause the run reports, which can be the change under test, and run again.
- Pass a short `--work-dir` from a deep worktree.
- When a run warns that the explicit `UNITY_EDITOR` override will be used, report the Editor that built it, not the one requested.
- Player builds are memory-heavy: run one at a time. [tools/README.md](../../../tools/README.md#measured-runs) owns the measured runs: how long a run took on a new or an imported mirror and under what load, the sizes it built, and which combinations passed on which date.
- Report the backend, the stripping level, whether UniTask was in, the Editor version, the exit code, and the passed and failed check counts.

## Tests

- EditMode tests live in `Mu3Library_Base/Tests/Editor` (`Mu3Library.Tests.Editor.asmdef`), `Mu3Library_URP/Tests/Editor` (`Mu3Library.URP.Tests.Editor.asmdef`), and `Mu3Library_Game_WatermelonGame/Tests/Editor`. Add new ones next to the nearest existing pattern.
- PlayMode tests live in `Mu3Library_Base/Tests/Runtime` (`Mu3Library.Tests.Runtime.asmdef`) and cover what only the player loop shows: a core's preparation when its component or object is turned off or destroyed, the `CoreRoot` accessor once the application quits, and the Multiplayer Debugger's lookup of a manager registered under `CoreRoot` (`MultiplayerDebuggerLookupTests`). A test belongs there only when edit mode cannot observe the behavior. The assembly also holds the components that EditMode tests save into a prefab, such as `ObservablePrefabTestComponent`, since a prefab keeps a component only through its own script and `AddComponent` refuses a script from an editor assembly; `Mu3Library.Tests.Editor` references it for them.
- `MultiplayerSteamIntegrationTests` run the Steam backend against the Steam client on the machine, on Steam's test app 480, only when the environment variable `MU3LIBRARY_STEAM_TESTS=1` reaches Unity (for example `MU3LIBRARY_STEAM_TESTS=1 bash ./test-unity.sh built-in`) and a signed-in Steam client runs; otherwise they report as ignored. Two players on two accounts remain a manual check (section 13 of `docs/specs/steam-player-hosted-multiplayer.md`).
- `MultiplayerLocalMachineTests` run the machine-wide local network over real loopback sockets and a temporary folder, so they wait in real time, 40 to 50 seconds per run without the three `[Explicit]` cases below; a `--filter` that names the whole fixture runs those too, which adds about 45 seconds (checked on `develop` at 2b35e375 on 2026-11-08 with no other Unity process running). The range is wide so that a test added to the fixture leaves it true: re-measure only when a run with no other Unity process falls outside it. The test that proves the listener refuses every address but loopback reports as ignored on a machine with no other network address. Separate processes are not part of the run: the pull request that adds such behavior records how it was checked across processes. Three cases there are `[Explicit]` and only log, in a line that starts with `[Lobby file]`: `LobbyFileWrite_Allocations_AreMeasured`, what one rewrite of the lobby file allocates; `LobbyFile_MainThreadWaits_AreMeasured`, about 40 seconds, how long the main thread takes where it may wait for a rewrite; and `LobbyFile_SearchesMeetingAReplacement_AreMeasured`, about 2 seconds, how long the updates of a search from another process take on the main thread, and how many updates it takes to answer, with the owner's lobby file in place, in the middle of a replacement, and left by a process that ended in one; run all three with `--filter Mu3Library.Tests.MultiplayerLocalMachineTests.LobbyFile`. Timings depend on the load, so note how many other Unity processes ran.
- A Multiplayer Play Mode virtual player is checked against the machine-wide local network by hand. By the user's decision on #188 the development projects do not keep `com.unity.multiplayer.playmode`: add it, at the version the Editor bundles (3.0.0 in Unity 6000.6.7f1), to a temporary copy of `UnityProject_BuiltIn` and the packages it references, for example under the Git-ignored `log/`, never to a tracked project. Turn on **Use Local Backend** in the Multiplayer sample, since the main Editor and a virtual player are one Steam account, which the host refuses with `DuplicateAccount`, then turn on Player 2 in **Window > Multiplayer > Multiplayer Play Mode** and enter play mode. Check the kick and the host's leave in separate play mode sessions: a kicked player cannot rejoin the session (`Banned`), and a lobby in a game leaves search and refuses joins (`GameInProgress`), so confirm the kick, then enter play mode again and let the host **Leave**, which ends the virtual player's session with `HostLeft`. No public API turns a virtual player on; a run without clicks calls the internal `MultiplayerPlaymode.PlayerTwo.Activate` through reflection, which another package version can break. The [#188 verification comment](https://github.com/doqltl179/Mu3Library_ForUnity/issues/188#issuecomment-6550684236) records that API and the 2026-11-01 run, on Unity 6000.6.7f1 with Player 2 only and without `-batchmode`.
- `MultiplayerPerformanceTests` measure NFR-1 and NFR-2 under the full 16-player load on both local networks. The in-process cases run on a test clock in about a second each and run with every `commands.test`; the machine-wide cases run about 36 seconds of real time each and are `[Explicit]`, so `commands.test` reports them as skipped. Run all four with `bash ./test-unity.sh built-in --filter Mu3Library.Tests.MultiplayerPerformanceTests`, about 75 seconds of tests after the project loads. Each case asserts that the steady state allocates nothing and that no message reaches its handler later than the frame after the one it was sent in (one frame more on the machine-wide network, for the loopback), and logs the host's timing in lines that start with `[NFR-1]`. The cases whose clients send to the host, the load NFR-1 holds to its target, also assert that the host's average stays within 0.5 ms, so a machine slower than the measurement PC can fail them; the cases whose host relays every message to the other clients only log their timing, as a reference.
- Under CPU load, a host frame in the machine-wide cases can take tens of milliseconds. With 16 processes that each spin a core on the measurement PC, the 19 host frames over 2 ms of one run took 106.1 ms in all, of which the main thread ran 10.5 ms, about a tenth, and waited for the send lock 0.06 ms (#288). That Windows gave the main thread's core to another thread of the same priority meanwhile is an inference, not a measurement: under the same load the send path from before the sending thread (#251), with no such thread or lock, had such frames too, more of them, and so did the in-process cases, which use no sockets. Their number and maximum varied widely between runs of the same code. So read the maximum and the frames over 2 ms only with the load noted, other Unity processes included, which the test summary counts under each run, and compare two versions under the same fixed load over several runs: `bash ./test-unity.sh built-in --filter <pattern> --load-spinners 16 --repeat <n>` spins 16 Python processes, one core each, from the first test of each run to its last, so that they slow neither the compile before nor Unity's shutdown after, starts Unity anew for each run, and totals the runs. [tools/README.md](../../../tools/README.md#fixed-load-and-repeated-runs) owns how the load starts and stops, what the summary and each run's `.load` record give, and why the runs do not repeat inside one Unity.
- `commands.test` runs the EditMode tests through the Unity Test Framework CLI for the projects that consume a changed package, selected as `commands.build` selects them, and `commands.test_playmode` runs the PlayMode tests for the same selection. Explicit targets: `bash ./test-unity.sh built-in|urp|watermelon|all`, with the compile script's options, `--platform editmode|playmode`, and `--filter <pattern>`, which runs only the tests whose full name matches it through Unity's `-testFilter`, `[Explicit]` ones included; `mu3-cli unity test` wraps it.
- A project runs only the packages its `Packages/manifest.json` lists under `testables`: `built-in` runs the Base tests, `urp` the Base and URP tests, and `watermelon` the Base and Watermelon Game tests. Base tests therefore run under three define sets, and `urp` is the only one without UniTask, so only its runs reach the coroutine paths that stand in for UniTask, such as `CoreBase`'s preparation.
- The command exits non-zero when a test fails, Unity fails, or a run writes no result. It also stops Unity and fails the target when Unity's log has not grown for `--stall-timeout` seconds, 600 by default, naming the test that began and did not end, so a test that never returns cannot hold the run; NUnit `[Timeout]` cannot do this, since the Unity Test Framework checks it only after a test method returns. Such a failure does not stop the remaining targets; a target that cannot start, such as an open project under `--in-place`, stops the command at once. NUnit XML lands in `log/unity-tests/<target>-<platform>.xml`, and Unity's log, with a `##utp:` line as each test begins and ends, beside it as `<target>-<platform>.log`. A project open in an Editor is tested in an isolated mirror, as in compile.
- Tests take minutes per target on a first import; when a request does not need them, report that they did not run.

## Report

- The compile targets run, the Editor version, Unity's exit status, and the error and warning counts from its log.
- For tests, the targets run and each target's total, passed, failed, skipped, and inconclusive counts from the summary. An inconclusive test reached no verdict and fails its target ([tools/README.md](../../../tools/README.md#unity-test-entrypoint) says why): name each one the summary lists, and do not report the behavior it covers as verified until a run gives it a verdict.
- Compile and test runs take minutes per target, so report the targets actually run rather than all targets.
- When a run warns about the Windows path limit, quote each warning with its target and name what the files Unity could not read can break: editor windows and UI Toolkit screens (`.uxml`, `.uss`), the Device Simulator (`.device`), Shader Graph and other shader assets, and code that loads a DLL the warning names. A passing compile or test run does not verify those features; check them only from a shorter path ([tools/README.md](../../../tools/README.md#fresh-clone-setup) owns the limit and its measurements).
