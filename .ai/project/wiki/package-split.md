# Package Split

How a feature leaves Base for a package of its own under [ADR 0001](../../../docs/adr/0001-package-split-and-repository-restructure.md), as unit 7 (#533) split Notifications into `packages/notifications`. Units 8 to 12 follow it and read their own decisions in the ADR first: the D7 table (package IDs, assemblies, namespaces, and the three new assemblies), the D5 exceptions, the D12 config table, D8 and D9 (di and the editor tools), D11 (tests), and D19 and D22 (steam).

## When

- moving a feature of Base into a package of its own.

## Route Away When

- surfaces, assembly direction, gates, and the `package.json` dependency rules: [package-architecture.md](rules/package-architecture.md),
- the first release, its tag, its install URL, and its dependency versions: [package-release.md](package-release.md),
- compiling and testing the split: [unity-verification.md](unity-verification.md),
- encoding and line endings of the new files: «File Encoding» in [overview.md](overview.md).

## New Package Files

- `packages/<name>/` takes the package ID, display name, assemblies, and namespaces of the D7 table. `Runtime/` holds the feature directly, without a `Scripts/` level (D20); `Editor/` and `Tests/` exist only when the package has editor code (D9) or tests (D11).
- `package.json` takes Base's form and fields: four-space indent and no BOM (Git stores LF; the working tree follows `core.autocrlf`), Base's `unity`, `license`, `author`, and `changelogUrl`, a `documentationUrl` at the package's own README on `main`, and `version` `0.1.0`, which stays until the first release.
- `README.md`, `CHANGELOG.md` (the header of the other package changelogs and an empty `## [Unreleased]`), and `LICENSE.md` (a copy of Base's) follow «File Encoding» in overview.md.
- Each new file at the package root has a `.meta` in the form of URP's, `PackageManifestImporter` for `package.json` and `TextScriptImporter` for the Markdown files, each new `.asmdef` an `AssemblyDefinitionImporter` `.meta`, a new script such as the runtime's `AssemblyInfo.cs` a script `.meta`, and each new folder, such as `Editor/` or `Tests/Editor/`, a folder `.meta`, each with a new GUID of 32 lowercase hex characters that `git grep` finds nowhere else.
- Write every new file before the next Unity run of a config that installs the package: Unity deletes a `.meta` whose file is missing and later gives that file a new GUID, as it did on 2026-11-16 to the README and CHANGELOG of the Input System package.

## Dependencies

- Declare the Unity-registry SDK the code uses at the version the `unity` floor bundles, per «Assemblies And Optional Integrations» in package-architecture.md, never at the newer version a config pins. Read it from the retarget lines that `compile-unity.sh <config> --editor-version <installed 6000.3 release>` prints, `<package> <config version> -> <floor version>`; for an SDK the config brings in only through another package, such as Addressables through Localization, read `packages.<name>.version` in that Editor's `Data/Resources/PackageManager/Editor/manifest.json`, the file the retarget reads (`editor_bundled_versions` in `tools/cli/src/common/editor.py`), not the run's `[Package Manager] Registered` list, which can show a higher version another package asked for. Name the 6000.3 release it came from in the commit body: Mobile Notifications 2.4.3 came from 6000.3.10f1.
- Declare such an indirect SDK too when the package's own code references one of its assemblies, since the code then uses it outside a gate: `Mu3Library.Localization` waits on `AsyncOperationHandle` from `Unity.ResourceManager`, so the Localization package declares Addressables 2.9.0 beside Localization 1.5.8, both read on 6000.3.10f1. Without such a reference, the wrapped SDK's own dependency brings it in, and the package does not declare it.
- A new dependency makes that lower-bound compile required («Lowest Supported Editor» in [tools/README.md](../../../tools/README.md#lowest-supported-editor)), besides the compile on the configs' own Editor. After it, check in the generated project's `Packages/packages-lock.json` or in its log that the declared version is the one that resolved: on 2026-11-15 a project that pinned Mobile Notifications 2.4.3 directly still resolved 2.5.0 while the package declared 2.5.0. The Editor manifest's `minimumVersion` also raises a lower request: Localization 1.5.8 asks for Addressables 1.25.0, and 6000.3.10f1 resolved 2.9.0.
- Name a Mu3Library package only when the code references one of its assemblies: a Git URL install does not resolve that dependency, so the README then tells the user to install it first. A split package that references Base names the Base release that removes the moved code, the next Base version after 0.28.0 (0.29.0, the minor bump that a breaking change gets before 1.0.0 in the kit's release.md), never 0.28.0 or earlier, which still holds the moved code, so the same types would sit in two assemblies. While that Base is unreleased, name the planned version; the first release confirms it. A config's `"checkout"` Base still resolves from its folder, whose `package.json` says 0.28.0, as the Input System package's compiles showed on 6000.6.7f1 and 6000.3.10f1.

## Moving The Code

- `git mv` the feature with every `.meta` file; a feature folder that becomes `Runtime/` itself takes its `.meta` along as `Runtime.meta`, with its GUID. What the assembly keeps follows D5 and D7:
  - notifications and di: the `.asmdef` moves with its GUID, assembly name, and namespace, so code and assembly references by name or GUID keep working;
  - steam: the `.asmdef` keeps its GUID, but its assembly and namespace become `Mu3Library.Steam.Multiplayer` (D19), so a reference by name and each `using` change;
  - addressables, localization, and inputsystem: `Addressable/`, `Localization/`, and `IS/` have no `.asmdef` today and compile into `Mu3Library`, so each package gets a new assembly (`Mu3Library.Addressables`, `Mu3Library.Localization`, `Mu3Library.InputSystem`) with a new GUID, and the namespaces (`Mu3Library.Addressable`, `Mu3Library.Localization`, `Mu3Library.IS`) stay; an assembly definition that references `Mu3Library` for them adds the new one. The new runtime assembly takes Base's platform and `autoReferenced` settings, so code without an assembly definition of its own keeps reaching it (D5).
- Editor tools (D9) go to `Editor/` in a new assembly `Mu3Library.<Name>.Editor` for the Editor platform, which references `Mu3Library.Editor` for `Mu3WindowDrawer` and the `Editor/FileUtil` helpers, and tests (D11) to `Tests/Editor/` in a new `Mu3Library.<Name>.Tests.Editor` in the form of Base's test assembly. Each moved file keeps its GUID and its namespace (D5): a drawer stays in `Mu3Library.Editor.Window.Drawer`, so a drawer asset made from it keeps its script, and a test in `Mu3Library.Tests`, so its full name stays. Give each new assembly the `rootNamespace` of the namespace its code keeps in the D7 table (`Mu3Library.IS`, `Mu3Library.Addressable`, `Mu3Library.Localization`, and `Mu3Library.Editor` or `Mu3Library.Tests` for moved drawers and tests), not its assembly name: a namespace `Mu3Library.InputSystem` or `Mu3Library.Addressables` would hide the SDK's static class `InputSystem` or `Addressables` inside `Mu3Library`.
- Find what the moved code used that its new assembly cannot reach. A moved test that read internals through `InternalsVisibleTo("Mu3Library.Tests.Editor")` gets an `InternalsVisibleTo` from the new runtime assembly to the package's own test assembly (D11). An `internal` member of a Base assembly is opened in Base as public or protected API (D22), never through an `InternalsVisibleTo` to another package: the Input System split made `Mu3WindowDrawer.GetNamespaceWarning` `protected internal`, which the Addressables and Localization exporters also call, and the Localization split made `FileCreator.WrapInDefineSymbol` `public`, since a member of a static class cannot be `protected`, which the Addressables exporter also calls. The Input System and Localization runtimes and tests needed no internals. The Addressables tests read the manager's own internals, so `Mu3Library.Addressables` opens them to `Mu3Library.Addressables.Tests.Editor`, and Base's `Runtime/AssemblyInfo.cs` dropped its `InternalsVisibleTo("Mu3Library.Tests.Editor")` with its comment, since only those tests used it: drop such an entry once no test left in Base needs it, and let the compile of every config that installs Base prove that none does.
- A Base tool that still reads the moved code, such as the Addressables cache section of Base's `RuntimeDiagnosticsDrawer` until unit 11 moves the drawer to di (D9), references the new runtime assembly by name and compiles that code behind a `versionDefines` symbol for the new package, not for the SDK: `Mu3Library.Editor` lists `Mu3Library.Addressables` and defines `MU3LIBRARY_ADDRESSABLES_PACKAGE` from `com.github.doqltl179.mu3library.addressables`, so the section compiles wherever the manager exists. Unity skips a reference by name that resolves to no assembly, so a config without the package compiles Base without it, and the assemblies stay acyclic, since the package's runtime assembly references only Base's runtime assemblies, and only its editor assembly references `Mu3Library.Editor`. Name the symbol after the package (`_PACKAGE`), since Base can keep the SDK's `_SUPPORT` symbol for a D1 extension, add its row to the gate table in package-architecture.md, and check in the `Library/ScriptAssemblies` of `full` that `Mu3Library.Editor.dll` holds the gated code, and in another config that it does not.
- Drop the SDK's gate from the moved code: its `defineConstraints` entry, its `versionDefines` entry, and each `#if` on its symbol (D21). Keep the UniTask and Steamworks.NET gates, which guard Git-distributed SDKs, and the `includePlatforms`: a new assembly whose files keep `#if MU3LIBRARY_UNITASK_SUPPORT`, such as the Localization runtime and tests, references `UniTask` and declares the `com.cysharp.unitask` entry in its own `versionDefines`, since a symbol is defined only in the assembly that declares it.
- Remove from Base what only the feature used, such as the SDK reference and `versionDefines` entry of `Mu3Library.Editor.asmdef` that only the Input System exporter needed. Check the runtime, editor, and test assemblies one by one: `Mu3Library.asmdef` references its SDKs by GUID, so find the SDK's entry by the GUID in its `.asmdef.meta`, as `GUID:eec0964c48f6f4e40bc3ec2257ccf8c5` is `Unity.Localization`. An assembly keeps the `versionDefines` entry that code left in it still reads and drops the SDK references that only the moved code used: the Addressables split dropped `Unity.Addressables` and `Unity.Addressables.Editor` from `Mu3Library.Editor`, whose gated diagnostics read only `AddressablesManager`, and `Unity.Addressables` and `Unity.ResourceManager` from `Mu3Library.Tests.Editor`, which keeps its entry for `SceneLoaderAddressablesTests`, a test that calls only `SceneLoader`. Delete the symbol's row from the gate table in package-architecture.md only once no package uses the symbol, as the Localization split did for `MU3LIBRARY_LOCALIZATION_SUPPORT`: `MU3LIBRARY_ADDRESSABLES_SUPPORT` stays for Base's `Scene/*SceneLoader.Addressables*.cs`, the `#if` blocks of `SceneLoader.cs`, and `SceneLoaderAddressablesTests`, and `MU3LIBRARY_INPUTSYSTEM_SUPPORT` for Base's `UI/MVP/MVPManager.cs` and Watermelon Game's `Helpers/InputHandler*.cs`, the extensions that D1 keeps.

## Configs, Tools, And Profile

- Name the package as `"checkout"` in the manifest of each config that the D12 table lists for it, which is not every config that installs its SDK: `urp` and `watermelon` install the Input System without the inputsystem package, and di also goes into `minimal`. List it under `testables` only when it has tests; each config that gets the package then keeps its test count, and a config that ran the moved tests under Base without getting the package stops running them, as `urp` and `watermelon` stopped running the 6 `InputSystemManagerTests`. Check with `compile-unity.sh changed --dry-run` that a file changed under the package folder alone selects those configs.
- Update the configs' package sets in `tools/cli/tests/test_unity_projects.py`, the package count and list in `tools/cli/tests/test_repository.py`, and the config table and selection examples in [tools/README.md](../../../tools/README.md#unity-project-configs). A package with tests also changes the test locations and each config's `testables` sentence in «Tests» in unity-verification.md, and the `testables` sentence of «Unity Test Entrypoint» in tools/README.md.
- In the profile, add a `[[release.packages]]` entry with the tag pattern `<name>/v{version}`, name the package in `project.summary`, and bind the moved paths: code the split left without a gate goes to its runtime or tools owner, and gated split files stay with `optional-integration-engineer` through its globs.
- Add the package to «Package Model» and «Commit Scopes» in overview.md, the compile selection in unity-verification.md, the release table in package-release.md, and the package names in the [glossary](glossary.md); its area label follows «Commit Scopes» in overview.md. A name that «Commit Scopes» listed as a surface, as it did `localization`, moves to its packages.

## Docs Until The First Release

- Move the feature's documentation from Base's README and the root README into the package README, and leave a pointer to it in each. A section of its own under «Core Modules» in the root READMEs, as «Addressables» was, keeps its heading with the pointer in place of its text. While Base keeps the SDK's gate for a D1 extension, the SDK's row stays in «Optional Packages», its feature cell names what Base keeps, and a sentence under the table points to the package and names the extension, as Input System and Addressables did. Once Base keeps no gate for the SDK, it also leaves the optional-integration lists: the root README's feature list and «Optional Packages» table and their copies, Base's README, the `description` in Base's `package.json`, and the glossary, as Mobile Notifications and Localization did.
- Under Unreleased in the root CHANGELOG and its copies: a Base entry saying that the feature moved, that a project using it installs the new package from its first release, and what D5 says stays or changes for that feature, such as an assembly reference to add (D7) or a renamed assembly and namespace (D19); and an entry for the new package. The package-local CHANGELOG gets its first version entry at the release.
- List the package in the root README and its copies, in the local-disk install list and the package list at the end, and say that it ships with the next release: no install URL names a tag that does not exist yet. «Install URLs» in package-release.md covers adding the URL.
- Add a dated entry to `docs/repository/CHANGELOG.md` for the config change.
