# Steam 플레이어 호스트 멀티플레이 유틸리티 요구사항

- 작성일: 2026-10-31
- 승인일: 2026-10-31 (11장의 결정 사항 확정)
- 대상 패키지: Mu3Library Base의 새 어셈블리 (결정 D2)
- 관련 이슈: [#162](https://github.com/doqltl179/Mu3Library_ForUnity/issues/162)

## 1. 문제

Mu3Library로 Steam 멀티플레이 게임을 만들려는 개발자는 세션 모집, 참가, 연결, 메시지 교환을 모두 직접 구현해야 한다. 현재 패키지에는 네트워크 세션 기능이 없다 (`Mu3Library_Base/Runtime/Scripts`에 로비, 세션, 소켓 관련 코드 없음, 2026-10-31 확인).

소규모 협동 게임이나 파티 게임은 플레이어 한 명의 PC가 호스트를 맡고 친구가 초대나 친구 목록으로 들어오는 방식으로 충분하다. 이 방식에서는 개발자가 서버를 운영하거나 비용을 낼 필요가 없다. 그러나 Steam 로비, 초대, P2P 연결, 호스트 이탈 처리, 정원 관리 같은 작업은 게임마다 똑같이 반복된다.

대규모 게임의 외부 서버 구성은 게임마다 방식이 크게 달라 공통 기능으로 만들기 어렵다. 반면 플레이어 호스트 방식은 Steam이 로비와 릴레이를 제공하므로 공통 유틸리티로 만들 수 있다.

근거: 요청자의 제품 방향 결정 (2026-10-31), 패키지 코드 확인.

## 2. 용어

| 용어 | 뜻 |
|---|---|
| 호스트 | 세션을 만들고 게임 상태의 권한을 가진 플레이어. 그 PC가 서버 역할을 함께 맡는다 (리슨 서버). |
| 클라이언트 | 호스트에 접속한 다른 플레이어. |
| 세션 | 호스트 한 명과 클라이언트들이 한 게임을 함께하는 단위. 로비 단계와 게임 단계를 포함한다. |
| 로비 | 게임 시작 전에 참가자를 모으는 단계, 또는 그 단계에서 쓰는 Steam 로비. |
| 슬롯 | 정원의 한 자리. Steam 계정 하나가 슬롯 하나를 차지한다. |
| 정원 | 호스트를 포함한 세션 최대 인원. |
| 백엔드 | 로비와 연결을 실제로 처리하는 구현. Steam 백엔드와 로컬 백엔드가 있다. |
| 외부 서버 | 게임 개발자가 운영하거나 비용을 내는 서버. Valve가 제공하는 Steam 로비와 릴레이는 외부 서버로 보지 않는다. |
| 사유 코드 | 실패나 종료의 원인을 나타내는 열거값 (부록 B). |

## 3. 사용자

| 사용자 | 해야 하는 일 |
|---|---|
| 게임 개발자 (주 사용자) | Mu3Library를 설치한 프로젝트에서 로비 생성, 검색, 초대, 참가 흐름과 게임 메시지 교환을 짧은 코드로 붙인다. Steam 없이 에디터에서 여러 인스턴스로 시험한다. |
| 게임 플레이어 | 친구를 초대하거나 친구 목록에서 참가한다. 실패하면 이유를 알 수 있고, 호스트가 나가면 메뉴로 안전하게 돌아간다. |
| 라이브러리 유지보수자 | Steam 계정 여러 개 없이도 세션 규칙을 자동 테스트로 검증한다. |

## 4. 범위

### 4.1 범위 안

- Steam 초기화와 사용자 정보 조회
- 로비 생성, 검색, 초대, 참가, 나가기, 참가자 목록, 준비 상태, 로비 데이터, 로비 채팅
- 인원 정책: 정원, 최소 시작 인원, 중도 합류, 재접속 슬롯 예약, 중복 계정, 강퇴
- 세션 수명주기: 게임 시작, 로드 완료 동기화, 로비 복귀, 호스트 이탈 처리
- 호스트 중심의 메시지 송수신 (신뢰, 비신뢰), 연결 품질 조회, 송신량 제한
- Steam 없이 같은 PC에서 시험하는 로컬 백엔드
- 샘플과 문서 (README, CHANGELOG, 현지화 사본)

### 4.2 범위 밖

| 항목 | 이유 |
|---|---|
| 전용 서버, 외부 서버 운영, 서버 브라우저 | 요청에서 제외. 서버 구성 방식이 게임마다 다르다. |
| 호스트 마이그레이션 | 게임 상태 전체를 다른 PC로 옮겨야 해서 게임마다 구현이 다르다. 호스트 이탈은 세션 종료로 처리한다 (FR-27). |
| 오브젝트와 변수 자동 동기화, 예측과 보정, 틱 동기화 | 네트코드 프레임워크의 영역이다. 라이브러리는 세션과 메시지 계층만 제공한다 (결정 D1). |
| 관전자 슬롯 | 정원 정책이 복잡해진다. 필요하면 게임이 메시지로 구현한다. |
| 실력 기반 매치메이킹, 랭크 | 외부 서버나 별도 점수 저장소가 필요하다. |
| 음성 채팅 | 독립된 기능이다. |
| Steam 외 플랫폼 (Epic, 콘솔, 모바일)과 크로스플레이 | Steam 출시가 기준이다. |
| 한 PC 여러 명 (분할 화면), Steam Remote Play Together | 로컬 입력 문제이며, Remote Play Together는 라이브러리 코드 없이 Steam이 제공한다. |
| 영구 차단 목록, 신고, 안티치트 | 저장소와 운영 정책이 필요하다. |
| 업적, 통계, 클라우드 저장 등 다른 Steamworks 기능 | 멀티플레이와 독립된 기능이다. |
| Steam 없이 하는 LAN 플레이 | 고려하지 않는다 (결정 D7). 모든 출시 플레이는 Steam 로비와 릴레이를 전제로 한다. 로컬 백엔드는 같은 PC 안의 개발과 테스트 전용이다. |

## 5. 기능 구성

```text
게임 코드
  │
  ├─ 세션 서비스 ──── 상태 흐름, 로비, 인원 정책, 시작과 종료
  ├─ 메시지 서비스 ── 메시지 종류 등록, 송신, 수신, 연결 품질
  ├─ Steam 플랫폼 서비스 ── 초기화, 사용자 정보, 아바타, 상태 표시 (Steam 백엔드에서만)
  │
  └─ 백엔드 (둘 중 하나를 선택, 게임 코드는 같다)
       ├─ Steam 백엔드: Steam 로비 + Steam P2P 연결 (Valve 릴레이 경유)
       │                Steamworks.NET을 설치한 프로젝트에서만 포함
       └─ 로컬 백엔드: 같은 PC의 인스턴스끼리 로비 공유 + 연결
                       항상 포함, 같은 PC 안의 개발과 테스트 전용
```

- 연결 구조는 호스트 중심 별형이다. 모든 클라이언트는 호스트 하나에만 연결되고, 클라이언트끼리 보내는 메시지도 호스트를 거친다. 클라이언트끼리 직접 연결하지 않으므로 NAT 문제와 신뢰 경계가 단순해진다.
- 호스트는 서버이면서 플레이어다. 호스트 자신의 플레이어 코드도 클라이언트와 같은 API로 호스트에 메시지를 보내며, 이 메시지는 네트워크를 거치지 않고 전달된다.
- 세션, 메시지, 로컬 백엔드는 Base 안의 새 어셈블리에 둔다. Steam 플랫폼 서비스와 Steam 백엔드는 Steamworks.NET이 설치된 프로젝트에서만 컴파일되는 별도 어셈블리에 둔다. Notifications 어셈블리와 같은 선택 연동 방식이다 (결정 D2, D3).
- Steamworks.NET을 설치하지 않은 프로젝트에서도 Base는 그대로 컴파일되고, 로컬 백엔드로 세션 기능을 쓸 수 있다 (NFR-7).

## 6. 인원 정책

| 항목 | 규칙 | 이유 |
|---|---|---|
| 세는 단위 | Steam 계정 1개 = 슬롯 1개. 호스트를 포함한다. | 플레이어가 화면에서 보는 "n/m명"과 같게 한다. |
| 정원 범위 | 1 이상, 라이브러리 상한 16 이하 (결정 D4). | Steam 로비는 250명까지 허용하지만, 리슨 서버에서는 호스트 PC가 게임 처리와 모든 송신을 맡는다. 클라이언트 15명에게 30Hz로 512B씩 보내면 호스트 상향 대역이 약 1.8Mbps (헤더 제외)이고, 32명이면 약 3.8Mbps로 늘어난다. 상한은 라이브러리가 성능을 검증하고 보장하는 범위다. |
| 기본 정원 | 4 | Steam 협동 게임에서 가장 흔한 규모다. |
| 정원 1 | 허용. 혼자 하는 플레이를 같은 코드 경로로 처리할 수 있다. 초대와 참가는 불가능하다. | 싱글과 멀티의 코드 분기를 줄인다. |
| 정원 집행 | Steam 로비 정원과 별도로, 호스트가 연결을 받을 때 다시 확인한다. | 거의 동시에 참가할 때 생기는 경쟁 상태에서도 정원을 넘지 않게 한다. |
| 정원 변경 | 로비 단계에서 호스트만 바꿀 수 있다. 새 값은 현재 인원 (예약 슬롯 포함) 이상, 상한 이하여야 한다. 게임 단계에서는 바꿀 수 없다. | 게임 중 정원 변경은 게임 규칙과 충돌하기 쉽다. |
| 최소 시작 인원 | 호스트가 정한다. 기본값 1. | 게임마다 다르다. |
| 준비 확인 | 켜져 있으면 호스트를 뺀 모든 참가자가 준비해야 시작할 수 있다. 기본값 켜짐. | 흔한 로비 흐름이다. |
| 중도 합류 | 거부 (기본) 또는 허용. 거부하면 게임 시작과 함께 세션이 검색과 참가에서 사라진다. | 대부분의 게임은 중도 합류 처리 코드가 없다 (결정 D5). |
| 재접속 슬롯 예약 | 게임 단계에서 비정상으로 끊긴 참가자의 슬롯을 정해진 시간 (기본 60초, 0이면 꺼짐) 동안 남겨 둔다. 그동안 그 슬롯은 정원에 포함되고 같은 계정만 돌아올 수 있다. | 일시적인 끊김으로 자리를 잃지 않게 한다. 2단계에서 구현한다 (결정 D6). |
| 중복 계정 | 같은 Steam 계정의 두 번째 연결은 거부한다. | 한 계정이 슬롯 두 개를 차지하지 못하게 한다. |
| 강퇴 | 호스트만 할 수 있다. 강퇴된 계정은 그 세션이 끝날 때까지 다시 들어올 수 없다. | 세션 단위 차단만 다룬다. 영구 차단은 범위 밖이다. |
| 관전자 | 없다. | 범위 밖 (4.2). |

## 7. 세션 상태 흐름

```text
           로비 생성                     성공
Offline ─────────────▶ Creating ───────────────▶ Lobby (호스트)
   │
   │       참가 요청                     로비 입장 + 호스트 연결 성공
   └─────────────────▶ Joining  ───────────────▶ Lobby (클라이언트)

Lobby ──호스트가 시작──▶ InGame ──호스트가 게임 종료──▶ Lobby
InGame (클라이언트) ──끊김, 예약 시간 안──▶ Reconnecting ──복귀──▶ InGame
                                         Reconnecting ──복귀 (그사이 게임 종료)──▶ Lobby

모든 상태 ──나가기, 강퇴, 호스트 이탈, 연결 실패──▶ Offline (사유 코드 포함)
```

상태 이름은 라이브러리의 `SessionState` 값과 같다. Reconnecting에서 복귀하면 그때의 세션 상태 (InGame 또는 Lobby)로 돌아간다.

> **결정 대기 (#200)**: 요구사항이 아니라 현재 구현의 동작이다. 현재 구현은 게임 단계에서 클라이언트의 호스트 연결이 비정상으로 끊기면 (재접속 예약이 켜져 있을 때) 바로 Offline이 되지 않고 Reconnecting을 거친다. 클라이언트는 자기 쪽 끊김과 호스트의 끊김을 구별할 수 없기 때문이다. 그 뒤 예약 시간이 지나거나, 로비가 호스트 이탈을 보여 주거나, 나가면 Offline이 된다. 그래서 호스트의 네트워크나 전원이 끊기고 로비가 그 사실을 보여 주지 않으면 FR-27의 종료 시간을 넘길 수 있다. 이 동작을 받아들일지는 #200에서 정한다.

## 8. 기능 요구사항

우선순위: [M] 1단계 필수, [S] 2단계, [C] 여유가 있을 때.

### 8.1 Steam 플랫폼

**FR-1 [M] Steam 초기화와 수명 관리**
라이브러리는 Steam이 이미 초기화되어 있으면 그 상태를 재사용하고, 그렇지 않으면 설정된 AppID로 초기화해야 한다. 라이브러리가 직접 초기화한 경우에만 종료 시 Steam을 종료해야 한다.

- Given Steam 클라이언트가 실행 중이 아님, When 초기화, Then 실패 이벤트가 사유 코드 `SteamNotRunning`과 함께 발생하고 예외가 게임 코드로 전파되지 않는다.
- Given 게임 코드가 이미 Steam을 초기화함, When 라이브러리 초기화, Then 중복 초기화 없이 준비 완료가 되고, 라이브러리 해제 시 Steam을 종료하지 않는다.

**FR-2 [M] Steam 이벤트 처리**
라이브러리가 Steam을 초기화한 경우, 게임 코드가 따로 호출하지 않아도 Steam 이벤트가 매 프레임 처리되어야 한다.

- Given 라이브러리가 초기화한 Steam, When 다른 계정이 로비에 들어옴, Then 게임 코드의 추가 호출 없이 참가 이벤트가 발생한다.

**FR-3 [M] 사용자 정보**
로컬 사용자와 세션 참가자 각각의 Steam ID와 표시 이름을 조회할 수 있어야 한다.

- Given 2인 세션, When 참가자 목록 조회, Then 두 계정의 ID와 Steam 표시 이름이 나온다.

**FR-4 [S] 아바타 이미지**
참가자의 Steam 아바타를 Unity 텍스처로 얻을 수 있어야 한다. 아직 내려받지 않은 아바타는 준비되면 알려야 한다.

- Given 아바타가 아직 캐시되지 않은 참가자, When 요청, Then 준비 완료 이벤트와 함께 텍스처가 전달된다. 실패하면 null과 사유 코드가 전달된다.

### 8.2 로비

**FR-5 [M] 로비 생성**
호스트는 공개 범위 (초대 전용, 친구 전용, 공개), 정원, 표시 이름, 게임 정의 키-값 데이터를 지정해 로비를 만들 수 있어야 한다. 라이브러리는 게임 식별자와 프로토콜 버전을 로비 데이터에 자동으로 기록해야 한다.

- Given 초기화 완료, When 정원 4인 공개 로비 생성, Then 다른 계정의 검색 결과에 그 로비가 정원 4, 표시 이름, 게임 정의 데이터와 함께 나온다.
- Given 초대 전용 로비, When 다른 계정이 검색, Then 결과에 나오지 않는다.

**FR-6 [M] 로비 검색**
공개 로비를 검색할 수 있어야 한다. 결과에는 게임 식별자와 프로토콜 버전이 같고 빈 자리가 있는 로비만 나와야 한다. 게임은 문자열 비교, 숫자 비교, 거리 범위, 최대 결과 수 조건을 더할 수 있어야 한다.

- Given 같은 AppID에서 게임 식별자가 다른 로비, When 검색, Then 결과에 나오지 않는다. (개발용 AppID 480은 여러 개발자가 함께 쓰므로 이 필터가 필요하다.)
- Given 프로토콜 버전이 다른 로비, 또는 정원이 찬 로비, When 검색, Then 결과에 나오지 않는다.

**FR-7 [M] 참가 경로**
다음 네 경로가 모두 같은 참가 절차와 같은 이벤트로 이어져야 한다: 로비 ID로 참가, Steam 오버레이 초대 수락, 친구 목록의 "게임 참가", 게임이 꺼진 상태에서 초대 수락으로 게임 실행.

- Given 게임이 꺼져 있음, When 친구의 초대를 수락해 게임이 실행됨, Then 게임 초기화가 끝난 뒤 자동으로 그 로비 참가가 시작되고, 게임 코드는 다른 경로와 같은 참가 이벤트를 받는다.
- Given 게임 실행 중이며 메뉴 화면, When 친구 목록에서 "게임 참가", Then 같은 참가 이벤트가 발생한다.

**FR-8 [M] 초대**
세션 참가자는 Steam 오버레이의 초대 대화상자를 열거나, 특정 친구에게 바로 초대를 보낼 수 있어야 한다.

- Given 로비 단계, When 초대 대화상자 열기, Then 그 로비로 초대하는 Steam 오버레이가 열린다.
- Given Steam 오버레이가 꺼져 있음, When 초대 대화상자 열기, Then 사유 코드 `OverlayUnavailable`이 반환된다.

**FR-9 [M] 참가자 목록과 변경 이벤트**
참가자마다 Steam ID, 표시 이름, 호스트 여부, 준비 상태, 연결 상태, 게임 정의 데이터를 조회할 수 있어야 한다. 입장, 퇴장, 끊김, 강퇴, 데이터 변경 때마다 이벤트가 발생해야 한다.

- Given 3인 로비, When 한 명이 나감, Then 남은 두 명에게 같은 계정 ID와 사유 코드가 담긴 퇴장 이벤트가 한 번씩 발생한다.

**FR-10 [M] 준비 상태**
각 참가자는 자기 준비 상태를 바꿀 수 있고, 그 변경은 모든 참가자에게 반영되어야 한다.

- Given 2인 로비, When 클라이언트가 준비, Then 호스트 쪽 목록에서 그 클라이언트가 준비 상태가 되고 변경 이벤트가 발생한다.

**FR-11 [S] 로비 데이터와 참가자 데이터**
호스트는 로비 데이터를, 각 참가자는 자기 참가자 데이터 (예: 고른 캐릭터)를 바꿀 수 있어야 한다. 변경되면 모든 참가자에게 이벤트가 발생해야 한다.

- Given 클라이언트, When 로비 데이터 변경 시도, Then 사유 코드 `NotHost`로 거부된다.

**FR-12 [S] 로비 채팅**
로비 단계에서 텍스트 메시지를 모든 참가자에게 보낼 수 있어야 한다. Steam 한도 (4KB)를 넘는 메시지는 보내지 않고 오류를 반환해야 한다.

- Given 4KB를 넘는 메시지, When 송신, Then 사유 코드 `MessageTooLarge`가 반환되고 아무에게도 전달되지 않는다.

**FR-13 [S] 친구 목록 상태 표시**
세션에 있는 동안 게임이 친구 목록에 보일 상태 문자열을 정할 수 있어야 한다. 같은 세션 참가자는 친구 목록에서 한 그룹으로 보여야 한다. 세션이 끝나면 이 표시는 지워져야 한다.

- Given 2인 세션, When 친구 목록 확인, Then 두 사람이 같은 그룹으로 보인다. When 세션 종료, Then 상태 문자열과 그룹 표시가 사라진다.

**FR-14 [M] 나가기**
참가자는 어느 상태에서든 세션을 나갈 수 있어야 한다. 나간 참가자의 슬롯은 즉시 비워져야 한다 (재접속 예약 대상이 아님).

- Given 4인 로비 (정원 4), When 한 명이 나감, Then 다른 계정이 그 로비에 참가할 수 있다.

> **결정 대기 (#200)**: 요구사항이 아니라 현재 구현의 동작이다. 현재 구현에서 Reconnecting 중에 나가면, 재시도 연결이 호스트에 닿아 있을 때만 슬롯이 즉시 비워지고, 그렇지 않으면 예약 시간이 끝날 때 비워진다. 연결이 끊긴 동안에는 호스트가 그 사실을 알 수 없기 때문이다.

### 8.3 인원 정책

**FR-15 [M] 정원 범위**
정원은 1 이상, 라이브러리 상한 이하여야 한다 (6장). 범위를 벗어나면 로비를 만들지 않고 거부해야 한다.

- Given 상한 16, When 정원 0 또는 17로 생성 요청, Then 사유 코드 `InvalidCapacity`로 거부되고 로비가 만들어지지 않는다.

**FR-16 [M] 정원 집행**
호스트는 Steam 로비의 정원과 별도로, 연결을 받을 때 정원 초과 여부를 확인해야 한다. 초과 연결은 거부하고 기존 참가자에게는 영향이 없어야 한다.

- Given 정원 4에 4명 참가, When 다섯 번째 계정이 연결 시도 (로비 정원 확인을 거치지 않는 경쟁 상태를 로컬 백엔드로 재현), Then 사유 코드 `SessionFull`로 거부되고 기존 4명의 연결은 유지된다.

**FR-17 [M] 정원 변경**
로비 단계에서 호스트는 정원을 바꿀 수 있어야 한다. 새 값은 현재 인원 (예약 슬롯 포함) 이상, 상한 이하여야 한다.

- Given 3인 로비, When 정원을 2로 변경, Then 사유 코드 `InvalidCapacity`로 거부된다.
- Given 게임 단계, When 정원 변경, Then 사유 코드 `InvalidState`로 거부된다.

**FR-18 [M] 시작 조건**
호스트는 최소 시작 인원 (기본 1)과 준비 확인 여부 (기본 켜짐)를 정할 수 있어야 한다. 조건을 채우지 못하면 시작 요청을 거부하고 무엇이 부족한지 알려야 한다.

- Given 최소 2인, 준비 확인 켜짐, 2인 로비에서 클라이언트가 준비하지 않음, When 호스트가 시작, Then 사유 코드 `StartConditionNotMet`와 준비하지 않은 참가자 목록이 반환된다.

**FR-19 [M] 중도 합류 정책**
호스트는 게임 단계 참가를 거부 (기본) 또는 허용으로 정할 수 있어야 한다.

- Given 거부 정책, When 게임 시작, Then 그 세션은 검색 결과에서 사라지고, 친구 목록이나 초대로도 참가할 수 없다 (사유 코드 `GameInProgress`).
- Given 허용 정책과 빈 자리, When 새 계정이 참가, Then 참가가 성공하고 게임 코드는 그 참가자가 중도 합류자임을 알 수 있다.
- When 호스트가 게임을 끝내고 로비로 돌아감, Then 세션은 생성 시 공개 범위대로 다시 참가 가능해진다.

**FR-20 [S] 재접속 슬롯 예약**
게임 단계에서 클라이언트가 비정상으로 끊기면, 라이브러리는 예약 시간 (기본 60초, 0이면 꺼짐) 동안 그 슬롯을 남겨 두어야 한다. 끊긴 클라이언트의 게임이 계속 실행 중이면 라이브러리가 자동으로 다시 연결을 시도해야 한다.

- Given 예약 60초, When 클라이언트의 네트워크가 20초 끊겼다가 돌아옴, Then 같은 슬롯으로 복귀하고 모든 참가자에게 재접속 이벤트가 발생한다.
- Given 예약 60초, When 61초가 지나도 돌아오지 않음, Then 슬롯이 비워지고 퇴장 이벤트가 사유 코드 `ConnectionLost`와 함께 발생한다.
- Given 예약 중인 슬롯, When 다른 계정이 참가 시도, Then 그 슬롯은 빈 자리로 세지 않는다.

**FR-21 [M] 중복 계정 거부**
이미 참가 중인 Steam 계정의 두 번째 연결은 거부해야 한다. 재접속 예약 중인 계정의 연결은 중복이 아니라 복귀로 처리해야 한다. 같은 계정이 게임을 새로 실행해 다시 참가하는 경우는 로비가 참가를 받아 줄 때 (로비 단계이거나 중도 합류를 허용할 때)만 복귀할 수 있고, 그렇지 않으면 사유 코드 `GameInProgress`로 거부된다.

- Given 계정 A가 참가 중, When 계정 A로 또 연결 시도, Then 사유 코드 `DuplicateAccount`로 거부된다.

**FR-22 [M] 강퇴**
호스트는 참가자를 강퇴할 수 있어야 한다. 강퇴된 참가자는 사유 코드 `Kicked`를 받고, 그 세션이 끝날 때까지 다시 들어올 수 없어야 한다.

- Given 계정 B를 강퇴함, When B가 같은 세션에 다시 참가 시도, Then 사유 코드 `Banned`로 거부된다.
- Given 클라이언트, When 다른 참가자 강퇴 시도, Then 사유 코드 `NotHost`로 거부된다.

### 8.4 세션 수명주기

**FR-23 [M] 상태와 사유 코드**
게임 코드는 현재 세션 상태 (7장)를 조회할 수 있어야 하고, 상태가 바뀔 때마다 이벤트를 받아야 한다. 모든 실패와 종료에는 사유 코드가 붙어야 한다.

- Given 아무 상태, When 상태 전환, Then 이전 상태, 새 상태, (실패나 종료면) 사유 코드가 담긴 이벤트가 정확히 한 번 발생한다.

**FR-24 [M] 게임 시작**
호스트가 시작 조건을 채운 상태에서 시작하면, 모든 참가자에게 시작 신호와 호스트가 정한 시작 데이터 (예: 맵 이름, 난수 시드)가 전달되어야 한다.

- Given 4인 로비, 조건 충족, When 호스트가 시작 데이터와 함께 시작, Then 4명 모두 같은 시작 데이터와 함께 게임 단계로 전환된다.

**FR-25 [S] 로드 완료 동기화**
각 참가자는 준비 완료 (예: 씬 로드 끝)를 알릴 수 있어야 한다. 호스트는 모두 완료되었을 때, 또는 제한 시간이 지났을 때 이벤트를 받아야 한다. 제한 시간이 지나면 완료하지 않은 참가자 목록을 받아야 한다.

- Given 4인, 제한 30초, When 3명만 완료하고 30초 경과, Then 호스트는 시간 초과 이벤트와 완료하지 않은 1명의 ID를 받는다.

**FR-26 [M] 로비 복귀**
호스트가 게임 종료를 선언하면, 같은 참가자로 로비 단계에 돌아와야 한다. 모든 준비 상태는 해제되어야 한다.

- Given 4인 게임 단계, When 호스트가 게임 종료, Then 4명 모두 로비 단계가 되고 준비 상태가 모두 해제된다.

**FR-27 [M] 호스트 이탈은 세션 종료**
호스트가 나가거나, 연결이 끊기거나, 프로세스가 강제 종료되면 모든 클라이언트의 세션이 끝나야 한다. 클라이언트는 Steam 로비에서도 자동으로 나가야 한다. Steam은 로비 소유자가 나가면 다른 멤버에게 소유권을 자동으로 넘기지만, 라이브러리는 그 로비를 새 세션으로 이어 쓰지 않아야 한다.

- Given 4인 게임 단계, When 호스트가 정상적으로 나감, Then 나머지 3명은 NFR-4 시간 안에 사유 코드 `HostLeft`와 함께 Offline이 된다.
- Given 4인 게임 단계, When 호스트 프로세스가 강제 종료됨, Then 나머지 3명은 NFR-3의 응답 없음 감지 시간 안에 사유 코드 `HostLeft`와 함께 Offline이 되고, 그 로비는 이후 검색 결과에 나오지 않는다.

**FR-28 [M] 종료 정리**
앱이 종료되거나 라이브러리가 해제되면 로비 나가기, 연결 닫기, 친구 목록 상태 지우기가 이루어져야 한다.

- Given 2인 세션의 클라이언트, When 앱 정상 종료, Then 호스트는 그 클라이언트의 퇴장 이벤트를 비정상 끊김이 아닌 정상 퇴장 사유로 받는다.

### 8.5 연결과 메시지

**FR-29 [M] 호스트 연결**
클라이언트가 로비에 들어가면 라이브러리가 자동으로 호스트와 연결해야 한다. 연결이 완료되기 전에는 참가 진행 중 상태로 보여야 한다.

- Given 로비 참가 요청, When 로비 입장은 성공했지만 호스트 연결이 실패, Then 클라이언트는 로비에서 나가고 사유 코드 `ConnectionFailed`와 함께 Offline이 된다.

**FR-30 [M] 버전 확인**
연결할 때 게임 식별자와 프로토콜 버전을 비교해야 한다. 다르면 연결을 거부해야 한다.

- Given 호스트 프로토콜 버전 3, When 버전 2인 클라이언트가 로비 ID로 직접 참가, Then 사유 코드 `VersionMismatch`로 거부되고 로비에서도 나간다.

**FR-31 [M] 송신 대상**
다음 송신을 지원해야 한다: 클라이언트에서 호스트로, 호스트에서 특정 참가자, 전체, 특정 참가자를 뺀 전체로, 클라이언트에서 다른 클라이언트로 (호스트 중계). 호스트는 클라이언트 간 중계를 메시지 종류별로 막을 수 있어야 한다. 호스트 자신을 대상으로 한 메시지는 네트워크를 거치지 않고 전달되어야 한다.

- Given 호스트, When 호스트 자신의 플레이어 코드가 "호스트로" 송신, Then 메시지는 같은 프레임 안에 호스트 핸들러에 발신자가 호스트로 표시된 채 전달된다.
- Given 4인, When 호스트가 "전체 (호스트 포함 안 함)" 송신, Then 클라이언트 3명만 받는다.

**FR-32 [M] 전달 보장 수준**
신뢰 전송 (재전송, 순서 보장)과 비신뢰 전송 (손실 허용, 순서 비보장)을 모두 지원해야 한다. 신뢰 메시지는 같은 발신자와 수신자 사이에서 보낸 순서대로 도착해야 한다.

- Given 로컬 백엔드에서 손실률 20% 시뮬레이션, When 신뢰 메시지 1,000개 송신, Then 1,000개 모두 보낸 순서대로 도착한다.

**FR-33 [M] 메시지 종류 등록과 발신자 확인**
게임은 메시지 종류 식별자와 처리기를 등록할 수 있어야 한다. 수신 측은 전송 계층이 확인한 발신자 계정을 함께 받아야 하며, 메시지 내용에 적힌 값을 발신자로 쓰지 않아야 한다. 종류마다 "호스트만 보낼 수 있음"을 지정할 수 있어야 한다. 등록되지 않은 종류의 메시지는 경고 로그를 남기고 버려야 한다.

- Given "호스트 전용" 종류, When 클라이언트가 그 종류를 송신, Then 수신 측 처리기는 호출되지 않고 경고 로그가 남는다.
- Given 처리기가 예외를 던짐, When 메시지 수신, Then 예외는 로그로 남고 세션과 이후 메시지 처리는 계속된다.

**FR-34 [M] 크기 제한**
메시지 하나의 최대 크기를 설정할 수 있어야 하고, Steam 송신 한도 (512KiB)보다 크게 설정할 수 없어야 한다. 한도를 넘는 메시지는 보내지 않고 오류를 반환해야 한다.

- Given 최대 64KiB 설정, When 65KiB 메시지 송신, Then 사유 코드 `MessageTooLarge`가 반환되고 아무에게도 전달되지 않는다.

**FR-35 [S] 직렬화 도우미**
기본 숫자 타입, 불리언, 문자열, 바이트 배열, Unity의 `Vector2`, `Vector3`, `Quaternion`, `Color`를 메시지에 쓰고 읽는 도우미를 제공해야 한다.

- Given 위 타입을 섞어 쓴 메시지, When 다른 참가자가 같은 순서로 읽음, Then 모든 값이 같게 복원된다 (부동소수는 비트 단위로 같다).

**FR-36 [S] 연결 품질**
참가자마다 핑, 패킷 손실률, 초당 송수신 바이트를 조회할 수 있어야 한다.

- Given 로컬 백엔드에서 편도 지연 100ms 시뮬레이션, When 핑 조회, Then 왕복 지연 200ms 기준 ±20ms 안의 값이 나온다.

**FR-37 [S] 송신량 제한**
호스트는 클라이언트별 초당 최대 메시지 수와 바이트를 정할 수 있어야 한다. 넘는 메시지는 버리고 이벤트를 발생시켜야 한다. 정해진 시간 동안 계속 넘으면 자동으로 강퇴하는 옵션이 있어야 한다.

- Given 초당 100개 제한, When 클라이언트가 초당 500개 송신, Then 호스트 처리기는 초당 100개 이하만 받고 초과 이벤트가 발생한다.

### 8.6 개발과 테스트 지원

**FR-38 [M] 로컬 백엔드**
Steam 없이 같은 PC의 여러 인스턴스 (에디터와 빌드, Multiplayer Play Mode의 가상 플레이어 등)가 같은 세션 API로 로비 생성, 검색, 참가, 메시지 교환을 할 수 있어야 한다. 한 프로세스 안에서 여러 참가자를 만들 수도 있어야 한다 (자동 테스트용). 게임 코드는 백엔드 선택 외에는 바꾸지 않아야 한다. 로컬 백엔드는 같은 PC 안에서만 동작해야 하며, 다른 PC와 연결하는 기능은 제공하지 않는다 (결정 D7).

- Given 같은 PC의 인스턴스 두 개, When 하나가 공개 로비를 만들고 다른 하나가 검색해 참가, Then 같은 참가 이벤트와 메시지 교환이 Steam 백엔드와 같은 순서로 일어난다.
- Given EditMode 테스트, When 한 프로세스에 호스트 1명과 클라이언트 3명 생성, Then Unity 플레이 모드 없이 로비부터 게임 시작까지 진행된다.
- Given 로컬 백엔드로 로비를 연 PC, When 같은 네트워크의 다른 PC에서 로컬 백엔드로 검색하거나 연결 시도, Then 그 로비는 보이지 않고 연결도 되지 않는다.

**FR-39 [M] 백엔드 선택**
게임은 초기화할 때 백엔드를 고를 수 있어야 한다. 에디터에서 Steam을 쓸 수 없을 때 로컬 백엔드로 바꾸는 설정이 있어야 한다.

- Given 대체 설정 켜짐, Steam 클라이언트 꺼짐, When 에디터에서 초기화, Then 경고 로그와 함께 로컬 백엔드로 준비 완료된다.
- Given 대체 설정 꺼짐 또는 플레이어 빌드, When Steam 없이 초기화, Then 사유 코드 `SteamNotRunning`으로 실패한다. 빌드에서는 자동으로 바꾸지 않는다.

**FR-40 [S] 네트워크 조건 시뮬레이션**
로컬 백엔드에서 지연 (ms), 지연 변동 (ms), 손실률 (%)을 인위로 넣을 수 있어야 한다.

- Given 손실률 10%, When 비신뢰 메시지 10,000개 송신, Then 도착 수가 8,500개에서 9,500개 사이다.

**FR-41 [S] 샘플**
Base의 `Samples~`에 로비 생성, 검색, 초대, 준비, 시작, 메시지 교환, 강퇴를 보여 주는 샘플을 둬야 한다. 샘플은 Steamworks.NET 없이도 로컬 백엔드로 실행되어야 한다.

- Given Steamworks.NET이 없는 새 프로젝트, When 샘플을 가져와 실행, Then 컴파일 오류 없이 로컬 백엔드로 로비부터 메시지 교환까지 동작한다.

**FR-42 [C] 에디터 디버그 창**
에디터 창에서 현재 세션 상태, 참가자, 연결 품질, 최근 메시지 종류별 송수신 수를 볼 수 있어야 한다.

- Given 플레이 모드의 4인 세션, When 창을 엶, Then 4명의 상태와 핑이 1초 이내 주기로 갱신된다.

## 10. 가정

- "외부 서버 없음"은 개발자가 운영하거나 비용을 내는 서버가 없다는 뜻이다. Valve가 제공하는 Steam 로비, 친구, 릴레이는 사용한다.
- 호스트는 로비를 만든 사람이며 게임 상태의 권한을 가진다. 게임 규칙의 판정은 호스트에서 이루어진다고 가정한다.
- 개발 중에는 AppID 480 (Spacewar)으로 시험할 수 있고, 출시 빌드는 게임 고유의 AppID를 쓴다.
- Steam 실제 환경 검증은 Steam 계정 2~4개와 PC 여러 대로 수동으로 한다. 16인 부하 검증은 로컬 백엔드로 한다.
- Steam 계정 하나가 플레이어 한 명이다.
- 라이브러리 서비스는 Base의 기존 DI와 매니저 규칙 (`CoreBase` 등록, `IDisposable` 해제, 일회성 구독)을 따른다. 이는 설계 단계의 제약이며 이 명세는 그 방식을 정하지 않는다.

- 자동: 로컬 백엔드의 한 프로세스 다중 참가자로 EditMode 테스트를 작성한다 (`bash ./test-unity.sh changed`). NFR-10의 규칙을 모두 다룬다.
- 다중 인스턴스: 로컬 백엔드로 에디터와 빌드, 또는 Multiplayer Play Mode를 써서 FR-38과 NFR-1, NFR-2를 확인한다.
- Steam 수동 점검 (계정 2개 이상, PC 2대, AppID 480): 로비 생성과 검색, 오버레이 초대, 친구 목록 참가, 게임이 꺼진 상태에서 초대 수락, 호스트 강제 종료, 연결 상대 IP 비노출을 점검표로 확인한다.
