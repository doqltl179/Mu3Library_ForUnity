**Mu3Library** is a modular architecture framework for Unity projects. Built around a custom DI (Dependency Injection) system and MVP (Model-View-Presenter) UI pattern, it supports scalable and maintainable game development.

## ✨ Key Features

- 🏗 **Modular Core System**: Clear separation of concerns through independent `CoreBase` modules, in the separate DI package
- 💉 **Custom DI Container**: Supports Singleton, Transient, and Scoped lifetimes, in the separate DI package
- 🎨 **MVP UI Pattern**: Testable UI logic with View-Presenter-Model separation
- 🔄 **Automatic Lifecycle Management**: Interface-based system with `IInitializable`, `IUpdatable`, `IDisposable`
- 📦 **Optional Package Support**: Conditional activation for UniTask, Addressables, Input System
- 🎵 **Audio System**: BGM/SFX/Environment channels with volume control, mixer-group routing, BGM ducking, persisted volumes, and awaitable fades
- ✨ **Particle Handler**: Convenient `ParticleSystem` playback, pause, stop, clear, restart, `Loop`/`IsLooping`/`SetLoop`/`PlayLoop`/`PlayOnce` controls, state queries, and lifecycle events on a required component
- 🌐 **WebRequest**: HTTP GET/POST/PUT/PATCH/DELETE, download size queries, retry backoff, in-flight cancellation, download progress, UniTask support
- 📊 **Observable Pattern**: Data change detection and event-based binding
- 🖥 **Debug Console**: In-game console for player builds with typed commands, developer-only and player-facing access, a mark for commands that change progress, and Unity's log
- 🔀 **State Machine**: Keyed states for game, UI, or AI flows, with enter and exit that may wait as coroutines or, with UniTask, as async methods, requests queued in order while a transition waits, guards, and a way back
- 💾 **Save System**: Section-based saves into slots, with data versions and migration, checked files written safely, and Unity types such as `Vector3` saved as they are, and multiplayer session saves that keep each player's data under their ID and that the host can share with another player
- 🛠 **Utility Collection**: Extension Methods, ObjectPool, EasingFunctions
- ✅ **Initialization Result Contracts**: Addressables/Localization expose explicit init success/failure state
- 🔁 **Resilient Networking**: WebRequest result-based APIs include status, headers, timeout, retry options, and opt-in cancellation propagation
- 🧭 **Deterministic Core Updates**: Core execution order is explicit and stable, in the separate DI package
- ⏳ **Scene Async APIs**: Phase-based UniTask helpers for built-in and Addressables scenes, plus structured lifecycle callbacks with resolved scene names
- 🎮 **Input System Manager**: Action asset management, interactive rebinding, and binding override persistence, with a name exporter drawer, in the separate Input System package
- 🌍 **Localization Manager**: String and localized asset lookup and locale changes that every subscriber hears, with a data exporter that splits locales, tables, and entries into focused scripts and a character collector, in the separate Localization package
- 🗂 **Addressables Manager**: Asset loading and caching by key, download size queries and dependency downloads, and catalog checks and updates that reach Addressables one call at a time, with a group data exporter that splits labels, groups, and entries into focused scripts it can wrap in a define symbol, in the separate Addressables package
- 🖼 **World-Space Background Utility**: Fits a required `SpriteRenderer` background to the camera viewport with optional automatic fitting, camera-front placement, and renderer display settings
- 🍉 **Watermelon Game Template**: Reusable `Mu3Library.Game.WatermelonGame` runtime assembly with an eleven-item 2D merge board, configurable `BoardConfig`, and board fitting and coordinate helpers

## 📚 Core Modules

### DI (Dependency Injection)
The DI container, with `CoreBase` and `CoreRoot`, moved to the separate DI package: see its [README](packages/di/README.md) for registration, injection, cores, and the link.xml it writes for player builds that strip managed code. Base keeps the contracts its managers implement, `IInitializable`, `IUpdatable`, `ILateUpdatable`, `IObjectInjector`, and `[Inject]`, in its `Mu3Library.Foundation` assembly. The examples below inject Base's services with `[Inject]`, as a core of the DI package does.

### MVP (Model-View-Presenter)
Separates UI into View, Presenter, and Model for testable business logic. The view is a component, so it lives in a file named after its class, `MainMenuView.cs`, as do `UICore` and `UIBootstrap` below.

```csharp
using Mu3Library.Audio;
using Mu3Library.DI;
using Mu3Library.UI.MVP;
using TMPro;
using UnityEngine;
using UnityEngine.UI;

// Arguments: Data passed to each Open
public class MainMenuArgs : Arguments
{
    public string PlayerName;
}

// Model: Data container, filled from the arguments before the presenter's LoadFunc() runs
public class MainMenuModel : Model<MainMenuArgs>
{
    public string PlayerName { get; private set; }

    // The base Init is empty: copy what the model needs from the arguments here
    public override void Init(MainMenuArgs args)
    {
        PlayerName = args?.PlayerName;
    }
}

// View: Unity component references
public class MainMenuView : View
{
    [SerializeField] private Button _startButton;
    [SerializeField] private TextMeshProUGUI _titleText;
    [SerializeField] private AudioClip _clickClip;

    public Button StartButton => _startButton;
    public TextMeshProUGUI TitleText => _titleText;
    public AudioClip ClickClip => _clickClip;
}

// Presenter: Business logic
public class MainMenuPresenter : Presenter<MainMenuView, MainMenuModel, MainMenuArgs>
{
    // From AudioCore, the core of the DI package's README that registers AudioManager;
    // Open throws when no AudioCore is in the scene, since this member is required
    [Inject(typeof(AudioCore))] private IAudioManager _audioManager;

    protected override void LoadFunc()
    {
        _view.StartButton.onClick.AddListener(OnStartClicked);
        _view.TitleText.text = $"Welcome, {_model.PlayerName}";
    }

    protected override void OpenFunc()
    {
        // Open animations, etc.
    }

    protected override void UnloadFunc()
    {
        // A closed presenter is pooled with its view, and the next Open runs LoadFunc() on it again
        _view.StartButton.onClick.RemoveListener(OnStartClicked);
    }

    private void OnStartClicked()
    {
        _audioManager.PlaySfx(_view.ClickClip);
        // Game start logic
    }
}
```

`MVPManager` opens a presenter only for a view type it holds a prefab of. Register each view prefab, one whose root holds the view component, with `RegisterViewResource` or `RegisterViewResources` before its first `Open`; adding `MainMenuView` to the root also adds the `Canvas`, `CanvasScaler`, `GraphicRaycaster`, and `CanvasGroup` the view requires. Without a registered prefab, `Open` logs `View not found` and returns null. `Open` builds the presenter's model with `Init(args)` and calls `LoadFunc()` while the view is still hidden. The view shows and starts opening in the next `MVPManager.Update()`, and later updates finish the open and, once the window has closed, unload it, so something has to call `Update()` every frame.

With the DI package, a core registers the manager, and `CoreRoot` calls its `Update()` every frame and disposes it when the core is destroyed. When `MVPManager` is registered through `CoreBase`, presenter `[Inject]` fields and properties are populated before presenter initialization:

```csharp
using Mu3Library.DI;
using Mu3Library.UI.MVP;
using UnityEngine;

public class UICore : CoreBase
{
    [SerializeField] private MainMenuView _mainMenuViewPrefab;

    [Inject] private IMVPManager _mvpManager;

    protected override void ConfigureContainer()
    {
        RegisterClass<MVPManager>();
    }

    protected override void Start()
    {
        base.Start(); // Injects _mvpManager

        _mvpManager.RegisterViewResource(_mainMenuViewPrefab);
        _mvpManager.Open<MainMenuPresenter>(new MainMenuArgs { PlayerName = "Player1" });
    }
}
```

Without the DI package's `CoreBase`, the code that creates the manager calls its `Update()` every frame and its `Dispose()` when done with it. Nothing gives such a manager an `IObjectInjector`, so it leaves presenter `[Inject]` members unset; leave the `[Inject]` field, with its `AudioCore`, which derives from `CoreBase`, and the `PlaySfx` call out of `MainMenuPresenter` there:

```csharp
using Mu3Library.UI.MVP;
using UnityEngine;

public class UIBootstrap : MonoBehaviour
{
    [SerializeField] private MainMenuView _mainMenuViewPrefab;

    private MVPManager _mvpManager;

    private void Awake()
    {
        _mvpManager = new MVPManager();
        _mvpManager.RegisterViewResource(_mainMenuViewPrefab);
    }

    private void Start()
    {
        _mvpManager.Open<MainMenuPresenter>(new MainMenuArgs { PlayerName = "Player1" });
    }

    private void Update()
    {
        _mvpManager.Update();
    }

    private void OnDestroy()
    {
        _mvpManager.Dispose();
    }
}
```

Use `Arguments` for data that changes each time a presenter is opened.

For chained presenters, ownership and visual hosting are configured separately.

```csharp
public class InventoryPresenter : Presenter<InventoryView, InventoryModel, InventoryArgs>
{
    private void OpenTooltip()
    {
        OpenAsChild<TooltipPresenter>(new HostOptions
        {
            Host = _view.TooltipHost,
            ApplyLayout = rectTransform =>
            {
                rectTransform.anchoredPosition = new Vector2(24f, -16f);
            },
        });
    }
}
```

`Owner` controls lifecycle chaining, while `HostOptions` controls where the child view is attached and how its root `RectTransform` is laid out.

A child can be opened from any presenter callback, `LoadFunc()` and `OpenFunc()` included; the owner does not have to be open yet. Closing an owner cascades to its children, including one that is still loading. A child hosted under the owner's view unloads even when the owner finishes closing first; its close transition then ends when the owner's view is hidden. The manager ends that close whether or not a view that overrides `OnDisable` calls `base.OnDisable()`, though such a view should still call it. A presenter that has started closing no longer takes new children.

A window opened under a host that is hidden, such as an inactive `HostOptions.Host`, cannot run its open transition there. It skips the wait instead: `OpenStart()` and `OpenEnd()` run back to back, an `AnimationView` takes its opened pose at once, and the window counts as opened in the next manager update. It shows fully open once the host is shown, a plain `Close` closes it, and `OpenAsync` completes for it. Closed while the host is still hidden, it skips its close transition, and an `AnimationView` takes its closed pose, so its next open animates again.

A window whose host or owner is hidden while it is still opening, such as a panel behind a tab that is switched away during the open animation, finishes its open at that moment instead of staying on its way in. The rest of the open transition is skipped, `OpenEnd()` still runs, an `AnimationView` takes its opened pose, and the window counts as opened in the next manager update, so a plain `Close` closes it and `OpenAsync` completes for it. When the host is shown again, the window is fully open. The manager ends such an open as well when the view overrides `OnDisable` without calling `base.OnDisable()`, in its next update while the view is still hidden; such a view shown again within the same frame stays opening, so it should still call `base.OnDisable()`. An `AnimationView` hidden in the middle of any animation takes the end pose of that animation, so its next animation starts from there. A view destroyed while it opens finishes its open the same way, so its `OpenEnd()` runs during the teardown, for example under a host whose scene unloads; only `DestroySelf()` leaves the open as it is.

`AnimationView` animations advance on unscaled time by default, so a popup opened from a pause menu that sets `Time.timeScale` to 0 still opens and closes. For an animation that should follow the game's time scale instead, set **Time Mode** on the view's `AnimationHandler` to `Scaled`, or set `AnimationHandler.TimeMode` from code. `TimeMode` is in the `Mu3Library.Utility` namespace.

Direct manager calls can keep the same ownership and host configuration in one overload:

```csharp
_mvpManager.Open<TooltipPresenter>(inventoryPresenter, new HostOptions
{
    Host = tooltipHost,
});
```

### Audio System
Separate management of BGM and SFX with volume control support.

```csharp
[Inject] private IAudioManager _audioManager;
[Inject] private IAudioVolumeSettings _audioVolumeSettings;

void Start()
{
    // Set volumes
    _audioVolumeSettings.MasterVolume = 0.8f;
    _audioVolumeSettings.BgmVolume = 0.6f;

    // Play BGM
    _audioManager.PlayBgm(bgmClip);

    // Play SFX
    _audioManager.PlaySfx(sfxClip);

    // Play SFX at its own volume, starting from the default SFX settings
    AudioSourceSettings sfxSettings = AudioSourceSettings.SfxStandard;
    sfxSettings.Volume = 0.5f;
    _audioManager.PlaySfx(sfxClip, sfxSettings);
}
```

Fades, ducks, loop intervals, and the gap between playlist tracks advance on unscaled time by default, so they keep running while `Time.timeScale` is 0, as the sources themselves keep playing then. Set `_audioManager.TimeMode = TimeMode.Scaled;` to have them follow the game's time scale. `PlayBgm`, `PlayBgmForce`, and `TransitionBgm` end a running BGM playlist, as `StopBgm` does.

### Addressables
`AddressablesManager`, which loads and caches assets by key and runs catalog checks and updates one call at a time, moved to the separate Addressables package: see its [README](packages/addressables/README.md) for its use. Base keeps the Addressables scene loading of the Scene Loader below.

### Scene Loader
Supports explicit scene commands for both built-in and Addressables scenes.

```csharp
[Inject] private ISceneLoader _sceneLoader;
[Inject] private ISceneLoaderEventBus _sceneLoaderEventBus;

// Legacy callbacks keep the requested target or Addressables key.
_sceneLoaderEventBus.OnSingleSceneLoaded += target =>
{
    Debug.Log($"Loaded target: {target}");
};

// Structured lifecycle callbacks expose the resolved Unity scene name.
// Addressables scenes use "UnnamedAddressableScene" until the runtime name is available.
_sceneLoaderEventBus.OnSingleSceneLifecycle += info =>
{
    Debug.Log($"{info.Phase}: target={info.Target}, resolved={info.ResolvedSceneName}");
};

// With Addressables, a load that started and then failed is reported once its command is over,
// so IsLoading is already false here and the handler may start another load.
_sceneLoaderEventBus.OnSceneLoadFailed += info =>
{
    Debug.LogWarning($"Load failed: target={info.Target}, additive={info.IsAdditive}, {info.ErrorMessage}");
};

await _sceneLoader.LoadSingleSceneAsync("Main");
await _sceneLoader.LoadSingleSceneWithAddressablesAsync("Sample_Addressables");
```

### State Machine
`StateMachine<TKey>` (`Mu3Library.States`) moves between states that a game registers under keys, usually an enum: a game flow from boot to title, lobby, game, and results, a UI flow, or an enemy's behavior. A state, usually a `State` subclass, overrides what it needs: `Enter` and `Exit`, which may `yield` to wait as a coroutine does, and `Update`. The machine steps these routines from its own `Update`, so it waits for `null`, a nested routine, a `CustomYieldInstruction` such as `WaitUntil` or `WaitForSecondsRealtime`, and an `AsyncOperation`, but `WaitForSeconds` and the other `YieldInstruction`s wait one frame only, with a warning: wait for time with `WaitForSecondsRealtime` or `WaitUntil` instead. A transition exits the current state, waiting until its `Exit` ends, then enters the new one, waiting until its `Enter` ends, and raises `OnStateChanged`; one that waits for nothing ends within `ChangeState`. Requests that come while a transition waits run one by one in the order they came. `AddGuard` adds a condition that can block a transition, which `OnTransitionBlocked` reports, and `Back` returns to the previous state, one step: the machine keeps no history, so a second `Back` returns to where the first one left. The owner calls `Update` every frame, which steps a transition that waits and otherwise updates the current state. With UniTask, a state derived from `AsyncState` awaits its `EnterAsync` and `ExitAsync` instead. The machine is tied to no scene loader or UI system; here a game flow loads its scenes with `SceneLoader`:

```csharp
using System.Collections;
using System.Threading;
using Cysharp.Threading.Tasks; // for AsyncSceneState only
using Mu3Library.Scene;
using Mu3Library.States;
using UnityEngine;

public enum GameFlow { Boot, Title, Game }

public class SceneState : State
{
    private readonly ISceneLoader _sceneLoader;
    private readonly string _sceneName;

    public SceneState(ISceneLoader sceneLoader, string sceneName)
    {
        _sceneLoader = sceneLoader;
        _sceneName = sceneName;
    }

    // The next state comes in once the scene loaded. A routine may yield null, a nested routine,
    // a CustomYieldInstruction such as WaitUntil or WaitForSecondsRealtime, or an AsyncOperation;
    // WaitForSeconds waits one frame only.
    public override IEnumerator Enter()
    {
        _sceneLoader.LoadSingleScene(_sceneName);
        yield return new WaitUntil(() => !_sceneLoader.IsLoading);
    }
}

// With UniTask, the same state awaits instead.
public class AsyncSceneState : AsyncState
{
    private readonly ISceneLoader _sceneLoader;
    private readonly string _sceneName;

    public AsyncSceneState(ISceneLoader sceneLoader, string sceneName)
    {
        _sceneLoader = sceneLoader;
        _sceneName = sceneName;
    }

    public override async UniTask EnterAsync(CancellationToken cancellationToken)
    {
        await _sceneLoader.LoadSingleSceneAsync(_sceneName);
    }
}

// The owner outlives the scenes it loads, such as a core or an object kept with DontDestroyOnLoad.
_flow = new StateMachine<GameFlow>();
_flow.Add(GameFlow.Boot, new SceneState(_sceneLoader, "Boot"));
_flow.Add(GameFlow.Title, new SceneState(_sceneLoader, "Title"));
_flow.Add(GameFlow.Game, new SceneState(_sceneLoader, "Game"));
_flow.AddGuard(transition => transition.To != GameFlow.Game || _isSignedIn);
_flow.OnStateChanged += transition => Debug.Log($"Flow: {transition}");
_flow.ChangeState(GameFlow.Boot);

// Every frame.
_flow.Update();

// Later: requests made while the boot scene still loads wait their turn.
_flow.ChangeState(GameFlow.Title);
_flow.Back(); // to the state before the current one

// When the owner goes away.
_flow.Dispose();
```

### WebRequest
Simplifies HTTP request handling.

```csharp
[Inject] private IWebRequestManager _webRequest;

// GET request
_webRequest.Get<string>("https://api.example.com/data", response =>
{
    Debug.Log(response);
});

// POST request
var requestBody = new { username = "player", score = 100 };
_webRequest.Post<object, ServerResponse>("https://api.example.com/submit", requestBody, response =>
{
    Debug.Log($"Success: {response.message}");
});

// UniTask support (when MU3LIBRARY_UNITASK_SUPPORT is enabled)
var data = await _webRequest.GetAsync<DataModel>("https://api.example.com/data");

// Propagate cancellation only when the caller explicitly needs it
var cancellableData = await _webRequest.GetAsync<DataModel>(
    "https://api.example.com/data",
    cancellationToken: token,
    propagateCancellation: true);

// Results carry the status code and headers of an HTTP error response, with the callback API and
// with UniTask alike. A request that got no response, such as a refused connection, has status code 0.
WebRequestResult<DataModel> result = await _webRequest.GetResultAsync<DataModel>("https://api.example.com/data");
if (!result.IsSuccess && result.StatusCode == 401)
{
    // Sign in again, then retry.
}
```

### Observable Pattern
Detects value changes and publishes events.

```csharp
[Serializable]
public class PlayerData
{
    public ObservableInt Health = new ObservableInt();
    public ObservableString PlayerName = new ObservableString();
}

// Subscribe to events
_playerData.Health.AddEvent(newHealth =>
{
    Debug.Log($"Health changed: {newHealth}");
    UpdateHealthUI(newHealth);
});

// Change value (automatically publishes event)
_playerData.Health.Set(80);
```

An Observable field can also sit inside a `[Serializable]` class, an array, or a list on a component or ScriptableObject; editing it in the Inspector applies the value and notifies its subscribers, and so does undoing or redoing that edit or reverting a prefab instance, with the restored value. In an `ObservableDictionary`, the first row of a key wins: a row that repeats a key stays in the list with a warning until its key is changed.

### Save System
Saves and loads a game in sections: each system or stage describes its part of the game as one section, and the game saves and loads sections at points it chooses, such as a checkpoint or the end of a stage, rather than every detail of the moment. It lives in the `Mu3Library.Save` assembly, which an assembly definition of your own references.

```csharp
using System;
using Mu3Library.Save;
using UnityEngine;

[Serializable]
public class PlayerSaveData
{
    public Vector3 Position;
    public int Level;
}

public class PlayerSaveSection : SaveSection<PlayerSaveData>
{
    private readonly Transform _player;
    private readonly PlayerStats _stats;

    public override string Key => "player";
    public override int Version => 2;

    public PlayerSaveSection(Transform player, PlayerStats stats)
    {
        _player = player;
        _stats = stats;
    }

    protected override PlayerSaveData Capture() =>
        new PlayerSaveData { Position = _player.position, Level = _stats.Level };

    protected override void Restore(PlayerSaveData data)
    {
        _player.position = data.Position;
        _stats.Level = data.Level;
    }

    // Version 1 saved no level, so those saves read it as 0.
    protected override PlayerSaveData Migrate(int savedVersion, PlayerSaveData data)
    {
        if (savedVersion < 2)
        {
            data.Level = 1;
        }

        return data;
    }
}

// Files in Saves under Application.persistentDataPath, written as JSON.
var saves = new SaveManager();
saves.RegisterSection(new PlayerSaveSection(playerTransform, playerStats));
saves.RegisterSection(SaveSection.Create("stage", () => _stage, data => _stage = data));

saves.Save("slot1");            // every registered section
saves.Save("slot1", "stage");   // one section; the slot keeps the others

saves.SetMetadata("slot1", "chapter", "3. The Forest");   // for a slot list

SaveResult result = saves.Load("slot1");
if (!result.IsSuccess)
{
    Debug.LogWarning($"Load failed: {result}");   // result.Reason says why
}
```

- **Sections and slots**: A slot holds one entry per section key. Saving one section keeps the slot's other sections, and a section the slot holds that no code registers stays in it untouched. Loading the whole slot reads, checks, and migrates every registered section first, so a damaged or too new section, or a migration that throws, restores none of them, and then calls `RestoreDefault` on each registered section the slot does not hold, such as one the game added after the slot was saved. Saving one section into a damaged slot fails with `SaveFailureReason.Corrupted`, while saving the whole slot writes it anew with the registered sections only, since what it held cannot be read.
- **Data**: The default `JsonSaveSerializer` writes a section's data through `JsonUtility`, so Unity types such as `Vector3`, `Quaternion`, and `Color` save as they are. The data is a `[Serializable]` class or struct; a primitive, a string, or a collection on its own is refused, so put it in a field. `JsonUtility` writes no dictionary or property.
- **Versions**: Raise a section's `Version` when its data changes shape. A slot saved with an older version passes through `Migrate`, which receives the data read into the current type, where a field the old version lacked holds its default, and runs before any section restores, so it must not touch the game. A slot saved with a newer version fails with `SaveFailureReason.VersionTooNew`, and so does a save that would write an older version over it, so a build that went back a version loses nothing a newer one saved. A slot written in a newer slot format is refused the same way.
- **Storage**: `FileSaveStorage` keeps each slot in `<slot ID>.sav` and writes it through a temporary file that then replaces it, so a write that stops partway leaves the previous save readable. `MemorySaveStorage` keeps slots in memory. Implement `ISaveStorage` for another place, such as a platform's cloud storage. Each slot carries a CRC-32 check, so a damaged file fails with `SaveFailureReason.Corrupted`.
- **Slot lists**: `GetSlots` and `TryGetSlotInfo` read a slot's sections, versions, times, size, and metadata without restoring anything; a damaged or too new slot is left out. `SetMetadata` sets a short value of a saved slot for such a list, such as a chapter name or play time, up to 32 values of 256 characters each, and saves keep them; `Peek` reads one section's data without restoring it. `ExportSlot` and `ImportSlot` hand out and take back a slot's checked bytes, such as for a backup, and every length is checked before it is read, so bytes from elsewhere are safe to parse, while the sections they hold restore as their sender wrote them. `MaxSlotSize`, 8 MiB by default, caps a slot with all its sections.
- Slot IDs take letters, digits, `_`, and `-`, up to 64 characters, but not a name Windows keeps for a device, such as `CON`; section and metadata keys also take `.`. A file system that ignores case keeps two IDs that differ only in case as one slot. Calls run on the calling thread, and a save, load, or storage failure comes back as a `SaveResult`; only a mistake in the calling code throws, such as a null argument or a `MaxSlotSize` of 0 or less. `ISaveManagerEventBus` raises `OnSaved`, `OnLoaded`, `OnSlotDeleted`, and `OnSlotImported`.

### Debug Console
An in-game console for player builds: commands the game registers, the lines it ran, and Unity's log, drawn over the game. It lives in the `Mu3Library.DebugConsole` assembly, which an assembly definition of your own references.

```csharp
using Mu3Library.DebugConsole;
using UnityEngine;

public class ConsoleSetup : MonoBehaviour
{
    private DebugConsoleManager _console;

    private void Awake()
    {
        _console = new DebugConsoleManager();   // captures Unity's log while it lives

        // Developer commands run in the editor and in a Development Build only.
        _console.RegisterCommand<int>("level", level => LoadLevel(level),
            new ConsoleCommandOptions("Loads a level.", affectsProgress: true));

        // Player commands are what the game offers its players on purpose.
        _console.RegisterCommand<int, int>("give", GiveItem,
            new ConsoleCommandOptions("Gives an item.", ConsoleAccess.Player, affectsProgress: true));

        // Let players open the console in a release build, for the Player commands only.
        _console.PlayerConsoleEnabled = _settings.AllowPlayerConsole;
        _console.OnProgressModified += commandName => _saveData.UsedConsole = true;

        DebugConsoleView.Create(_console);   // the ` key opens it
    }

    private void GiveItem(int item, int count = 1) { /* ... */ }

    private void OnDestroy() => _console.Dispose();
}
```

- **Access**: A `Developer` command, the default, runs only in the editor and in a Development Build. A `Player` command is one the game offers its players on purpose, such as a convenience or a cheat it allows: it also runs in a release build once the game turns on `PlayerConsoleEnabled`. A release build keeps the console closed until then, and lists, completes, and runs only the commands its build lets run: it answers a `Developer` command as unknown.
- **Progress**: A command marked `affectsProgress` sets `HasModifiedProgress` and raises `OnProgressModified` when it runs, even if it then throws, so the game can mark the save or hold back achievements by its own rules; `ResetProgressModified` clears the mark.
- **Arguments**: A command takes up to four typed parameters: `string`, `int`, `long`, `float`, `double`, `bool` (`true`, `false`, `on`, `off`, `yes`, `no`, `1`, `0`), an enum by name or number, `Vector2` and `Vector3` as `x,y` and `x,y,z`. A method's default values make its last parameters optional, a vector's `default` reading as zero, and words in double quotes keep their spaces. A command registered with an `Action<ConsoleCall>` gets the words as typed and can `Print`. Names match without case; `help` and `clear` come built in.
- **View**: `DebugConsoleView` draws the console with IMGUI, which reads the keyboard under either input backend. The toggle key, `` ` `` by default, opens and closes it, Enter runs the line, Up and Down walk the history, Tab completes a command name, and Escape closes it. On a device without a keyboard, call `Open` from the game's own button or gesture. The keys also reach the game's own input, so pause it while the console is open, such as from `OnOpenChanged`. The view filters Unity's log by level, and the console keeps the newest `MaxLines` lines, 1000 by default.
- `Execute` runs a line from code and returns a `ConsoleResult` that says why a line failed, and a command that throws also logs its exception; `IDebugConsoleManagerEventBus` raises `OnLineAdded`, `OnCleared`, `OnOpenChanged`, `OnProgressModified`, and `OnExecuted`. Dispose the manager to stop capturing the log.

### Multiplayer
`MultiplayerManager` (`Mu3Library.Multiplayer`) runs a player-hosted session: one player hosts, the others find the host's lobby and connect to the host, and the host decides the roster, the rules, and when the game starts. It runs on a backend: `LocalBackend` (`Mu3Library.Multiplayer.Local`), for several players inside one process or, on a network from `LocalNetwork.CreateMachineWide`, editors and player builds on one computer, or `SteamBackend` from the separate [Steam package](packages/steam/README.md). Code in an assembly definition of its own references `Mu3Library.Multiplayer` to use it. Everything runs on the main thread, and what the backend reports, the other players' messages, and the answers to lobby requests arrive from inside `Update`, so call it every frame.

```csharp
using System;
using System.Text;
using Mu3Library.Multiplayer;
using Mu3Library.Multiplayer.Backend;
using Mu3Library.Multiplayer.Data;
using Mu3Library.Multiplayer.Local;
using UnityEngine;

public class SessionRunner : MonoBehaviour
{
    private const ushort MoveMessage = 1;

    private IMultiplayerBackend _backend;
    private MultiplayerManager _manager;
    private readonly MessageWriter _writer = new MessageWriter();

    private void Awake()
    {
        // Players on one computer. A Steam game creates its backend with SteamBackend.TryCreate,
        // or with SteamBackend.CreateOrFallback, which falls back on a LocalBackend in the editor.
        _backend = new LocalBackend(LocalNetwork.CreateMachineWide("my-game"), "Player");
        _manager = new MultiplayerManager();
        _manager.Initialize(_backend, new MultiplayerConfig("my.game", 1));

        // Every player registers the same message types with the same policy.
        _manager.RegisterMessage(MoveMessage, OnMove);

        _manager.OnGameStarted += startData =>
        {
            // Load the level the start data names, then tell the host this player is ready to play.
            _manager.ReportLoaded();
        };
        _manager.OnAllPlayersLoaded += () => Debug.Log("Every player loaded"); // the host only
    }

    private void Update() => _manager.Update();

    private void OnDestroy()
    {
        _manager.Dispose(); // before the backend, which belongs to whoever created it
        _backend.Dispose();
    }

    // The host creates the lobby.
    public void Host()
    {
        LobbyCreateOptions options = new LobbyCreateOptions
        {
            Name = "My lobby",
            Visibility = LobbyVisibility.Public,
            Rules = SessionRules.Default.WithCapacity(4),
        };
        _manager.CreateLobby(options, result => Debug.Log($"Create lobby: {result}"));
    }

    // A client searches for a lobby and joins it.
    public void Join()
    {
        _manager.SearchLobbies(new LobbySearchQuery(), found =>
        {
            if (found.IsSuccess && found.Lobbies.Count > 0)
            {
                _manager.JoinLobby(found.Lobbies[0].Id, result => Debug.Log($"Join lobby: {result}"));
            }
        });
    }

    public void SetReady() => _manager.SetReady(true); // a client, in the lobby

    // The host starts the game once the rules allow it; the result names the players who are not ready.
    public void StartGame() => _manager.StartGame(Encoding.UTF8.GetBytes("Level1"));

    public void SendMove(Vector3 position)
    {
        _writer.Clear().WriteVector3(position);
        _manager.Send(MoveMessage, _writer.Written, MessageTarget.Others, DeliveryMode.Unreliable);
    }

    private void OnMove(MessageContext context, ReadOnlySpan<byte> payload)
    {
        MessageReader reader = new MessageReader(payload);
        Vector3 position = reader.ReadVector3();
        // Move the character of context.Sender to the position.
    }

    public void ReturnToLobby() => _manager.EndGame(); // the host

    public void Quit() => _manager.Leave();
}
```

- **Message policy**: `MessagePolicy.Default` lets any player send a type, and the host passes a client's message on before its own handler runs. `HostOnly` is for what only the host decides, such as scores or spawns: the host drops it when a client sends it. `NoClientRelay` is for a client's request the host must check before anyone else sees it, such as an attack: the client sends it to `MessageTarget.Host`, and the host's handler sends on what it accepts. Every player registers each type with the same policy, since the host enforces it.
- **Delivery mode**: `DeliveryMode.Reliable`, the default, arrives in the order it was sent from the same sender and suits events that must not be lost. `Unreliable` may be lost or arrive out of order and suits state the next message replaces, such as positions sent every frame.
- **Rate limits**: `SessionRules` sets no limit by default. `MaxMessagesPerSecond` and `MaxBytesPerSecond` cap what the host takes from one client in a second, counting every packet the client sends, its ready changes and load reports included, so set them above what the game sends at its busiest: a client that sends its position 30 times a second fits within `SessionRules.Default.WithCapacity(4).WithMaxMessagesPerSecond(60).WithMaxBytesPerSecond(16 * 1024)`. The host drops a game message beyond a limit and raises `OnRateLimitExceeded`, and with `RateLimitKickSeconds` above 0 it kicks a client that goes past a limit every second for that many seconds.
- **Loading**: after `StartGame`, each player calls `ReportLoaded` once its level is ready, and the host hears `OnAllPlayersLoaded`, or `OnLoadTimedOut` with the players who did not report once `SessionRules.LoadTimeoutSeconds` (60 by default) passes. A game that changes levels within one game calls `BeginLoadPhase` on the host with data such as the next level's name: every player's loaded flag clears, every player hears `OnLoadPhaseBegan` with the data, loads, and reports again, and the host waits again under the same rules. A report sent before the phase began counts for nothing in it.

```csharp
// In Awake, beside OnGameStarted: every player, the host included, hears each new phase.
_manager.OnLoadPhaseBegan += phaseData =>
{
    // Load the level the phase data names, then report again.
    _manager.ReportLoaded();
};

// Later in the game, the host moves everyone to the next level.
_manager.BeginLoadPhase(Encoding.UTF8.GetBytes("Level2"));
```
- **Voice**: `SteamBackend` and `LocalBackend` implement `IVoiceBackend` (`Mu3Library.Multiplayer.Backend`), which records this player's voice and decodes other players' voice: Steam voice on Steam, and the default microphone on the local backend, so the same code runs in the editor. The game carries the voice as a game message, usually `Unreliable`, and picks who hears it: the sender with a `MessageTarget`, or the host, for each message and each player, with `SetRelayFilter`, as proximity voice or a radio channel needs. A `VoicePlayer` plays each speaker through an `AudioSource` of the game's own, whose settings, such as `spatialBlend` and rolloff, decide how the voice sounds in the scene. Voice counts toward the rate limits: the local backend's voice takes 16,000 bytes a second while it records, silence included.

```csharp
// Beside the session code above: add using System.Collections.Generic;
private const ushort VoiceMessage = 2;
private IVoiceBackend _voice;
private readonly Dictionary<PlayerId, VoicePlayer> _voicePlayers = new Dictionary<PlayerId, VoicePlayer>();

// In Awake, after Initialize.
_voice = _backend as IVoiceBackend;
_manager.RegisterMessage(VoiceMessage, OnVoice);
// Only on the host does the filter count: nobody hears a player who is far away.
_manager.SetRelayFilter(VoiceMessage, (speaker, listener) => AreClose(speaker, listener));
_manager.OnParticipantLeft += (participant, reason) =>
{
    if (_voicePlayers.TryGetValue(participant.Id, out VoicePlayer player))
    {
        player.Dispose();
        _voicePlayers.Remove(participant.Id);
    }
};

// Push to talk.
public void SetTalking(bool talking)
{
    if (talking)
    {
        _voice.StartVoiceRecording();
    }
    else
    {
        _voice.StopVoiceRecording();
    }
}

// In Update, after _manager.Update(): send what was recorded since the last frame, and play.
if (_voice.TryReadVoice(out ReadOnlySpan<byte> voice) && _manager.State == SessionState.InGame)
{
    _manager.Send(VoiceMessage, voice, MessageTarget.Others, DeliveryMode.Unreliable);
}

foreach (VoicePlayer player in _voicePlayers.Values)
{
    player.Update();
}

private void OnVoice(MessageContext context, ReadOnlySpan<byte> payload)
{
    if (!_voicePlayers.TryGetValue(context.Sender, out VoicePlayer player))
    {
        // An AudioSource on the speaker's character, which the game looks up.
        player = new VoicePlayer(VoiceSourceOf(context.Sender), _voice.VoiceSampleRate);
        _voicePlayers.Add(context.Sender, player);
    }

    if (_voice.TryDecodeVoice(payload, out ReadOnlySpan<float> samples))
    {
        player.Write(samples);
    }
}
```
- **State sync**: `StateSyncManager` (`Mu3Library.Multiplayer.Sync`) keeps game states the same on every player within a byte budget, so systems whose state changes every frame do not each send messages of their own. Each system decides what its state holds and how precisely it writes it, in a `SyncState` subclass or an `ISyncState` of its own, with a whole write and, if it overrides one, a write of what changed. The manager decides how much goes and when: every `StateSyncConfig.TickIntervalSeconds` (20 times a second by default) it gathers the states that changed into one message per player and delivery mode, and sends each player at most `MaxBytesPerTick` (512 by default). States that do not fit wait for a later tick, picked by their priority and by how long they waited, and a player who missed a change, joins during the game, or comes back to their slot gets the whole state. The host sends the states it owns, and a state a client owns, such as its own character, goes from that client to the host under the same budget and on to the other players. An unreliable state, the default, also goes whole every `FullStateIntervalSeconds` (1 by default), so a copy that lost an update catches up; a reliable one suits a state that changes now and then, such as a door. An interest filter lets the host send a state only to the players it picks, such as those close by. `TransformSync` syncs a transform's position and rotation, quantized, and moves each copy smoothly between the updates. The manager syncs while the game runs (`SessionState.InGame`); `CheckRateLimits` tells whether what a client sends fits the session's rate limits, which the manager also checks as each game starts and logs when they do not, and the Multiplayer Debugger shows what each tick sent each player.

```csharp
// Beside the session code above: add using System.Collections.Generic; and using Mu3Library.Multiplayer.Sync;
private const ushort SyncMessage = 3;
private StateSyncManager _sync;
private readonly List<TransformSync> _transforms = new List<TransformSync>();

// In Awake, after Initialize. Every player creates it with the same config.
_sync = new StateSyncManager(_manager, new StateSyncConfig(SyncMessage));

// Once the game starts, every player registers the same states under the same IDs.
_manager.OnGameStarted += startData =>
{
    _transforms.Add(new TransformSync(1, _boss.transform));
    _sync.Register(_transforms[_transforms.Count - 1]); // the host sends it
    foreach (Participant participant in _manager.Participants)
    {
        // An ID every player gives this player's character, such as its place in the start data.
        TransformSync character = new TransformSync(CharacterIdOf(participant.Id), CharacterOf(participant.Id));
        _transforms.Add(character);
        _sync.Register(character, participant.Id); // its player sends it, and the host sends it on
    }
};

// When the game ends, every player unregisters them, so the next game registers its own.
_manager.OnReturnedToLobby += ClearSyncedStates;
_manager.OnStateChanged += change =>
{
    if (change.Current == SessionState.Offline)
    {
        ClearSyncedStates();
    }
};

// In Update, after _manager.Update(): send this tick's changes, and move the copies.
_sync.Update();
foreach (TransformSync synced in _transforms)
{
    synced.Update();
}

// In OnDestroy, before _manager.Dispose().
_sync.Dispose();

private void ClearSyncedStates()
{
    foreach (TransformSync synced in _transforms)
    {
        _sync.Unregister(synced.Id);
    }

    _transforms.Clear();
}
```
- `IMultiplayerManagerEventBus` lists every event, and the XML comments of `IMultiplayerManager` and `IMultiplayerMessenger` describe each call; in the editor, **Mu3Library > Windows > Multiplayer Debugger** shows the running sessions in play mode.

#### Session Saves
`SessionSaveManager` (`Mu3Library.SessionSave`) saves a session through a `SaveManager` on the host, and lets the host send the save to another player, who can host the session from it later. The sections registered with the `SaveManager` hold what the whole session shares, such as the world; each `PlayerSaveSection<TData>`, or one from `PlayerSaveSection.Create`, is saved once for every player of the session as `player.<PlayerId>.<key>`, so a player's data stays theirs whoever hosts. Code in an assembly definition of its own references `Mu3Library.SessionSave`, `Mu3Library.Save`, and `Mu3Library.Multiplayer`.

```csharp
using System;
using System.IO;
using Mu3Library.Save;
using Mu3Library.SessionSave;
using UnityEngine;

// Every player creates it the same way, with the same message type; the share takes it and the next one.
var saves = new SaveManager(new FileSaveStorage(Path.Combine(Application.persistentDataPath, "SessionSaves")));
saves.RegisterSection(SaveSection.Create("world", () => _world, data => _world = data));

var session = new SessionSaveManager(_manager, saves, messageType: 900);
session.RegisterPlayerSection(PlayerSaveSection.Create<InventoryData>("inventory",
    player => _inventories[player],
    (player, data) => _inventories[player] = data,
    restoreDefault: player => _inventories[player] = new InventoryData()));

// The host, at a point the game chooses; Update every frame paces a share.
session.Save("coop-1", sessionName: "Forest Run");
session.Load("coop-1");                          // before StartGame
session.Share("coop-1", friendId, out uint shareId);

// The player the host shares with.
// AcceptShare replaces a slot of that ID, so the save takes a new one.
session.OnShareOffered += offer => session.AcceptShare(offer.ShareId, $"shared-{Guid.NewGuid():N}");
session.OnShareCompleted += transfer => Debug.Log($"Stored {transfer.SlotId}");
```

- **Players**: Only the host saves and loads. `Save` writes every player of the session, those whose slot the host keeps while they are away included, and a player the slot holds who is not in the session keeps their sections in it. `Load` gives each player of the session their sections, and a player the slot does not hold, such as one who joins the saved session for the first time, starts from `RestoreDefault`. `LoadPlayer` loads one player, such as one who joins a game already under way. A player section key takes up to 36 characters, and no other section's key may start with `player.`.
- **Origin**: The slot's metadata names the host who last saved it and the session name it was saved with, which `TryGetSessionInfo` reads with the players the slot holds. A save received from another player keeps those, so it shows where it came from until the player saves it as host.
- **Share**: `Share` offers a saved slot to another player of the session; their game answers `OnShareOffered` with `AcceptShare`, naming the slot to store it as, or `DeclineShare`. `AcceptShare` replaces a slot of that ID, so name one that none of the player's own saves uses, such as a new GUID, rather than the host's `SourceSlotId` or its `ShareId`, which each host counts from 1 again whenever it starts. The host then sends the save as reliable messages of at most `ShareChunkSize` bytes (16 KiB by default) at `ShareBytesPerSecond` (128 KiB a second by default), since the host's own sends pass no rate limit of the session and the share must leave room for the session's other messages; the player's two answers count toward the session's rate limits like any other message. The receiving player refuses a save larger than its `SaveManager.MaxSlotSize` and checks the whole save with the slot's CRC-32 before it stores it, so damaged bytes are never stored. `OnShareProgress` reports the bytes sent and received. Every share that `Share` started on the host, or that `OnShareOffered` reported on the receiving player, ends there with `OnShareCompleted` or `OnShareFailed` and a `SaveShareFailureReason`, such as `Declined`, `Corrupted`, `Timeout` (no answer within `ShareTimeoutSeconds`, 60 by default), `PlayerLeft`, or `SessionEnded`; an offer the receiving player turns down by itself, because it is too large (`TooLarge`) or another share runs (`Busy`), raises nothing there, and the host hears why.

## 🧩 Inspector Attributes

Apply `ButtonInvokeAttribute` to a parameterless instance method that returns `void`. Its label and height are optional; an omitted label is displayed as `Invoke {method name}`. Buttons are appended after the default serialized properties by the fallback Inspector, so source declaration order cannot position them among fields. A type with its own custom Inspector must render its `ButtonInvoke` buttons there.

```csharp
[ButtonInvoke("Refresh Data", ButtonHeight = 36f)]
private void RefreshData()
{
}

[ButtonInvoke]
private void ResetData()
{
    // Inspector label: Invoke ResetData
}
```

The fallback Inspector is registered with `isFallback` for every `MonoBehaviour` and `ScriptableObject`, so once Base is installed it draws every such type that has no custom editor of its own, whether or not the type uses `ButtonInvoke`. It builds that Inspector with UI Toolkit through `CreateInspectorGUI`: Unity's default inspector, then the buttons. Property drawers that implement only `CreatePropertyGUI` and IMGUI property drawers therefore render as they do in Unity's own default inspector, multi-object editing works, and a button runs its method on every selected object. A custom editor can derive from `ButtonInvokeEditorBase` to get the same default inspector and buttons; if it overrides `OnInspectorGUI`, the Inspector keeps calling that IMGUI method instead. A tool that draws an editor through IMGUI by calling `OnInspectorGUI` directly gets the IMGUI version, where a drawer that implements only `CreatePropertyGUI` shows "No GUI Implemented".

  - **Writing a backend**: A backend for another platform implements `IMultiplayerBackend` from `Mu3Library.Multiplayer.Backend`, and may also implement two optional interfaces that the manager looks for: `ILobbyInviteBackend`, when its lobbies that are not public let a player in only by invite, so the host invites back a player who returns to a kept slot, and `IUnavailableReasonBackend`, to name why the backend is not available, as the Steam backend names `SteamNotRunning`. A third, `IVoiceBackend`, which the game uses itself, records and decodes voice. `LobbyDataKeys` lists the lobby data keys that the manager reserves under the `mu3.` prefix and writes in every lobby it creates; a backend stores them like any other lobby data and may read them. A backend that starts a search after `SearchLobbies` returns keeps a copy of the query from `LobbySearchQuery.Clone()`
- **ObjectPool**: Queue-based object pooling with duplicate inactive enqueue protection, batch `List<T>` enqueue and count- or argument-list-based `List<T>` dequeue support, optional no-argument creation callbacks, typed `CreateArguments` initialization callbacks, and `Clear()` cleanup
- **Observable**: Data change detection system
- **Preference**: PlayerPrefs wrapper
- **Resource**: Resources folder loading
- **Save**: Section-based saves into slots, with data versions and migration, a checked slot format, and file or in-memory storage, in the `Mu3Library.Save` assembly
- **SessionSave**: A multiplayer session's save on the host, with each player's sections under their ID, players who join or stay away handled, and its paced, checked share to another player who can host from it, in the `Mu3Library.SessionSave` assembly
- **States**: `StateMachine<TKey>` with `State` and, with UniTask, `AsyncState`: transitions that exit and then enter, waiting for routines or async methods, requests queued in order, guards, and `Back`
- **Scene**: Scene loading abstraction with phase/status queries, lifecycle/progress callbacks, one-shot lifecycle subscription helpers, and unified rejection events
- **UI**: MVP pattern implementation, the `UIAreaGrid`/`UIAreaElement` helper that anchors children to one of nine areas with per-axis uniform or independent cut lines, and the `SafeCanvas`/`SafeRect` pair that keeps a canvas inside the screen safe area
- **IS**: Moved to the separate Input System package ([README](packages/inputsystem/README.md))
- **Utility**: Singleton, EasingFunctions, Settings, `Mu3Library.Utility.WorldSpaceBackground` for fitting a `SpriteRenderer` background to a camera viewport, and `Mu3Library.Utility.ScreenChangeNotifier` for following a screen that changed its size or its safe area while the game runs, without a per frame check of your own
- **WebRequest**: HTTP request management

## 🧱 URP and Watermelon Game Packages

The main features of the URP and Watermelon Game packages are listed under their packages below:

URP package (**Mu3 Library URP**):
- **Camera Stack Helper**: `Mu3Library.URP.Cam.CameraStackSetter` adds `SetCameraStackToMain(...)` and `SetCameraStack(...)` helpers so any URP overlay camera can be inserted into `Camera.main` or an explicit root camera stack with optional insertion index control

Watermelon Game package (**Mu3 Library Game - Watermelon**):
- **Fruit item indexes**: The board configuration always contains 11 fruit entries, addressed by zero-based list index
- **Item contact area**: The board-relative resize sizes the item collider, so an item index keeps the same contact area in every `BoardConfig`; `BoardItemInfo.ColliderScale` decides how much of the sprite that collider covers, `BoardItemInfo.ColliderOffset` moves it as a fraction of the collider diameter, and the sprite is drawn around the collider
- **Board fitting**: `BoardArea.Fit(...)` fits the board sprite inside the configured camera viewport padding
- **Board collision boundaries**: `BoardArea.SetOutColliders()` creates or updates left, right, and bottom `BoxCollider2D` boundaries from the item-area viewport padding while keeping the top open
- **Board-relative coordinate conversions**: `BoardArea` exposes world, screen, and local normalized-position conversions with initialization-safe `Try...` variants
- **Board input**: `InputHandler` reads the Input System while the package is installed and Active Input Handling enables its backend, and the Input Manager otherwise; a press over UI starts no drag, `InputHandler.DragStartFilter` holds a press back by a project's own rule, and a drag taken away before it is released is canceled with the held item kept in hand
- **Merge effects**: `BoardItemInfo` supports optional `ParticleHandler` resources for merge effects, with completed spawned effects cleaned up automatically
- **Scoring extension point**: Override `BoardItemScoreRule.GetScore(int)` to customize the default triangular score progression
- **Board commands**: `BoardController.EnqueueCommand(...)` takes commands into the board's public command queue. `IUpdatableBoardCommand` and `ICancelableBoardCommand` let a command run frame by frame and be canceled, and `BoardCommand` builds both on lifecycle hooks. `BoardController.CommandContext` is the narrow surface through which an external command reaches items, the score, and sounds, and the package carries Flow, Item, and Score commands, `MergingCommand` among them
- **Board sound volumes**: `BoardController.SfxVolume` and `BoardController.BgmVolume` control board playback independently from `BoardConfig.SoundConfig`; both clamp to 0–1

To stack an MVP render camera with the new helper, pass the render camera explicitly:

```csharp
using Mu3Library.URP.Cam;

CameraStackSetter.SetCameraStack(targetCamera, _mvpManager.RenderCamera);
```
