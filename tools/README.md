# Tools

Repository-local support tooling lives here. These tools can help agents inspect or verify the repository, but they do not own Unity package behavior.

| Path | Owns |
|---|---|
| [cli/](cli/README.md) | Python tools, one package and command each: `mu3-repo` for repository checks, `mu3-unity` for Unity diagnostics, compiles, and test runs, `mu3-di-strip-harness`, and `mu3-verify-build`; beside them the fixed load helper the shell entrypoints run, and `common`, the code the tools share, the project generator among it |
| [unity-projects/](unity-projects/) | The [project configs](#unity-project-configs) `minimal`, `full`, `urp`, and `watermelon`, from which the tools generate the Unity projects they compile, test, and build |
| [di-strip-harness/](di-strip-harness/) | The assets of the [DI stripping harness](#di-stripping-harness), which `mu3-di-strip-harness` copies into a mirror project, builds as a player, and runs |
| [verify-build/](verify-build/) | The build script of the [verification build](#verification-build), which `mu3-verify-build` adds to the project it generates from the `full` config |
| [dev/](dev/) | The scripts that enter the [development environment](#development-environment), which the root `.envrc` mirrors for direnv, `ensure_tools.py`, which both scripts run to keep the tools in `.venv` in step with `tools/cli`, and `env.local.example`, the template for personal variables |
| [../compile-unity.sh](../compile-unity.sh) | Git-change-aware Unity batchmode compilation of the projects generated from the configs |
| [../test-unity.sh](../test-unity.sh) | EditMode and PlayMode test runs through the Unity Test Framework, built on `compile-unity.sh`'s selection, Editor lookup, lock check, and project generation |

Generated files under `bin/`, `obj/`, `.venv/`, and `*.egg-info/` are local artifacts and should not be tracked.

Run `mu3-repo check` before sharing repository-level documentation or agent-framework changes. It replaces the former remote repository-hygiene workflow with its useful checks at the local tooling boundary.

## Fresh Clone Setup

A new clone or worktree holds only tracked files. Set it up in this order before the first Unity run:

1. Install the Unity Editor version that each `tools/unity-projects/*/ProjectSettings/ProjectVersion.txt` names through Unity Hub, and on Windows Git for Windows, whose bash runs the shell entrypoint.
2. Install Python 3.10 or later, which the shell entrypoints run to read the configs and generate the projects, then enter the [development environment](#development-environment), which installs the tools in `tools/cli` and their one dependency, `typer`, into `.venv` at the repository root on first use. `python -m pip install -e tools/cli` installs both without it. Every command below also runs without installing the tools, from the repository root with `PYTHONPATH=tools/cli/src python -m <package>` in place of the command, such as `python -m unity` for `mu3-unity`; [cli/README.md](cli/README.md#tools) lists each package and its command.
3. Set the user environment variable `MU3_WORK_ROOT` to a short folder outside the checkout, such as `D:/w`, once per machine. The shell entrypoints generate each project in the unit's work folder below it, `${MU3_WORK_ROOT}/Mu3Library_ForUnity/<unit>/<target>` ([Unity Project Configs](#unity-project-configs)), and stop before Unity starts when it is not set and no `--work-dir` is given.
4. Check the environment; every line should pass:

   ```bash
   PYTHONPATH=tools/cli/src python -m unity doctor
   ```

5. Compile and test: `./compile-unity.sh all`, then `./test-unity.sh all` and `./test-unity.sh all --platform playmode`. The first run of each project in a unit's work folder imports it from scratch and takes minutes; later runs there keep its `Library/`.

   Unity's asset import cannot read a file whose path has 260 characters or more, even with `LongPathsEnabled=1`, and the run still passes. A first import of the former development projects from `.claude/worktrees/<session>/.worktrees/<unit>` on 2026-11-08, with Unity 6000.6.7f1, could not read 49, 64, and 190 package files whose paths had 260 to 317 characters, among them `.uxml`, `.uss`, `.device`, shader, and template files in `Library/PackageCache` and `Unity.Collections.LowLevel.ILSupport.dll`, which the API updater reads; 32, 38, and 124 asset imports failed on them. No C# file was among them, and the compile and the EditMode tests passed. Unity did not import the failed files again on later runs of the same project, so a later log names fewer of them, or none.

   A generated project lies in the short work folder, so its `Library/PackageCache` stays below the limit when `MU3_WORK_ROOT` is short; the projects reference this checkout's own packages where they lie, and the longest of their files, 93 characters below the checkout, stays below it from a nested worktree too. On Windows both shell entrypoints still warn twice. Before Unity starts, they warn when the project folder has 98 characters or more: the longest path below a project folder that Unity could not read, `Library\PackageCache\com.unity.render-pipelines.core@13460d8ea9e5\Editor-PrivateShared\Tools\Converter\Window\RenderPipelineConverterVisualElementListFilter.uxml`, has 161 characters, so it reaches 260 there. After Unity exits, they warn with the number of files its log says it could not find at paths of 260 characters or more, the asset imports that failed on them, and each DLL among them. `test-unity.sh` gives both warnings again under the target in its summary, and `compile-unity.sh` repeats them once every target of a run of several has compiled; a failed compile ends the run at once, right after its own warnings and error. Neither warning fails the run, since the measured failures broke no compile and no test; a plugin whose failed import does break the compile fails the target through Unity's exit status, as any compile error does. With `MU3_WORK_ROOT` at `D:/w`, a project folder such as `D:/w/Mu3Library_ForUnity/<unit>/watermelon` has at most 68 characters, and 80 with the suffix of an `--editor-version`, such as `-6000.3.17f1`.

   A player build that builds Addressables content first reaches the limit from a shorter folder, and fails rather than warns. The Scriptable Build Pipeline writes files in `Library\BuildCache`, whose folder and file names are hashes of fixed length, and its managed code then opens them again, which it cannot do from 260 characters. On 2026-11-14, with Unity 6000.6.7f1, a Mono `StandaloneWindows64` player whose content build wrote a `CAB-<hash>.sharedAssets` file 138 characters below the project folder failed from project folders of 151 and 130 characters with `SBP ErrorException` and `BuildFailedException: Failed to build Addressables content, content not included in Player Build.`; from 110 characters the content and the player built, the longest file of that build's `Library\BuildCache` having 143 characters below the folder. With the content build off, the player built from 151 characters too (#445). `BuildPipeline.BuildPlayer` returned a report whose result was `Unknown`, not `Failed`, so a build script must treat every result but `Succeeded` as a failure. Neither shell entrypoint builds a player; [`mu3-verify-build`](#verification-build) does, and refuses a project folder of 98 characters or more.

## Worktree Removal

A checkout holds no links and no Unity project folders any more: the tools generate the projects, and link the samples into them, in the work folder outside the checkout. A worktree of a branch cut after #523 is removed with a plain `git worktree remove <worktree>`; its longest tracked path has 130 characters, so even a worktree nested in a session worktree stays below Windows' 260 characters. The unit's work folder outside the checkout holds the `full` project's junction into the checkout's `Samples~`; [Unity Project Configs](#unity-project-configs) says how to delete such a folder by hand.

A worktree of an older branch still holds the former development projects, whose `UnityProject_BuiltIn/Assets/Mu3LibrarySamples` may be a Git-ignored junction to Base's `Samples~` that an older `mu3-samples link` made, and whose Addressables settings hold files with paths of 261 to 269 characters from a nested worktree. Git for Windows stops at a junction with `error: failed to delete '<worktree>': Directory not empty` and deletes a long path only while `core.longpaths` is on, which `git worktree remove` takes from the checkout it runs in. Remove such a worktree from the main checkout with the setting given for that one command, after removing each link with `cmd /c rmdir "<link>"` from Command Prompt or PowerShell, or `cmd //c rmdir '<link>'` from Git Bash; without `/s`, `rmdir` removes a junction and leaves its target alone, while PowerShell's own `rmdir` is `Remove-Item`, which takes the target's files for the junction's own:

```bash
git -c core.longpaths=true worktree remove <worktree>
```

This changes no repository setting. Do not add `--force`, which skips the check that the worktree holds no unsaved changes.

If a removal has already left a folder behind, delete it with a tool that reaches paths of 260 characters or more, and only once nothing in it is a link. This command, run from outside the folder, prints every junction, symbolic link, or other reparse point in the folder and nothing when there is none; it does not descend into a link it prints:

```bash
python -c "import os, stat, sys; r = 2 * os.sep + '?' + os.sep + os.path.abspath(sys.argv[1]); [print(p[4:]) for d, ds, fs in os.walk(r) for n in ds + fs if os.lstat(p := os.path.join(d, n)).st_file_attributes & stat.FILE_ATTRIBUTE_REPARSE_POINT and not (n in ds and ds.remove(n))]" <folder>
```

Remove each path it prints with `rmdir` as above, and run it again. Once it prints nothing, delete the folder:

```bash
python -c "import os, shutil, sys; shutil.rmtree(2 * os.sep + '?' + os.sep + os.path.abspath(sys.argv[1]))" <folder>
```

Both commands put the `\\?\` prefix before the folder's absolute path, which lets Windows reach paths of 260 characters or more, and both run alike from Git Bash and PowerShell. On 2026-11-14, with Git 2.41.0.windows.1 and Python 3.12.2, they found and removed a junction in a left folder of 179 files and then deleted the folder while the junction's target kept its file, and `git -c core.longpaths=true worktree remove` deleted worktrees at that depth with exit status 0 (#466).

## Development Environment

One command, run from the repository root, enters the repository's development environment in a terminal:

| Shell | Enter | Leave |
|---|---|---|
| PowerShell | `. .\tools\dev\activate.ps1` | `deactivate` |
| bash, including Git Bash | `source tools/dev/activate.sh` | `deactivate` |
| direnv | `direnv allow` once, then enter the repository folder | leave the folder |

Entering it:

- creates `.venv` at the repository root on first use, with `uv` when it is installed and `python -m venv` otherwise, and installs the tools in `tools/cli` into it in editable mode. Their commands act on this checkout wherever they run. Entering an existing `.venv` checks its tools against `tools/cli/pyproject.toml` with [dev/ensure_tools.py](dev/ensure_tools.py) and installs them again when they differ, such as in a `.venv` made before the tools were split into one command each (#485), which still holds the former `mu3-cli`, or before `mu3-verify-build` was added (#481); [cli/README.md](cli/README.md#environment-bootstrap) says what it compares (#504);
- activates that virtual environment, so its `python` and the tools' commands come first on `PATH`;
- sets every variable that `.env.local` at the repository root lists, such as those in [Environment](#environment), and `MU3_DEV_ROOT` to the repository root;
- in PowerShell on Windows, makes `bash` run the bash that the tools use, normally that of Git for Windows, putting its folder first on `PATH` when `bash` does not already find it, so `bash ./test-unity.sh` runs the bash the scripts are written for.

`deactivate` restores every variable and `PATH` as they were before. Entering it while another virtual environment is active leaves that one first. The `.envrc` does not create `.venv`; run one of the scripts once first. The PowerShell script needs an execution policy that runs local scripts, such as `RemoteSigned`.

`.env.local` is personal and Git-ignored; copy [dev/env.local.example](dev/env.local.example) to start one. It holds one `KEY=VALUE` per line. The three ways of entering parse it separately, so keep to the subset all of them read alike, which the example file lists. PowerShell has no `NAME=value command` form, so a variable that a bash example sets for one command belongs in `.env.local`, or in `$env:NAME = 'value'` for the current session.

## Unity Project Configs

The repository commits no Unity project. Each folder in [unity-projects/](unity-projects/) is a config from which the tools generate one, and each config is the target of the same name in `compile-unity.sh` and `test-unity.sh` (ADR 0001 D12, D15):

| Config | Packages | Optional SDKs | Notes |
|---|---|---|---|
| `minimal` | Base | none | Active input handling is the Input Manager, since the Input System package is absent |
| `full` | Addressables, Base, Input System, Localization, Notifications | UniTask, Steamworks.NET, Addressables (through the Addressables and Localization packages), Localization, Input System, Mobile Notifications | Input handling Both, `steam_appid.txt`, the Addressables settings, and Base's samples linked in |
| `urp` | Base, URP | Input System | Input handling Input System, the URP settings assets |
| `watermelon` | Base, URP, Watermelon Game | UniTask, Input System | Input handling Both, the URP settings assets, the Input Actions |

The define sets differ, so each package compiles and runs its tests under every config that names it. `minimal` and `urp` are the configs without UniTask, so only their runs reach the code paths that replace UniTask with coroutines, and `minimal` is the one that compiles Base without the Input System.

A config holds `Packages/manifest.json`, with `testables`, `ProjectSettings/`, and only the template files its project needs: `full`, `urp`, and `watermelon` started from the former development projects `UnityProject_BuiltIn`, `UnityProject_URP`, and `UnityProject_Game_WatermelonGame`, whose Editor versions they keep. In the manifest, a dependency whose value is `"checkout"` is the package of that name in this checkout: the generator finds it by the `name` in its `package.json` among the files Git tracks or would track, and writes the absolute path of its folder in its place, `file:<checkout>/<folder>`, so moving a package folder needs no config edit. `full`, `urp`, and `watermelon` keep their former `Packages/packages-lock.json`, which pins the commits of UniTask and Steamworks.NET that the manifests name by Git URL; it holds no entry for a checkout package, which Unity adds as it resolves the project, and `minimal`, which names no package by Git URL, has none. `full` also holds `sample-links.json`, which maps `Assets/Mu3LibrarySamples` to Base, whose `Samples~` the generator links there (a junction on Windows, a symbolic link elsewhere) so that the Multiplayer sample compiles; Unity skips a folder whose name ends in `~`, so the samples compile only through such a link.

`full` keeps the Addressables settings of the former `UnityProject_BuiltIn` that edit-mode Addressables needs: `Addressables.InitializeAsync` in the Editor loads the settings asset at `Assets/AddressableAssetsData/AddressableAssetSettings.asset` and, without it, falls back to a built `settings.json`, which a test project has not, and fails (source of Addressables 2.11.2, `AddressablesImpl.InitializeAsync`), so `AddressablesManagerTests`, which initialize Addressables, need it. The bundle deployment configuration is not carried over (ADR 0001 D17): the settings hold only the `Default` profile, the `Default Local Group`, which builds to `Local.BuildPath` and loads from `Local.LoadPath`, and no remote catalog. Nothing else needs a settings asset: `LocalizationManagerTests` make their own `LocalizationSettings`, and the Input System tests their own `InputActionAsset`.

A generated project lies in `<work-dir>/<target>`, and in `<work-dir>/<target>-<version>` with `--editor-version`, so that each Editor keeps its own `Library/`. `<work-dir>` is `--work-dir`, or `${MU3_WORK_ROOT}/Mu3Library_ForUnity/<unit>`, where `<unit>` is the first 32 characters of the current branch with slashes as dashes and without trailing dots ([overview.md](../.ai/project/wiki/overview.md) «Development Projects»); without either, or on a detached HEAD without `--work-dir`, the scripts stop before Unity starts and say what to set. Each run refreshes the project before Unity opens it: it writes each file of the config whose content differs, writes the manifest with the checkout packages' folders, removes each file that an earlier run wrote and the config no longer holds, and leaves everything else, `Library/`, `Logs/`, `UserSettings/`, and what Unity wrote, for the next run. The project's marker file, `.mu3-unity-project`, names the checkout the project was generated for and lists what the generator wrote; the generator writes into a folder only when it is new, empty, or holds that marker, and refuses a project whose `Temp/UnityLockfile` an Editor holds, since a refresh would change the files under it. Branches whose first 32 characters agree, such as two `claude/group-and-process-issues-<hash>` session branches, share a `<unit>`, so the generator also refuses a project whose marker names another checkout and asks for `--work-dir`; a marker without that line, which a run from before the line existed wrote, counts as this checkout's and gets the line. It removes a samples link the config no longer names, or one that points elsewhere, without following it, and `mu3-verify-build --fresh` removes the links before it deletes its project. To delete a generated project or a whole work folder by hand, mind that the `full` project holds a junction into the checkout's `packages/base/Samples~`: delete it with Git Bash's `rm -rf`, which removes a junction without following it (on 2026-11-15 the target of a junction in a deleted folder kept its file), or remove the link first with `cmd /c rmdir`, and never with Windows PowerShell 5.1's `Remove-Item -Recurse`, which takes the target's files for the junction's own. The generator is [cli/src/common/unity_projects.py](cli/src/common/unity_projects.py), which the shell entrypoints run by its path; a dry run only reads the configs and creates nothing.

## Unity Compile Entrypoint

The default command compiles the projects selected from staged, unstaged, and untracked Git changes:

```bash
./compile-unity.sh --dry-run
./compile-unity.sh
```

A changed package selects every config whose `Packages/manifest.json` names it as `"checkout"`, since each config installs different optional packages and so compiles the shared sources with a different define set: a `packages/base` change selects `full`, `minimal`, `urp`, and `watermelon`, a `packages/addressables`, `packages/inputsystem`, `packages/localization`, or `packages/notifications` change `full`, a `packages/urp` change `urp` and `watermelon`, and a `packages/game/watermelon` change `watermelon`. A change inside `tools/unity-projects/<config>/` selects that config.

Package Markdown, licenses, `Documentation~`, and other repository tooling changes do not trigger Unity compilation.

Each target compiles in the project generated from its config ([Unity Project Configs](#unity-project-configs)); `--dry-run` prints, for each selected target, the project folder it would generate or refresh, and creates nothing. A project counts as open while a process holds its `Temp/UnityLockfile`, and an open project stops the run before any Unity starts. An Editor that crashed leaves that file behind with no holder; the script reports it as stale and compiles the project anyway, and `mu3-unity doctor` reports it apart from an open project. PowerShell checks the holder on Windows and `lsof` does elsewhere; on a host with neither, an existing lock file stops the target.

The script prints Unity's log as Unity writes it and keeps it in `log/unity-compile/<target>.log`, which is Git-ignored. When the log has not grown for `--stall-timeout <seconds>`, 300 by default, the script stops Unity and its child processes and fails the target, so a compile that waits on something batch mode never answers, such as a dialog, cannot hold the run; `--stall-timeout 0` waits as long as Unity runs. The script looks at the log every second and times a silence to the microsecond with bash 5, the bash of Git for Windows; an older bash, such as the 3.2 that macOS ships, counts only whole seconds, so there the script waits up to a second longer. Either way it never stops Unity before the log has stood still for the whole timeout. Like any failed compile, a stalled one ends the run before the remaining targets. The default is about 12 times the longest silence measured in a first import. On 2026-11-01, cold runs of the former development projects in new mirrors and one with `--editor-version 6000.3.17f1`, while up to six other Unity batch processes ran, each took 80 to 128 s; their logs stood still longest while Unity resolved the packages (up to 14 s) and compiled the scripts (up to 25 s, in the run beside six other Unity processes). A slower machine, a larger code base, or a package download can stay silent longer, which the margin leaves room for.

Beside the log, each run keeps what Unity's Data Store service left of it, as a [test run](#unity-test-entrypoint) does, since a compile starts the service as a test run does and runs more often, so it gives more chances to catch a service that ends early (#420). The helper that watches the service records in `log/unity-compile/<target>.load` when each `Unity.DataStore.exe` of the run started and ended and its exit code, with the keys a test run's `.load` record gives them, and the counts of the other Unity processes, which a compile does not report. A run whose Unity log says `Launching Unity Data Store` keeps the project's `Logs/UDS-Service.log` as `log/unity-compile/<target>.uds-service.log`. The script removes both as a target starts, before its project is generated, and warns about one it cannot remove, such as one another program holds open, without stopping the compile; it judges neither: a service that ended during a compile neither fails the target nor warns. The helper runs with the `python` or `python3` of version 3.10 or later from `PATH` that the script needs anyway; when the helper file is missing, the script warns and keeps only the service's log.

Use a Git base when selecting committed changes, or keep the explicit targets for manual verification:

```bash
./compile-unity.sh changed --base origin/develop --dry-run
./compile-unity.sh full
./compile-unity.sh minimal
./compile-unity.sh urp
./compile-unity.sh watermelon
./compile-unity.sh all
./compile-unity.sh all --work-dir D:/w/scratch
```

A new package needs no change to the scripts: name it as `"checkout"` in the manifest of each config that should compile it, and under `testables` where its tests should run.

## Unity Test Entrypoint

`test-unity.sh` runs the EditMode tests, or with `--platform playmode` the PlayMode tests, through the Unity Test Framework CLI and exits non-zero when a test fails or is inconclusive, Unity fails, or a run reports no result:

```bash
./test-unity.sh --dry-run
./test-unity.sh            # projects selected by Git changes, as compile-unity.sh selects them
./test-unity.sh full       # Base tests with every optional SDK
./test-unity.sh minimal    # Base tests without any optional SDK
./test-unity.sh urp        # Base and URP tests with the URP config's define set, which lacks UniTask
./test-unity.sh watermelon # Base and Watermelon Game tests with that config's define set
./test-unity.sh all
./test-unity.sh changed --platform playmode
./test-unity.sh urp --platform playmode
./test-unity.sh full --filter Mu3Library.Tests.MultiplayerPerformanceTests
./test-unity.sh full --filter Mu3Library.Tests.MultiplayerPerformanceTests --load-spinners 16 --repeat 3
```

It takes the same targets and options as `compile-unity.sh` and sources it for target selection, the Editor lookup, the lock check, and project generation, so it refuses a project an Editor has open as a compile does. A project runs only the tests of the packages its config's `Packages/manifest.json` lists under `testables`: `full` runs the Addressables, Base, Input System, and Localization tests, `minimal` the Base tests, `urp` the Base and URP tests, and `watermelon` the Base and Watermelon Game tests; a config that lists none is reported as skipped. `minimal` and `urp` are the configs without UniTask, so they are where the Base tests reach the code paths that replace UniTask with coroutines; `--platform playmode` runs the tests that need the player loop, among them a core's coroutine preparation. A failed test or Unity run does not stop the remaining targets, and a summary closes the run; a target that cannot start, such as a project an Editor has open or one that cannot be generated, stops the script at once. Each run writes NUnit XML to `log/unity-tests/<target>-<platform>.xml`, such as `urp-playmode.xml`, which is Git-ignored and removed before the run so an old result never stands in for a new one.

The summary gives each target the counts of the `<test-run>` element of its result file, as `<target>: <total> tests, <passed> passed, <failed> failed, <skipped> skipped, <inconclusive> inconclusive`, or `FAILED` and the reason. A test is inconclusive when an `Assume.That` in it does not hold or it calls `Assert.Inconclusive`. It reached no verdict, so it fails the target as a failed test does, and the summary names each one under its target as `inconclusive: <full name>`; the target's `error:` line is followed by the failed and the inconclusive tests. Each is named as the test names itself: the result file writes a name with XML references, such as `Case(&quot;a &amp; b&quot;)` for a test case that takes the string `a & b`, and the script replaces the predefined entities and the numeric character references, so that the name reads `Case("a & b")`, as the name of a test that stalled does. A control character in a name is printed as an escape, so that each line that names a test stays one line: the `failed:` lines after a target's `error:` line; the `inconclusive:` lines there and in the summary; the `environment:` and `warning:` lines about the Data Store service below, under the run and in the summary; `while running <test>` in the `error:` line and the summary entry of a run that stalled or wrote no results; the `failed in` and `inconclusive in` lines of the `--repeat` totals in the summary; and the `counted repeat:` lines under a run and the `counted repeat in` lines of the `--repeat` totals, in the summary, which [Fixed Load and Repeated Runs](#fixed-load-and-repeated-runs) describes. A tab, a line break, and a carriage return are printed as `\t`, `\n`, and `\r`, and every other control character, U+0001 to U+001F and U+007F to U+009F, the line and paragraph separators U+2028 and U+2029, and the noncharacters U+FFFE and U+FFFF, as `\u` and four lowercase hexadecimal digits, such as `\u001b` and `\ufffe`, the form in which NUnit's XML writes a character that XML cannot hold, so a name with U+FFFE, which Unity's log writes as the character, is printed alike in the `failed:` and the `environment:` lines (#493); a test case named `Case("a<line break>b")` is printed as `Case("a\nb")`. A backslash stays as it is, as in the `\\` and `\n` that NUnit writes for a backslash and a line break in a string that a test case takes, so a name without a control character is printed as the result file gives it, and a printed `\n` may also stand for a backslash and an `n`. The script compares and counts the names themselves, so only what it prints changes. It reads the names in UTF-8, as Unity's log and the result file write them; in a locale whose encoding is not UTF-8, such as `ja_JP.SJIS`, it runs in the C locale, which reads them byte for byte, since bash, grep, and awk there drop or fail to match the bytes of a name outside ASCII (#494). The C locale holds for the whole run: the path-length check of `compile-unity.sh` then counts a path's bytes, so it may warn about a path outside ASCII that is still below the limit, and Unity, git, and the helper inherit it, which on Windows changes nothing they read, while on macOS and Linux the Editor's culture follows it. The Unity Test Framework itself exits with 2 for an inconclusive test, as for a failed one. A warning instead would let a run pass with a test that checked nothing: `Mu3Library.Tests.MultiplayerLocalMachineTests.Directory_ReadWhoseThreadIsHeldUpPastTheWait_FindsAReplacementThatFinishedInTime_AndLooksOnceAtTheOthers` gives up its verdict when its thread is held up past the read's wait, so under load its target fails and is run again with less. A test that cannot run on a machine, such as one that needs a signed-in Steam client or a network address besides loopback, calls `Assert.Ignore`, which NUnit counts as skipped. The `Assume` calls in `MultiplayerSteamTests` hold unless Steam still runs in the Unity process; Steam starts there only through a Steam backend, which stops it when disposed, so in a command-line run they fail only after an earlier test left one running.

A run in which Unity's Data Store service ended is told apart from one whose tests failed. Unity 6000.6.7f1 serves the Editor the files it imported through `Unity.DataStore.exe`, which it starts as it opens the project and stops as it exits. When that process has ended before the Editor, the Editor logs `Unity Data Store service (pid <n>) is no longer running. Artifacts will be read in process for the rest of this session, and the service will not be restarted.` as an error, once, as it next reads such a file, and from then on reads them in its own process. The Unity Test Framework fails the test then running on that error, whatever the test checks. The script reads the process ID, that test, and the error from Unity's log, passing over the line that ends a test, whose failure message can quote the error. It then finds that test among the failed tests of the result file by its name, read as for the `failed:` lines, with the predefined entities and the numeric character references replaced, and reads its failure message. Only a message that holds the error and nothing else counts, in either form such a failure takes, each perhaps after `TearDown : `: the Unity Test Framework's `Unhandled log message: '[Error] <error>'. Use UnityEngine.TestTools.LogAssert.Expect`, and the `Unhandled log message: [Error] <error>` line that the TearDown of `Mu3WindowTests` writes, followed by `Stack trace of the first:` and the error's stack trace. For such a test it adds `environment: Unity's Data Store service (pid <n>) ended while <test> ran, …; run the target again` under the run, after the `error:` line and in the summary; when that was the run's one failure, its counts end with `; its one failure came from the environment`, and the script's closing `error:` line says how many runs failed only on the environment. With `--repeat`, the totals add in how many runs the service ended and how many of them failed on that alone. In every other case the line is a `warning:`, and the run keeps its verdict and its failures: when the service ends between tests, when the test then running passes, and when its message shows a failure of its own, such as an assertion, another log, or a second failure that the TearDown adds after the stack trace. A test that lets failing logs pass with `LogAssert.ignoreFailingMessages`, as `AddressablesManagerTests` and `SceneLoaderAddressablesTests` do, does not fail on the error, so a failure it has meanwhile is its own. Unity's log writes the name as a JSON string, whose escapes the script replaces by JSON's rules, `\uXXXX` and a surrogate pair of them included, and writes the characters in UTF-8 as for the result file, so that a name with a line break, which the log writes as `\n` and the result file as `&#xA;`, matches; the name of a test that stalled is read the same way. The log and the result file differ in a character that XML cannot hold, U+0001 to U+0008, U+000B, U+000C, U+000E to U+001F, U+FFFE, and U+FFFF: NUnit writes it into the result file as the text `\u` and four lowercase hexadecimal digits, such as `\u001b` for an escape, and the log writes it as itself or as a JSON escape such as `\u001B`. NUnit writes a backslash as it is, so the result file writes an escape and the text `\u001b` alike, which the log tells apart as `\u001B` and `\\u001b`. The script therefore writes such a character of the log's name in the result file's form before it compares the two, rather than replacing the result file's `\u` text, which would read the text `\u001b` in a name as an escape; of two failed tests whose names the result file writes alike, it reads the first. Unity 6000.6.7f1 and `com.unity.ext.nunit` 2.1.0 wrote the names so on 2026-11-15 (#476). The log cuts a name at U+0000 and writes half a surrogate pair as U+FFFD, with the character after a high surrogate gone too, while the result file writes `\u0000`, `\ud800`, and `\udc00`, so such a name matches no test there, and the line is then a warning too.

Such a run still fails, for the reason an inconclusive test fails it: the test reached no verdict, and a pass would count it as one that passed. The tests do not let the error pass either. The Unity Test Framework fails a test on the first failing log it did not expect and names only that one, so a test that passed apart from it could hide a second error; and the framework has no setting that lets one message pass in every test, so each test that reads an imported file would have to expect it. The script does not run the target again by itself, since that starts Unity anew and repeats every test.

In the 36 runs that followed from a 143-character project path with no other Unity process, 30 of `--filter Mu3Library.Tests.Mu3WindowTests` and 6 of the whole `built-in` suite, a sampler that looked every 0.25 s and held each `Unity.DataStore.exe` open to read its exit code saw every service exit with 0 between 0.8 and 3.3 s before its Editor, and every `UDS-Service.log` end with `Shut down UDS service system complete`.

So that a service that ends again leaves what its cause can be read from (#407), the helper that counts the other Unity processes ([below](#fixed-load-and-repeated-runs)) also watches the `Unity.DataStore.exe` that descends from the script, the run's own. Every 0.25 s, after it has read Unity's log, so that a look holds up neither the start nor the stop of the load, it lists the processes until it finds the service, and from then on only asks the service, which it holds open, whether it has ended, since the Editor starts one and does not start it again. The run's `.load` record lists the services' process IDs as `data_store_pids` and gives each one's start, end, and exit code as `data_store_<pid>_started`, `data_store_<pid>_ended`, and `data_store_<pid>_exit_code`, the times local to the millisecond with their offset from UTC, as Windows dates them, and as `data_store_<pid>_error` why one could not be opened, whose end and exit code then stay empty. A run whose Unity log says it launched the service, with `Launching Unity Data Store`, keeps the log the service wrote in the project, `Logs/UDS-Service.log`, beside its results as `<target>-<platform>.uds-service.log`; a [compile](#unity-compile-entrypoint) keeps both the record and the log too. It keeps one for every such run, not only for those in which the service ended early, since Unity logs the end only as it next reads an imported file, so an end late in a run may never reach its log, and a run whose service ended with its Editor gives the log to compare with; each such log that the development projects held on 2026-11-12 was under 1 KB. A project in which the run did not launch the service holds an earlier run's log, which is left out. Under the `environment:` or `warning:` line, the summary then gives `data store service: pid <n> exited with code <code> at <time>; its log is kept as …`, or says what the record lacks. A service that lives less than one look can go unseen. On other hosts a process that is not the helper's child gives neither its start nor its exit code, so both stay empty and the look that finds it gone dates its end; only Windows has run this. On 2026-11-12 the helper, given the process ID of another worktree's Unity 6000.6.7f1 batch run as its root, recorded that run's service as started at 22:08:00.996, within the second Windows lists as its creation time, and as ended at 22:09:39.560 with exit code 0.

`--filter <pattern>` runs only the tests whose full name matches the pattern, which the script passes to the Unity Test Framework as `-testFilter`: a regular expression, such as the full name of a test, a fixture, or a namespace, or several separated by `;`. It also runs the `[Explicit]` tests it matches, which a run without it reports as skipped; the benchmark `Mu3Library.Tests.MultiplayerPerformanceTests` runs this way, as in the last example above. A filtered run takes the same lock check and project as a full one and writes the same result file, and a target where no test matches the pattern fails. A pattern may not start with `-`, which would read as an option, or `/`, which Git Bash rewrites as a file path; the script keeps Git Bash from rewriting the rest of it.

Beside each result file the script keeps Unity's log, such as `log/unity-tests/urp-editmode.log`, while it prints the log as Unity writes it. The `Results:` line that closes its output names what each run keeps: the result file, Unity's log, the [helper's record](#fixed-load-and-repeated-runs) as `.load` when the helper can run, and the Data Store service's log above as `.uds-service.log`. It starts Unity with `-automated`, which makes the Unity Test Framework log a `##utp:` line as each test begins and ends. When the log has not grown for `--stall-timeout <seconds>`, 600 by default, the script stops Unity and its child processes and fails the target with the name of the test that began and did not end; `--stall-timeout 0` waits as long as Unity runs. It times the silence as a [compile](#unity-compile-entrypoint) does. A run that ends without results names that test too. The NUnit `[Timeout]` attribute cannot take this role: the Unity Test Framework checks it only after a test method returns, so a test that never returns runs past it.

### Fixed Load and Repeated Runs

`--load-spinners <n>` puts each run under a fixed load, so that two versions of a timing-sensitive test can be compared under the same one: *n* Python processes that each spin a CPU core, from the first test of the run to its last, so that they slow neither the compile and the project load before the tests nor Unity's shutdown after them. A helper, [cli/src/fixed_load/fixed_load.py](cli/src/fixed_load/fixed_load.py), starts them waiting before Unity starts and reads Unity's log every 0.05 s. It lets them spin once the log holds the `##utp:` line of the first test's start, and stops them once every test that the run's `TestPlan` line names has ended, or else when Unity exits; a test that the Unity Test Framework runs again, under `[Retry]`, `[Repeat]`, or `-repeat`, ends once each time, so the helper goes by the tests' names, not by how many ends it has read. The summary gives how many milliseconds after the first test began the load started, by the time that test's line gives, and whether it lasted until the last test ended or until Unity exited. A test shorter than one look can end before the load starts; the summary then says after how many tests it started. A run under which no test ran with the load fails, since none of its timings were measured under it: the run ended before the helper saw its first test begin, or every test had ended by then. The script stops the helper as a run ends, as it fails or is interrupted too, and the helper stops the spinners; a spinner also ends by itself once the helper ends, however it ends, since its input then closes, and the helper ends once the script does, so no spinner outlives its run.

On Windows a kill that the script cannot trap, such as `taskkill /F`, can still leave one `bash.exe` behind when it lands while Git Bash forks (#438). The forked child, whose command line is the script's and which Git Bash's `ps` does not list, keeps the script's output open, such as a file it was redirected to, and waits about 300 s for the fork to finish. It then writes `*** fatal error in forked process - WFSO timed out after longjmp` to that output, leaves `bash.EXE.stackdump` in its working directory, the folder the script was started from, which need not be the repository root, and ends (#454). `.gitignore` ignores that file as `*.stackdump` in any folder of the repository; a run started from a folder outside the repository leaves it there, out of the reach of that rule. The other new `bash.exe` processes that appeared under the script as a kill landed, its children and their children, ended by themselves: the 34 that #454's runs timed, counted as those found in a snapshot just after the kill and not in one just before it, within 0.7 s, some after writing `*** fatal error in forked process - couldn't create signal pipe, Win32 error 5` to the output, and none left a dump.

`--repeat <n>` runs each selected target *n* times, each run in a Unity of its own, and keeps each run's results as `<target>-<platform>-run<k>.xml`, `.log`, `.load`, and `.uds-service.log`, with *k* as wide as *n*, after removing those an earlier repeat left. A failed run does not stop the remaining ones. Each run has its summary entry, and the target's runs close with their totals: how many failed, the sums of the counts of the runs that wrote results, the number of runs in which each failed or inconclusive test had that result, the summed totals of each `[CountedRepeat]` test (below), and the fewest and most other Unity processes over all runs.

The script starts Unity anew for each run instead of repeating the tests in one Unity. In the Unity Test Framework that Unity 6000.6.7f1 bundles (1.8.0), both the `-repeat` command-line option and NUnit's `[Repeat]` attribute end a test's repeats at its first result that is not a success and report one result for them, so neither counts how many runs fail, which a timing measurement needs. A run of its own gives every test its own verdict in its own result file, with the framework's own fixture setup and the load's start the same in every run, for any filter, a whole fixture included. Each run pays for Unity's start, the project load, and the shutdown, about 19 s a run in the runs above, so `--repeat` suits up to some tens of runs; a failure rate over hundreds of runs of a test that lasts a fraction of a second needs the runs inside one Unity, which `[CountedRepeat]` gives.

`[CountedRepeat]`, an attribute of the Base EditMode tests in [CountedRepeatAttribute.cs](../packages/base/Tests/Editor/CountedRepeatAttribute.cs), runs an `[Explicit]` test in one Unity as many times as the environment variable `MU3LIBRARY_TEST_REPEAT` says, once without it, and goes on after a run that does not pass. It wraps the Unity Test Framework's own command for the fixture's setup and teardown, so each run is the framework's: the `[SetUp]` methods, base class first, the test's `ITestAction` attributes, the test with the framework's check for error logs it did not expect, and the `[TearDown]` methods, base class last, all in the one fixture instance the framework made. The test's timeout, 180 s by default, counts from each run's start, and each run's result is its own. Each run logs a line to Unity's log, `[Repeat] <full name>: run <k> of <n>: <result> in <ms> ms`, followed by `: <message>` when the result has one, with the message's lines joined by ` | `, and the last line gives the totals, `[Repeat] <full name>: totals: runs <ended> of <n>, passed <p>, failed <f>, inconclusive <i>, skipped <s>, failure rate <f / ended>%`; the result is NUnit's, such as `Passed`, `Failed`, `Failed:Error`, or `Inconclusive`. Each line, the one that starts the runs, `[Repeat] <full name>: start, runs <n> (<source>)`, included, writes the full name on one line, with a backslash as `\\`, a line break as `\n`, and a carriage return as `\r`, the escapes of a JSON string, since Unity's log ends a line at a line break in a message (#492); every other character stays as it is. So the log shows the test case that NUnit names `Case("C:\\Temp")` as `Case("C:\\\\Temp")`, as the `##utp:` lines do. The test fails when a run failed, with the totals and the first failure as its message, is cancelled when the run of the tests stopped before its last run, is inconclusive when a run was and none failed, and is skipped when every run was. As an invalid test it refuses a test that is not `[Explicit]`, so that the default run never runs it, a fixture with `[UnitySetUp]` or `[UnityTearDown]` and a test with an `IOuterUnityTestAction` attribute on its method or on a class above it, which the framework calls outside it, once around all the runs, a fixture with a `[SetUp]` or `[TearDown]` that returns a `Task`, which the framework waits for over several frames while each run takes one call, in which a task that continues on Unity's main thread never ends (#442), and a value of the variable that is not a whole number from 1; the framework refuses it on a `[UnityTest]`. `CountedRepeatAttributeTests` checks each of these refusals, on fixtures that the run does not load, but the one for the variable's value, whose reading `CountedRepeatByNameTests` checks through `ParseRuns`: a test that is not `[Explicit]`; a `[UnitySetUp]`, a `[UnityTearDown]`, and an inherited `[UnitySetUp]`; an `IOuterUnityTestAction` on the method, on the fixture class, on its base class, and on a set-up fixture above the fixture; and a `[SetUp]`, a `[TearDown]`, and an inherited `[SetUp]` that return a `Task`. It also runs, three times each, a test that is `[Explicit]` and a test under a fixture that is, both of which the attribute accepts, and checks that each run calls the wrapped command and that those runs' lines go to a list that the test passes to the attribute, none to Unity's log, so that a default run's summary gives no counted repeat (#472). It runs a third test three times, one whose full name holds a line break, a carriage return, and the text `\n`, and checks that each line names it in the one-line form, and checks that form for names with a backslash, a quote, and a tab, which stays as it is (#492).

The runner [below](#repeating-a-test-by-name) repeats a test by its name alone. To repeat a test with the attribute, call it from an `[Explicit]` `[Test]` of the same fixture that carries the attribute, and copy any attribute of the test that changes how it runs, such as `[Timeout]`. Do not start that test's name with the name of the test it repeats: the filter is a regular expression that matches anywhere in a full name, so a filter that names the repeated test by its full name would select the repeating test too. `MultiplayerLocalMachineTests.Repeated_SearchAndJoin_ThatMeetAReplacement` repeats `SearchAndJoin_ThatMeetAReplacement_FindTheLobby_WithoutHoldingAnUpdate` this way. Run it by name, with the load or without it; the summary gives its totals, and the line of each run stays in the run's Unity log, with `--repeat` in each `-run<k>.log`:

```bash
MU3LIBRARY_TEST_REPEAT=400 ./test-unity.sh full --filter Mu3Library.Tests.MultiplayerLocalMachineTests.Repeated_SearchAndJoin_ThatMeetAReplacement
MU3LIBRARY_TEST_REPEAT=1000 ./test-unity.sh full --filter Mu3Library.Tests.MultiplayerLocalMachineTests.Repeated_SearchAndJoin_ThatMeetAReplacement --load-spinners 16
grep '^\[Repeat\]' log/unity-tests/full-editmode.log
```

The script passes its environment to Unity. A run's counts take the repeating test as one test, so under the run the summary gives the totals line the attribute logged for each such test, read from the run's Unity log, as `counted repeat: <full name>: runs <ended> of <n>, passed <p>, failed <f>, inconclusive <i>, skipped <s>, failure rate <rate>`; a run whose log holds no totals line, such as one that stopped before the attribute logged it, gives none. With `--repeat`, the target's totals add `counted repeat in <k> of <runs> runs: <full name>: …`, which sums each count over the *k* runs whose log gave that test's totals, and the failure rate of the sums, the failed runs over the ended ones, to two decimals with a half rounded up. Both lines print the name with its control characters escaped, as the `failed:` lines do, while the totals add up by the name itself, so two tests whose names print alike, such as one with a tab and one with the text `\t`, keep totals of their own. The script reads the name back from the attribute's one-line form, replacing its escapes as it replaces those of the names in the `##utp:` lines; since the attribute doubles every backslash of the name, the name read back is the test's own, so a test whose name holds a line break gets its `counted repeat` lines, and one whose name holds the text `\n`, printed alike, keeps totals of its own (#492). NUnit writes a line break in a test case's string argument as `\n`, so such a name comes from elsewhere, such as a `TestName` that holds one. Until #492 the attribute logged the name as it is, and on 2026-11-15 the log of Unity 6000.6.7f1 ended a line, with CR LF as its other lines, at each line break of such a name, so a run with `TestName`s that held one gave no `counted repeat` line for `…Line<line break>Break` and read the totals of `…Misread<line break>[Repeat] y` as those of a test named `y`, while a carriage return without a line break stayed in its line; the run's counts and verdict, which come from its result file, were right. Under `--load-spinners` the load starts as that test begins and stops as it ends, so all its runs take place under the load, but for the first run's first milliseconds, before the helper sees the test begin.

On 2026-11-13, on the measurement PC with Unity 6000.6.7f1 and no other Unity process running, the second command above passed all 1000 runs in one Unity in about 5 minutes: the load started 18 ms after the test began and lasted 276.9 s, and a run, its setup and teardown included, took 232.0 to 467.9 ms, a median of 274.4 ms. Without the load, 200 runs passed at 264.8 to 310.0 ms, a median of 272.2 ms. Under `--repeat`, at about 19 s a run, the 1000 runs would have taken over five hours.

#### Repeating a Test by Name

`CountedRepeatRunner.RepeatTheNamedTest`, an `[Explicit]` test of the Base EditMode tests in [CountedRepeatRunner.cs](../packages/base/Tests/Editor/CountedRepeatRunner.cs), repeats the test whose full name, as the `fullname` attribute of the result file gives it, the environment variable `MU3LIBRARY_TEST_REPEAT_NAME` holds, as many times as `MU3LIBRARY_TEST_REPEAT` says, once without it, so that measuring a test's failure rate needs no repeating test written and compiled for it (#425). Run it by its own full name, which names no other test, with the load or without it:

```bash
MU3LIBRARY_TEST_REPEAT_NAME=Mu3Library.Tests.MultiplayerLocalMachineTests.SearchAndJoin_ThatMeetAReplacement_FindTheLobby_WithoutHoldingAnUpdate \
MU3LIBRARY_TEST_REPEAT=400 ./test-unity.sh full --filter Mu3Library.Tests.CountedRepeatRunner.RepeatTheNamedTest
```

It finds the test among all the EditMode tests of the project, which a run loads whatever its filter, has the Unity Test Framework build that test's command as for a run of it, and runs, each time, the part of the command that `[CountedRepeat]` wraps, so each run is the one the attribute gives: the `[SetUp]` methods, base class first, the test's actions, the test with the check for error logs, and the `[TearDown]` methods, base class last. The runs share one instance of the test's fixture, which the runner makes with NUnit's commands, as the framework does: the constructor, the `[OneTimeSetUp]` methods, base class first, and the fixture's suite actions before the first run, and the actions, the `[OneTimeTearDown]` methods, base class last, and `Dispose` after the last, each checked for error logs as the framework checks them. A one-time setup that fails runs nothing and fails the runner with `OneTimeSetUp: <message>`; a one-time teardown that fails fails it after the runs. The attributes of the test and its fixture that change the context, such as `[Timeout]`, apply to every run without being copied, and the timeout counts from each run's start; a `[Retry]`, `[Repeat]`, or `[MaxTime]` of the test acts within each run, as it does around one run of the test. The runner goes on after a run that does not pass, logs the lines of `[CountedRepeat]` under the full name of the test it repeats, not its own, so the summary gives that test's totals as `counted repeat: <full name>: …`, and ends with the result the attribute gives.

With `MU3LIBRARY_TEST_REPEAT_NAME` empty or unset, the runner runs nothing and reports itself as ignored, which the summary counts as skipped, with a message that asks for the name. A filter that matches it among other tests, such as `--filter Mu3Library.Tests` or `--filter Mu3Library.Tests.CountedRepeat`, selects it as it selects every `[Explicit]` test it matches, and such a run passes, as a test with `[CountedRepeat]` passes there after one run. Otherwise it refuses before any run, as an invalid test that fails the run, with a message that names the reason: a name that no test has, that more than one has, or that names a suite, such as a fixture or a method with test cases, each of which has a full name of its own; itself and a test with `[CountedRepeat]`; a test that the framework would not run, such as an ignored test or one under an ignored fixture; a test outside a fixture; a test that returns `IEnumerator`, as a `[UnityTest]` does, or a `Task`; a fixture that takes arguments, whose tests `[CountedRepeat]` can still repeat from an `[Explicit]` test of it; a fixture with `[UnitySetUp]`, `[UnityTearDown]`, `[UnityOneTimeSetUp]`, or `[UnityOneTimeTearDown]`, or with a `[SetUp]` or `[TearDown]` that returns a `Task`, and an `IOuterUnityTestAction` on the test or on a class above it, all of which the framework runs over several frames, while each run of the runner takes one call; an `ITestAction` that targets suites on the method of a test case, which the framework calls once around the method's cases; a `[PrebuildSetup]` or `[PostBuildCleanup]` on the test or its fixture, or a fixture that implements their interfaces, which the framework calls before and after a run only for the tests its filter selects; a `[SetUpFixture]` above the test that is not above the runner, which the run never sets up; and a value of `MU3LIBRARY_TEST_REPEAT` that the attribute refuses. An attribute of the test that throws as it changes the context, such as a `[SetCulture]` of a culture that does not exist, fails the runner before the first run, and the fixture is still torn down. For a test in another test assembly than the runner's, Base's EditMode tests, the suite actions and context changes that attributes of that assembly declare are neither made nor refused; the packages' test assemblies declare none. Nothing public in the Unity Test Framework builds a test's command or opens a log scope, so the runner reaches `TestCommandBuilder.BuildTestCommand`, the command type `EnumerableSetUpTearDownCommand` under which a run's command sits, and `LogScope` by reflection. It was written against version 1.8.0 of the framework, which Unity 6000.6.7f1 bundles, and under a version without them it refuses, naming what is missing. `CountedRepeatByNameTests` checks, on fixtures that it builds and the run does not load, the order of the calls with the fixture's suite and test actions, the lines, the timeout of the test and of its fixture class, the one-time setup and teardown, an attribute that throws on the context, the run without a name, and every refusal but the one for a missing internal, which needs another version of the framework. It sends the lines to a list instead of Unity's log, so that a default run's summary gives no counted repeat.

On 2026-11-14, with Unity 6000.6.7f1 and no other Unity process running, the command above with `MU3LIBRARY_TEST_REPEAT=40` and `Mu3Library.Tests.MultiplayerLocalMachineTests.Repeated_SearchAndJoin_ThatMeetAReplacement` added to the filter repeated the same test 40 times through the runner and 40 times through `[CountedRepeat]` in one Unity. All 80 runs passed, at 267.3 to 301.0 ms, a median of 272.0 ms, through the runner, and at 267.3 to 278.7 ms, a median of 272.2 ms, through the attribute, 10.9 s for each 40, and the summary gave a `counted repeat:` line under each name. Run with the name of a `[UnityTest]`, the runner failed as invalid with that message. With no name, `--filter Mu3Library.Tests.CountedRepeat` ran it and the 41 tests of `CountedRepeatByNameTests` and passed, the summary counting the runner as the one skipped test.

## Lowest Supported Editor

Each package declares the lowest Editor it supports in the `unity` field of its `package.json`, `6000.3` for every package, while the configs name a newer Editor. `--editor-version <version>` compiles or tests the selected targets with another Editor installed through Unity Hub, such as a 6000.3 release:

```bash
./compile-unity.sh all --editor-version 6000.3.17f1
./test-unity.sh all --editor-version 6000.3.17f1
```

Each target then runs in a project of its own, `<work-dir>/<target>-<version>`, so that neither Editor imports over the other's `Library/`. As the generator refreshes it, it retargets the project and prints each version it changed:

- `ProjectSettings/ProjectVersion.txt` names the requested version.
- `Packages/packages-lock.json` is left out, so Unity resolves the packages again.
- Each `com.unity.*` dependency that `Packages/manifest.json` pins to a version takes the version that Editor bundles: the one its own package manifest recommends, or else the version of its built-in copy. A built-in module the Editor does not ship, such as `com.unity.modules.tetgen` on 6000.3, is dropped. A package it does not bundle keeps its version, with a warning.

The check therefore compiles against the Unity packages a project on that Editor gets by default. Run it when a change touches code behind a `UNITY_6000_x_OR_NEWER` branch or an API that differs between Editor versions, changes a package's dependencies, or moves the declared floor. The first run of each such project imports it from scratch, so it takes minutes per target. `UNITY_EDITOR` still overrides the executable, with a warning when it is not the requested version.

The [DI stripping harness](#di-stripping-harness) takes the same `--editor-version` and retargets its own mirror by the same rule, so a player built with the floor Editor shows whether stripping keeps what the container needs there.

## DI Stripping Harness

The DI container reaches the constructors it calls and the `[Inject]` members it fills only through reflection, which the Unity linker cannot see, so a player built with Managed Stripping Level Medium or High keeps them only through the link.xml that Base's editor `DILinkerProcessor` writes for each build. The Editor and the EditMode and PlayMode tests never strip, so only a player shows a regression. `mu3-di-strip-harness` builds a Windows x64 player of a small mirror project, runs it, and prints one line per check:

```bash
PYTHONPATH=tools/cli/src python -m strip_harness --stripping High
PYTHONPATH=tools/cli/src python -m strip_harness --stripping Medium --backend il2cpp
PYTHONPATH=tools/cli/src python -m strip_harness --stripping High --with-unitask --work-dir "${MU3_WORK_ROOT:?set MU3_WORK_ROOT}/Mu3Library_ForUnity/<unit>/di-strip-harness"
PYTHONPATH=tools/cli/src python -m strip_harness --stripping Medium --editor-version 6000.3.17f1 --work-dir "${MU3_WORK_ROOT:?set MU3_WORK_ROOT}/Mu3Library_ForUnity/<unit>/di-strip-harness"
```

`--stripping` takes `Disabled`, `Minimal`, `Low`, `Medium`, or `High` (default `High`), and `--backend` takes `mono` (default) or `il2cpp`, which needs the Editor's Windows IL2CPP module and Visual Studio's C++ workload. Without `--with-unitask` cores prepare through the coroutine path, as in the `minimal` and `urp` projects; with it, through UniTask. The command runs only on Windows.

`--editor-version <version>` builds with another Editor installed through Unity Hub instead of the one the `minimal` config names, such as a 6000.3 release for the [lowest supported Editor](#lowest-supported-editor), where `DILinkerProcessor` finds the loaded assemblies through `AppDomain` instead of its `UNITY_6000_5_OR_NEWER` branch. That Editor gets its own mirror, `project-<version>/`, so each Editor keeps its own `Library/`, and the harness retargets it as `compile-unity.sh --editor-version` retargets its projects: `ProjectVersion.txt` names the version, each `com.unity.*` package pinned to a version takes the version that Editor bundles, a built-in module it does not ship is dropped, and any other package it does not bundle keeps its version with a warning. The command prints each change. `UNITY_EDITOR` still overrides the executable, with a warning when it is not where Unity Hub installs the requested version, since the mirror and the labels then name a version that does not build them. The Editor needs Windows Build Support (Mono), and Windows Build Support (IL2CPP) for `--backend il2cpp`.

[di-strip-harness/](di-strip-harness/) holds the mirror's assets. No game code in them creates a service with `new`; only the container does:

- `Assets/Harness/StripHarnessServices.cs`: the services, among them a class with a parameterless and a longer constructor, one whose only constructor takes parameters, one that takes the `ContainerScope` and registers the rest through it, a nested class, a class that only the player compiles, a class nothing uses, and a consumer with every kind of `[Inject]` member: private and base-class fields, auto and explicit properties, keys, another core, an optional missing one, `IEnumerable`, `Func`, `Lazy`, and `IObjectInjector`. Three more classes each declare one required `static` `[Inject]` member that no code reads or writes: a field, a property, and a field on a base class. A test of the tooling checks that their names appear nowhere else but in the messages the boot expects, since any reference would keep the member in the player without the link.xml. One more declares an instance `[Inject]` field that no code reads or writes, for a transient service whose constructor counts the injections; a test of the tooling checks that the field's name appears only in its declaration, since the linker keeps the `[Inject]` attribute of a field that code reads. Another declares an instance `[Inject]` auto-property with a private setter that no code reads or writes, for a transient service counted the same way; a test of the tooling checks that the property's name appears only in its declaration, since a call to its getter or setter would keep it in the player without the link.xml. For each of these five classes, and the base class, the tests also check that the class is named nowhere else but in its declaration, where the boot creates it, the message the boot expects, and, for the base class, the derived class's declaration, since reflection on the class, such as `typeof(...).GetField`, can keep its member too. These checks read every file under `Assets/` and `Plugin/`, the code a harness player is built from, and skip whole-line comments.
- `Assets/Harness/StripHarnessBoot.cs`: creates itself in an empty scene, creates two cores, runs the checks after ten frames, destroys the core to check `Dispose`, and quits with 0 only when every check passed and nothing logged an error or exception.
- `Assets/Domain/`: an assembly that does not reference `Mu3Library.DI`, whose classes `Assembly-CSharp` registers.
- `Plugin/HarnessPlugin.cs`: compiled with the Editor's own Mono compiler into `Assets/Plugins/HarnessPlugin.dll`, a precompiled assembly that does not reference `Mu3Library.DI` either.
- `Assets/Editor/StripHarnessBuild.cs`: the `-executeMethod` entry that sets the backend and the stripping level and builds the player.

The checks cover the core (its initialized and prepared events, an `[Inject]` field and a private-set property), registrations and constructors (the default constructor, the longest constructor, a `ContainerScope` parameter, a keyed registration without the `new()` constraint, a class with only a parameterized constructor, a factory with field injection, an instance with property injection), where a constructed class lives (the DI-free assembly, the precompiled DLL, a nested class, a player-only class), member injection (each kind of member above, and a player-only `[Preserve, Inject]` property), the required `static` members (injecting each of the three classes through `IObjectInjector` throws the exception that names its member, which the container finds only when the player kept the member), the instance `[Inject]` field that no code reads (injecting its class through `IObjectInjector` creates one service, which the container does only when the player kept the field's `[Inject]` attribute), the instance `[Inject]` auto-property that no code reads (injecting its class through `IObjectInjector` creates one service, which the container does only when the player kept the property, its setter, and its `[Inject]` attribute), and the lifecycle (`Initialize`, at least five `Update` and `LateUpdate` calls, and `Dispose`): 36 in all.

`--work-dir`, `log/di-strip-harness` by default, holds the mirror in `project/` (`project-<version>/` with `--editor-version`), the player in `players/<label>/`, and Unity's logs as `<label>-build.log` and `<label>-player.log`. The label is `<backend>-<level>`, followed by `-unitask` with `--with-unitask` and by `-<version>` with `--editor-version`, such as `mono-high-unitask` or `mono-medium-6000.3.17f1`. Each run brings the mirror up to date and keeps its `Library/`, so only the first run imports it from scratch. The mirror's `Packages/manifest.json` holds the built-in modules and uGUI of the `minimal` config, which like the mirror holds Base without an optional SDK, Base from this checkout as a `file:` path, found by the name in its `package.json`, and with `--with-unitask` the UniTask commit that the `full` config's lock file pins; without `--editor-version` its `ProjectVersion.txt` is the `minimal` config's, so the harness runs the Editor that config names, or `UNITY_EDITOR`. No config is opened or changed. Keep `--work-dir` short on Windows: the command warns when the mirror path passes 100 characters, which a deep worktree reaches, since Unity's `Library/` and the IL2CPP build add their own long paths below it. A `--work-dir` outside the checkout goes in a folder of its own in the unit's folder under the machine's `MU3_WORK_ROOT`, such as `di-strip-harness/` beside the projects the shell entrypoints generate there, never in a drive root and never the unit's folder itself, which the harness would refuse once it holds those projects: [overview.md](../.ai/project/wiki/overview.md) «Development Projects» names that root and the `<unit>` the examples above use.

The harness changes and deletes files only in a work folder it made. It writes the marker file `.mu3-di-strip-harness` into a `--work-dir` that does not exist or is empty, and refuses any other folder without that file before it touches anything, so a wrong `--work-dir` cannot cost a project its assets. A work folder made before the marker existed, such as an older `log/di-strip-harness`, is refused too: delete it yourself or pass another `--work-dir`, and the next run imports a new mirror.

The command exits 0 only when the player built, exited 0 within `--player-timeout` (120 seconds by default), logged every check as passed and as many checks as it counted, and logged no error or exception; 1 only when the player ran and a check failed or it did not report; and 3 when the run stopped around the player instead: the work folder was refused, the mirror or the previous player and logs could not be prepared or removed (a file another process holds, a missing permission, a malformed or incomplete package manifest or lock file, or a malformed package file of the Editor `--editor-version` names), the build failed or passed `--build-timeout` (3600 seconds by default), or the player could not be started. Exit 3 prints one `error:` line with the cause rather than a traceback, so automation does not read a setup problem as a DI regression. Once the player ran, its checks decide the exit code: nothing after them turns it into 3. It also prints the total size of the managed DLLs for Mono and of `GameAssembly.dll` for IL2CPP, and only warns when it cannot read them.

## Verification Build

`mu3-verify-build` builds a Windows x64 player of a project generated from the `full` config, with the Addressables content or without it, for a check that needs a player, such as one across processes:

```bash
PYTHONPATH=tools/cli/src python -m verify_build --content none --work-dir "${MU3_WORK_ROOT:?set MU3_WORK_ROOT}/Mu3Library_ForUnity/<unit>/verify-build"
PYTHONPATH=tools/cli/src python -m verify_build --content build --work-dir "${MU3_WORK_ROOT:?set MU3_WORK_ROOT}/Mu3Library_ForUnity/<unit>/verify-build"
PYTHONPATH=tools/cli/src python -m verify_build --content none --no-build
```

- The project is `full/` in `--work-dir`, `log/verify-build` by default, generated and refreshed from the config as the shell entrypoints do it ([Unity Project Configs](#unity-project-configs)), with this checkout's working tree as its packages and Base's samples linked in. Give it a folder of its own, apart from the projects the shell entrypoints generate in the unit's folder: the command claims its work folder as a whole. A later run reuses the project and its `Library/`; `--fresh` deletes the project, its links first, and the players, and generates a new one.
- The `full` config's Addressables settings hold no remote profile and no remote catalog, and their one group builds into the project's own `Library/com.unity.addressables/aa`, which a player build copies into `StreamingAssets/aa` (ADR 0001 D17). `--content build` sets `m_BuildAddressablesWithPlayerBuild` to `1` (`BuildWithPlayer`), so that the content builds with the player whatever the Editor preference says, and passes only when the player carries the content, `VerifyBuild_Data/StreamingAssets/aa/settings.json`. `--content none` sets it to `2` (`DoNotBuildWithPlayer`) and is refused on a project whose `Library/com.unity.addressables/aa` holds an earlier content build, which the player would carry; pass `--fresh`. The values come from the order of `AddressableAssetSettings.PlayerBuildOption` in the source of Addressables 2.11.2, and the build logs of #480 read them back as `BuildWithPlayer (1)` and `DoNotBuildWithPlayer (2)`.
- In the project only, it also sets `companyName` and `productName` to `Mu3LibraryVerify` and `VerifyBuild`: a player keys its `persistentDataPath`, where Addressables keeps a downloaded catalog, and its PlayerPrefs on those names, and with `m_DisableCatalogUpdateOnStart: 1` it loads a catalog cached there in place of its own, as a player under the config's names did on 2026-11-15 from what the former bundle deployment had left on the PC (#499). Last, it adds [verify-build/Editor/Mu3VerifyBuild.cs](verify-build/Editor/Mu3VerifyBuild.cs) as `Assets/Mu3VerifyBuild/Editor/Mu3VerifyBuild.cs`, from the checkout's working tree. The next refresh writes the config's settings back, and the command changes them again.
- `--no-build` stops there, with a project to open in the Editor. Otherwise the command runs the Editor that the project's `ProjectVersion.txt` names, or `UNITY_EDITOR`, with `-executeMethod Mu3VerifyBuild.Build`. The script reads back the player build option as Unity loaded it, and the build path of every group and of a remote catalog, and refuses to build when the option differs from what the command wrote or a path lies outside the project, before a content build could write there. It builds one empty scene, or each `--scene`, an asset path of the project such as a scene of the Multiplayer sample below `Assets/Mu3LibrarySamples/`, judges the build by a result of `Succeeded` only (see step 5 of [Fresh Clone Setup](#fresh-clone-setup)), and logs `MU3VERIFY` lines, which the command prints. Unity may take `--build-timeout` seconds, 3600 by default, to open the project and build; then the command stops it and the processes it started, with `taskkill /T` on Windows, as `mu3-di-strip-harness` does. The player goes to `players/content-<mode>/VerifyBuild.exe` and Unity's log to `content-<mode>-build.log`, both in `--work-dir`; the command does not run the player.

The command refuses before it writes anything when the project folder would have 98 characters or more on Windows, the length from which Unity cannot read every package file and a content build fails. It changes and deletes files only in a work folder it marked: it writes `.mu3-verify-build` into a `--work-dir` that does not exist or is empty, and refuses any other. The command exits 0 when the project is ready and, with a build, the player built as `--content` asks; 1 when Unity exited non-zero, passed `--build-timeout`, built no player, built a player without the content with `--content build`, or built content with `--content none`; 2 on a usage error; and 3 when it could not prepare the project, start Unity, or read Unity's log afterwards, with one `error:` line that names the cause.

## Environment

The shell entrypoints and `mu3-unity doctor` read the same variables, so the Editor and the work folder the doctor accepts are the ones the script uses. Listed in `.env.local`, the Unity variables are set in every terminal that enters the [development environment](#development-environment); `MU3_WORK_ROOT` belongs in the user environment, which agent shells inherit too ([overview.md](../.ai/project/wiki/overview.md) «Development Projects»).

| Variable | Effect |
|---|---|
| `MU3_WORK_ROOT` | Absolute folder outside the checkout, such as `D:/w`, or one that starts with `~` for the home folder (a relative one stops the run), below which the shell entrypoints generate each unit's projects, in `${MU3_WORK_ROOT}/Mu3Library_ForUnity/<unit>/<target>`, unless `--work-dir` names another folder. Keep it short on Windows, where a long path pushes Unity's package cache past the path limit. |
| `UNITY_EDITOR` or `UNITY` | Path to a Unity executable (or `Unity.app`) used for every target instead of the version in `ProjectVersion.txt` or the one `--editor-version` names. |
| `UNITY_HUB_EDITOR_ROOT` | Folder that holds one folder per installed Editor version, for a Unity Hub set to install Editors outside its default location (`C:\Program Files\Unity\Hub\Editor`, `/Applications/Unity/Hub/Editor`, or `~/Unity/Hub/Editor`). |

On Windows the script runs in the bash of Git for Windows. `mu3-unity` finds it even when only `git` is on `PATH`; see [cli/README.md](cli/README.md#bash-on-windows).
